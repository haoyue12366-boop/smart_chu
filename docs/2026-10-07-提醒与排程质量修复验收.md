# 提醒流、五分钟出菜与排程预算修复验收

用户确认的优先级是：先使多道菜出锅时间差不超过 300 秒，再减少总人工工作量，再减少总流程。初排 5 秒以内算优秀，最多 7 秒，尽量稳定。2026-10-07 用户确认“现在可以切换了”，默认重排已改为 5000ms，版本 p6-quality-v2。本报告对应工作区源码；阶段进度只登记在 [task.md](task.md)。

切换前 3 秒重排预算的完整实验有质量反例，失败材料全部保留。5 秒候选通过完整实验后，经用户授权发布为新默认；切换后的完整真实 HTTP 复测单列，不把候选报告改写成新版本通过证据。

## 如何判断修复成功

1. **提醒可靠性：** 用真实 TCP、独立 SQLite 数据库开始 SSE，取得首帧后持有 `BEGIN IMMEDIATE` 写锁，覆盖多个真实轮询周期。同一连接持续心跳；解锁后收到新提交消息；游标只前进一次，`Last-Event-ID` 重连不重复；执行事实保持不变。响应开始前的锁仍返回合法 JSON 503。仅恢复 SQLite BUSY/LOCKED，其他错误不被吞掉。
2. **约束正确性：** 每个实际发布结果重新加载当前问题和运行快照，由独立 Validator 扫描。检查全部工序覆盖、人工互斥、物理设备、容量与温度、预热、先后及有限间隔、物料来源和数量、冻结执行与库存事实。再扫描比赛五字段响应和真实串行参考对应的 `timeSave`。
3. **质量：** 对固定代表菜单和事件三轮运行，全部请求保留在分母。直接用实际计划的 `max(各菜完成时刻)-min(各菜完成时刻) <= 300秒` 判定，不以求解器返回成功替代。总人工和总流程与修复前实际请求配对，另列连续人工工作块的代价。
4. **性能：** 计时覆盖完整本机 HTTP 请求和响应；同时记录服务耗时。初排超过 5 秒不算优秀，超过 7 秒不满足用户上限；新默认重排超过 5 秒不达预算，旧 3 秒实验按其原上限保留结果。冷启动与显式预热单列，不混入在线请求指标；独立验收扫描及归档在请求计时之外。
5. **验收边界：** 全部固定请求正确、时限及五分钟指标通过，且运行期间源码指纹不变，才接受该轮。代表集重复通过是本机样本证据，不能证明任意菜单、任意负载或真实烹饪中的最坏耗时。

## 实际实现

- `app/api/notifications.py`：SSE 开始后遇到 SQLite BUSY/LOCKED，清空待输出批次并在下一周期从原游标重试；心跳继续，不重发已输出批次、不推进烹饪执行。初始查询仍在响应头之前完成。
- `data/policies/p6-quality-v2.json` 和 `app/config.py`：用户授权的新默认质量策略；原 `p4-runtime-v1.json`、`p6-quality-v1.json` 及候选策略保留。初排总预算 7000ms，构造上限 300ms、求解上限 5000ms、发布预留 600ms。重排总预算 5000ms，构造上限 400ms、求解上限 2800ms、发布预留 1400ms。这些是共享截止时间内的阶段上限，不是各阶段依次领取新时间。
- `app/scheduling/objectives.py`、`ranking.py`、`engine.py`：采用整数精确优先级“超出五分钟的部分 → 总人工 → 总流程”。先搜索五分钟达标区间，未取得合法候选才尝试软目标；UNKNOWN 不当作不可行。只有精确的该目标序列走新行为，自定义/旧目标序列保持其原语义。
- 没有冻结事实时，有限逐道 Greedy 构造可独立核验的串行参考，减少额外进程调用；它是合法参考，不宣称串行最优。有冻结事实时使用完整原路径，历史不平移。参考仍须通过独立约束校验和串行顺序核对。
- 严格五分钟区间内，只有在逐候选证明所有完整覆盖方案的人工量相同、且没有执行历史时，才把恒定人工项化简为总流程目标。人工工作量可变化的共享案例仍使用完整目标。化简不修改任何工序时长或来源。
- `cp_sat.py`、`json_worker.py`、`worker.py`：按完整问题身份缓存基础模型，每轮克隆阶段约束；同进程后续消息可引用已确认的问题，仍完整验证作业。缓存传输身份与建模计时身份分别维护，超时/进程退出清空。旧计划部分工序只作为搜索提示，新菜保持自由，不冻结未执行任务。
- `model_builder.py`：为诊断映射建立目录序号的查询索引，替代逐约束反复扫描和集合构造。维度内并集、维度间交集，筛选后再归并诊断 ID，重复 ID 也保持原逐记录语义。约束、报告及不可行核归属没有删减。
- `candidate_pool.py`：累计校验耗时继续报告；下一候选的预留采用已实际测到的单次最大开销的两倍，最低 150ms，避免把多次累计耗时再次扣除。完整扫描和 SQL 发布预留继续执行。

## 为什么响应快，解质量如何解释

在线读不可变知识快照，使用本机 SQLite 和已就绪的 CP-SAT 工作进程，不为每个请求调用 LLM 或 Neo4j。菜单只有 3—5 道菜，编译后是有限载体和整数秒的约束模型；构造提供合法回退，求解器可能在预算耗尽前就返回。预算是上限，设为 7 秒不会强制等满 7 秒。

原先快速返回确实不等于质量高：原核查中五分钟出菜和人工阶段经常未完成。现在以独立约束扫描、五分钟完成差、人工工作量、实际总流程和求解状态/界共同评估。`OPTIMAL` 只证明当前保留候选模型的目标最优；工艺输入和名义时间正确性仍依赖真实审核和烹饪验证。前端已有“完成时间差”和“最长连续人工”供直接核对。

## 人工工作量与必要代价

排程不能把固定的切菜、搅拌等真实工作凭空变短。当前发布中，共享备料的很多时长仍等于各份工作相加，改变顺序只改变工作安排，不减少总工作量。本轮不修改这些知识时长。

新增可独立枚举的共享反例检验目标有效性：单独加工总人工 240 秒，共享加工 180 秒，强制被动过程给出总流程 240 秒的下界；求解结果须同时达到五分钟、180 秒人工和该流程下界，且由独立 Validator 接受。真实发布菜单另做开启/关闭共享的实际对照，结果单列，不用合成下降代替真实下降。

集中出菜可能增加等待或连续工作块。配对比较直接报告真实 makespan、剩余总流程、总人工和连续忙碌，不用 `timeSave` 的变化归因于修复，因为新旧串行参考构造和请求预算不同。
