# 扰动实验失败问题记录

记录日期：2026-10-05。关联任务：P6-03、P6-06。

本文保留修复前实验结果，并记录已复现的模拟器问题。2026-10-05 的反例固化、启动窗口修复，以及后续持续反馈、可选快速重排和关键窗口保护的验证记录见 [task.md 的 P6-03 修复记录](task.md#p6-03)。任务进度和验收状态以 task.md 为准。

## 1. 问题与证据

修复前模拟器的合成时长扰动实验出现大量执行失败，原缓冲与单次重排没有显示整体收益。以下统计绑定原模拟器版本；实验完成不等于抗扰动能力达标，也不能直接代表修复后的失败率。

基线为 [P6-robustness-run2/report.json](../benchmarks/reports/P6-robustness-run2/report.json)：40 个菜单，每个 100 条轨迹，四组共 16000 条。各组使用相同菜单和配对随机轨迹，未来扰动由模拟器持有，不提前进入调度输入。

| 实验组 | 策略 | 完成数 | 失败数 | 总数 | 失败率 |
| --- | --- | ---: | ---: | ---: | ---: |
| NOMINAL_SHIFT | 名义排程，顺延执行 | 855 | 3145 | 4000 | 78.6% |
| NOMINAL_REPLAN | 名义排程，允许一次观察触发重排 | 837 | 3163 | 4000 | 79.1% |
| BUFFERED_SHIFT | 开工前缓冲，顺延执行 | 767 | 3233 | 4000 | 80.8% |
| BUFFERED_REPLAN | 开工前缓冲，允许一次观察触发重排 | 764 | 3236 | 4000 | 80.9% |

全部轨迹完成 3223 条，失败 12777 条，失败原因如下：

| 报告中的失败原因 | 条数 |
| --- | ---: |
| 模拟器判定实际最大工艺间隔超限 | 12553 |
| 初排没有通过独立校验的完整候选 | 200 |
| 重排时运行阶段已到预计结束，需确认完成或更新剩余时长 | 14 |
| 重排没有通过独立校验的完整候选 | 8 |
| 离线重排绑定超出固定 2400ms 预算 | 2 |

最大工艺间隔类失败占全部失败约 98.2%，应作为首要诊断对象。这一分类来自模拟器判断，不能据此断言所有轨迹都已客观不可挽救。

实验使用合成时长分布，并受工艺允许边界约束；固定热过程及固定程序阶段保持不变。上述失败率不能直接解释为真实厨房失败概率。完成差、延迟等完成轨迹指标需与全部轨迹失败率一起阅读，避免只看成功样本。

## 2. 对程序的影响

- 实际开始、完成或剩余时长偏离估计后，设备与人工安排、预计出菜时间可能失准，需要重排。正常初排通过不能证明扰动执行也能完成。
- 重排无法得到完整合法计划时，程序保存已发生的事实，保留已有计划作为历史记录，记录失败原因并阻止新的执行任务启动。已有计划不能被视为当前状态下仍然合法的可执行方案。
- 前端显示“事实已保存，本次未发布合法计划”。后续处理可能需要补充剩余时长、确认实际结果、调整任务，或使用已审核的恢复路径；不能假定这些操作一定能挽救已经错过的工艺窗口。
- 当前默认使用 NOMINAL。BUFFERED 仍是可选实验策略，本次结果不支持默认启用。

实际服务与原四组实验的重排触发范围不同：服务会根据操作时间偏差、剩余时长更新、设备和物料等事件触发重排；原实验仅观察初排中最早的一个可扰动阶段，该阶段完成延迟达到 30 秒才重排，之后不再触发。若该阶段未达到阈值，后续延迟也不会触发实验重排。两个原重排组各实际触发 853 次，不能据此评价持续反馈重排的效果。

新增七组比较保留原四组口径，另外比较快速单次重排、快速持续反馈及快速关键窗口保护。持续反馈逐个处理实际开始、实际完成和剩余估计事件，复用服务的 `replan_reasons`，同秒事实合并后计算；计算输入只包含当时可观察状态与当前已发布计划。预计结束仍未完成时报告固定 30 秒的合成剩余估计，不能称为实测，不能从私有未来时长计算精确剩余量。重复反馈不重复落账，过期状态结果不发布，未确认完成不释放占用。

用户选择的可选 `replan_search_mode=FEASIBILITY_FIRST` 仅用于重排：取得完整合法候选和同一状态的已验证串行参考后提前发布，构造失败继续实际 CP-SAT，省略后续可选质量优化；初排和默认 `OPTIMIZE` 保持优化流程。所有阶段共享会话策略指定的截止时间。该模式会牺牲可选目标优化，报告不能将其标为已优化人工、稳定性或出菜差。

可选 `critical_window_policy_id=SERIAL_RECIPE_V1` 将菜单中前一道菜的全部汇点连接到后一道菜的全部源点，限制同时展开的菜谱数。它按菜单实例顺序建立带策略来源的依赖，独立校验器重新核对来源，真实执行入口也检查该顺序；不会改写原菜谱工艺、固定热过程或资源容量。该保守方案减少跨菜争用，但可能显著增加总用时和出菜差，因此需连同失败率与时间代价一起比较。两个新增字段的默认值不写入原策略 JSON，保持默认策略版本身份。

两份可直接读取的版本策略为 [快速重排](../data/policies/p6-feedback-fast-v1.json) 和 [快速重排加逐菜保护](../data/policies/p6-feedback-critical-v1.json)，均保留原 4200/2400ms 预算。开发服务可通过 `SMART_COOKING_POLICY_PATH` 指向选定文件；Windows 安装目录的 `policy.json` 采用同一契约。新建会话保存选定策略，已有会话仍使用其已绑定策略，不能以修改文件推定旧会话已换策略。

快速并行分支现已补齐 `timeSave` 所需参考计算：当前完整候选本身满足串行顺序时复用本轮校验结果，否则在原求解总额度内计算并独立校验串行参考。参考也参与候选比较，选出总用时不超过参考的真实计划；不通过截断负数修改统计值。取消全部菜品的合法空计划以自身为参考，实际节省为零。缺少参考或预算不足时明确失败，保留已提交事实并阻止旧计划派发。串行参考、候选、持久化问题快照绑定同一菜单、知识、状态和时间原点。

用户于 2026-10-06 允许重排总预算适当放宽至 3000ms；新增 [快速重排 v2](../data/policies/p6-feedback-fast-v2.json) 采用 4200/3000ms，初排/重排 Solver 额度为 3000/2100ms，新增的 600ms 分配给重排求解阶段。人工、设备和工艺约束保持原口径。原 v1 策略与历史报告保留；2400ms 和 3000ms 均进行固定菜单对照，构造失败保留原 CP-SAT 优化回退。新建会话可通过 `SMART_COOKING_POLICY_PATH` 选择 v2，已有会话继续使用已绑定版本。修复进度与实际验收结果统一见 [task.md](task.md)。

内部事件接口为 `POST /api/v1/sessions/{session_id}/events`。调用方应读取响应业务 `status`；该接口的 HTTP 200 也可能包含 `FAILED`，不能只凭 HTTP 状态码认定新计划已成功发布。

## 3. 已确认限制与待验证原因

### 已确认的策略限制

1. 原四组实验的单观察点、最多一次重排限制了对后续扰动的纠偏能力；新增持续反馈组逐个处理可观察事件，原四组作为对照保留。
2. BUFFERED 将允许估计阶段总名义时间的 15% 作为菜谱开工前等待，不预约等待期间的人工或设备，也不为内部关键衔接窗口单独留余量。实验结果未显示整体收益。
3. 运行中阶段缺少有效完成确认或剩余时长反馈时，重排会明确阻塞。缺失观测不能按已经完成或剩余时间为零处理。

### 已复现的模拟推进缺陷

模拟器计算可启动阶段时，以当前时间和原计划启动时间为基础，再根据依赖完成偏差调整；若得到的预计启动时间超过最大间隔，会直接结束轨迹。

三工序合成反例：A 名义 180 秒、实际 120 秒，B 为固定 60 秒等待，C 名义 60 秒，依赖 A 的零最大间隔和 B 的完成。旧模拟器取多个前驱的最大完成偏差，仍建议 C 在 180 秒启动，因而在 120 秒结束轨迹。C 实际可在 120 秒立即启动，流程在 180 秒完成并通过独立终态校验。

原归档 `combination-000 / NOMINAL_SHIFT / 000` 也复现同类问题：当前时刻和合法窗口上界均为 1706 秒，原计划偏差算法建议 1778 秒启动；运行时状态转换接受在 1706 秒启动。回归见 [合成窗口与占用测试](../tests/integration/test_robustness_dispatch.py)、[原归档前缀回放](../tests/integration/test_robustness_archive_replay.py)；窗口计算见 [dispatch.py](../benchmarks/robustness/dispatch.py)。

修复将名义计划时间保留为执行参考，实际启动必须满足已观察前驱的最小/最大间隔、用户延期、显式根节点缓冲和真实资源占用。编译器按名义时长传播的界不当作实际执行的绝对门槛。窗口内调整保留原资源/载体绑定，不产生新的已发布计划；需要求解的新绑定仍由重排负责。失败记录分别标明窗口关闭、窗口无交集、缺少观测、资源阻塞和重排失败。

该缺陷在原 12553 条间隔类失败中的全量占比仍未量化。小规模对照按 [compare_dispatch.py](../benchmarks/robustness/compare_dispatch.py) 共用原归档初排并加载已保存的旧源码；旧策略和修复策略使用相同菜单、种子、知识、单次重排规则及预算。小规模结果不代替 16000 条全量复验。

新增 [210 条七组配对实验](../benchmarks/reports/P6-feedback-critical-small-run2/report.json) 中，快速持续反馈完成 17/30，快速单次完成 14/30，逐菜保护完成 14/30。持续反馈有 6 条失败转完成、3 条完成转失败，逐菜保护相对持续反馈有 3 条失败转完成、6 条完成转失败。两个持续组的所有完成轨迹均超过 300 秒出菜差，逐菜策略还明显增加总用时。这些结果支持保留可选模式及明确质量标志，尚不支持默认启用逐菜保护或宣称综合质量达标。[配对汇总](../benchmarks/reports/verification/P6-feedback-critical-fix/comparison-summary.json) 将全部失败、仅完成样本的时间指标和两组都完成的配对差分别记录。

## 4. 建议修复顺序

1. **先诊断并验证模拟器。** 为失败轨迹补充具体依赖、真实前序完成时间、允许启动窗口、当前时刻、计划启动时间与资源占用信息。构造已知可挽救和已知无法挽救的反例，区分计划过期、实际窗口超限、缺少反馈和资源阻塞；确认后修正推进逻辑。
2. **对齐持续反馈重排。** 保留原单次重排组，新增与实际服务触发规则一致的实验组。开始、完成和剩余时长变化均通过明确事件进入状态；关键窗口临近耗尽时及时评估重排。事件先持久化，计算使用最新状态，每次重排共享既有截止时间，保持幂等和条件发布。
3. **保护关键工艺衔接。** 在版本化可选策略中优先保障紧最大间隔的连续工序所需人工与设备，必要时推迟其他菜开工或减少同时展开的任务。再比较关键窗口缓冲与原开工前等待策略；任何资源预留都须进入正式约束并经独立校验。
4. **逐步扩大验证。** 先验证反例，再运行代表性菜单的小规模配对实验；有效后完成全量对照，并复验实际 HTTP、前端状态、通知、性能及 Windows 交付。正式验收所需外部条件继续单列。

修复过程中保持固定热时长、最小/最大工艺间隔、单人人工及设备容量要求；不覆盖实际历史，不提前释放未确认资源，不向调度器泄露私有未来时长。源工序时长、实际工作量和策略缓冲分别建模。

## 5. 建议验收标准

以下标准区分本次模拟器修复与后续持续反馈、策略和全量工作；各项实际验证证据统一见 task.md：

- 前序提前完成、延后完成、零最大间隔及紧间隔衔接反例得到正确结果；已知可挽救用例能恢复，已知不可挽救用例明确失败。
- 第一个观察阶段未达到阈值、后续才出现延迟的用例能够按持续反馈策略触发重排；多次扰动不会因已经重排一次而失去后续纠偏。
- 未确认完成、缺少剩余时长、设备未释放、重复事件及过期计算结果均保持现有约束，不产生虚假成功或重复物料效果。
- 使用相同菜单、随机种子、知识和扰动分布比较策略；如同时修改模拟器，旧策略和新策略都在修正后的同一模拟器中重跑，单独记录模拟器版本影响。
- 保留全部失败在总分母中，分别报告完成率、失败原因、完成差、延迟、实际重排次数、缓存命中和计算耗时；不只比较成功轨迹的时间指标。
- 改进策略降低同口径失败率，同时评估出菜时间和人工连续工作等代价；具体降幅目标在诊断后确定，不预先保证所有扰动均可完成。
- 初排服务内总预算保持 4200ms，重排保持 2400ms，复验 P50、P95、最大耗时和超预算率；正确性检查不能为满足预算而省略。
- 原实验报告与轨迹归档保持不变，新实验使用独立目录记录命令、退出码、源码/数据哈希、种子和实际耗时。涉及程序变更时重新生成并验证纯 Windows 交付包。

## 6. 相关位置

### 可选连续工艺链保护

`data/policies/p6-window-guard-v1.json` 使用 `dispatch_guard_policy_id=TIGHT_HUMAN_V1`，初排预算为 4200ms、重排预算为 3000ms（Solver 上限 2100ms），搜索模式仍为 OPTIMIZE。默认策略的保护开关为 NONE，默认序列化不增加字段，原策略文件保持原身份。通过 `SMART_COOKING_POLICY_PATH` 指向该文件创建新会话；已存在的会话继续使用其已绑定策略。

保护逻辑在开工前识别具有有限最大间隔的工艺链，合并同一承载体、连续占用范围以及链中经过的依赖路径。先完成整条链的外部前序，并确认后续所需资源没有被其他执行占用；链开始后，其他争用这些资源的阶段等待链中相关阶段真实完成。保护只是派发选择，不登记额外占用，不推测未来释放时刻，也不延长最大间隔。链已经开始后的合法接续由实际窗口与资源检查决定，风险策略不再阻断接续。

`app/runtime/dispatch_windows.py` 提供实际启动窗口的纯函数，运行模拟入口和扰动实验使用同一实现。实际运行仍经 RuntimeService 的事务、触发与暂停派发规则；偏移触发重排后应在当前观察时刻处理重排，再继续派发。此策略采用保守等待，可能增加总用时和出菜差，不能据此保证任意扰动或未确认设备反馈都能完成。固定轨迹、质量代价与实际验收证据统一记录于 task.md。
