# P5 运行与接口说明

工作台与接口默认使用固定发布 `delegated-v3-multilayer-onepot-v1-all`，在线启动、初排、重排和知识查询读取快照。任务验收状态以 [task.md](task.md#p5) 为准，检查记录见 [P5实施记录](P5实施记录.md)。

## 本地启动

在项目根目录运行，环境为 Python 3.12、Node 25.8.1 / npm 11.11.0：

```powershell
npm --prefix web ci
npm --prefix web run build
& '.venv\Scripts\python.exe' -m uvicorn app.main:create_app --factory --host 127.0.0.1 --port 8000
```

打开 `http://127.0.0.1:8000/` 使用工作台，`http://127.0.0.1:8000/docs` 提供交互接口测试。默认运行库为 `data/runtime/p5.sqlite3`，保持同一文件可恢复会话、请求与历史计划。环境变量 `SMART_COOKING_DATABASE_PATH` 可指定其他运行库。

用户于2026-10-07授权修正出锅口径并移除总人工优化。2026-10-08的新默认策略 `p6-cook-prepared-multilayer-v1` 保留目标：依次优化超出300秒的出锅差、最长连续人工操作、总流程；累计人工仅统计。60秒及以上空档开始新的连续人工块。优化保留原有总时长硬限制：不超过本轮合法串行参考；取得出锅达标种子后，额外总时长最多为其5%且不超过120秒。纯连续操作的单菜可能因此无法插入额外休息，优先级不表示无约束全局最优。预算沿用初排7000ms、重排5000ms，设备受限导致五分钟不可达时如实显示超标。发布前在共享预算内尝试提前独立的冷却、切分和装盘等收尾，保留出锅时刻，且不恶化连续人工及候选排序；改善后的完整候选仍经独立校验。

重启后端，浏览器强制刷新并点击“新的一桌”使用新策略；已有会话保留原知识和策略。若设置环境覆盖，请将 `SMART_COOKING_POLICY_PATH` 指向 `data/policies/p6-cook-prepared-multilayer-v1.json`，并将 `SMART_COOKING_RELEASE_ID` 改为 `delegated-v3-multilayer-onepot-v1-all`，`SMART_COOKING_RELEASE_ROOT` 仍为 `data/preparations/p4-v1/releases`。本轮已构建web/dist；依赖已有时无需重复安装。原部署ZIP未被此源码修复自动更新。

用户确认开工前能完成的浸泡、腌制、冷藏等准备按已提前备好处理，不计入本轮调度。新策略以绑定菜谱内容的明确工序清单声明准备及所需食材；页面“开工前准备”保留菜名、原步骤时长和假设来源，比赛 `recipeDetail.cookingSteps` 同样列出无加工时间区间的说明。准备不产生设备预约、人工操作或实际完成事件。包含蒸煮烘烤等厨具加工的步骤，以及炒熟后放凉、馅料冷却等中途等待仍正常调度。旧策略继续计入原准备时间，重排不迁移旧桌策略，也不改写过去事实。

用户确认蒸箱、烤箱为两台独立设备，各有三层。同一设备不同层只有温度相同且模式、湿度等配置兼容才能同时在场；各菜按原时长分层放入和取出，取放仍受唯一人工约束。同一完整设备预约保持实际层集合；轻松一锅蒸从原放托盘步骤到取出同时占第1、3层，只执行一份工艺，第2层可同温兼容复用。执行反馈、重排冻结及未释放占用保留实际层位。新知识保留原时长和配置：124个配置一致的预约开放层位复用，5个预约中途改变温度或模式，仍整腔独占。新策略关闭原可选STRICT_TOGETHER合批；不把不同时长合成统一加热。设备甘特图分别显示“蒸箱 · 第1/2/3层”“烤箱 · 第1/2/3层”，重叠复用区间带金色内框及“复用”标记，悬浮卡显示实际复用时间。

出锅时刻采用逐菜审核的主体取出工序结束时间；多次加热取最终主体边界、多主体取最大，月饼冷却及FINISH仍计入总流程但不推迟出锅。取出与点缀合并的原段保留其粒度，珍珠爆浆蛋糕的珍珠末段无独立盛出时间，使用热处理结束代理；这些为计划估计，非厨房实测。完整100菜代理审核记录见 `data/preparations/cook-finish-v1/review.json`。库存替代若覆盖出锅节点且缺少原出锅时间，明确拒绝，不能以接收时刻伪造出锅。

工作台有“安排”“执行与反馈”“历史版本”“接口测试”四个入口。安排页选菜并初排，已有会话时每次追加一道。甘特图支持按设备与人工、按菜品分组，完整日期与秒级区间来自后端。执行页提交明确的开始、完成、数量与异常反馈；设备恢复和本次执行清空分别确认。模拟模式需点击推进按钮，记录带 `SIMULATED` 来源。

## 自动计时与剩余重排

新建工作台会话及比赛任务默认采用 `SCHEDULE_CLOCK`。初排成功发布后自动开始计时，重排和服务重启沿用首次锚点；开始、完成及按配方推算的用料均保留独立来源，页面显示“计划时钟推算”。这不等同设备实测，人工或设备反馈仍可修正当前进度。已有人工/模拟会话保持原模式，新建会话时可显式选择 `MANUAL_CONFIRM` 或 `SIMULATED`。

加菜和“重新优化剩余操作”先同步插入时刻的执行状态，立即计算并发布未来计划，不等待在途蒸制或烘烤结束。已完成及正在执行的操作保留时间、设备层位和执行身份，不能中断的必要衔接继续受约束；其他操作可使用空闲人工、设备和兼容层。新增任务不得早于插入时刻，也不排入求解期间已经过去的时间；发布事务再次检查版本与生效时刻。计划时钟不重置，完成反馈只在实际时间经过后产生。设备异常仍需有效反馈，不按原预计时间伪造完成。

页面在重排操作及甘特图附近显示正在优化和当前版本，新计划发布后自动更新。当前版本优先展示，历史对照版本读取失败不阻止新甘特图出现。求解并发或预算耗尽时仍可返回PENDING，后台继续已提交请求，与等待烹饪结束无关。本菜自身占两层不标成跨菜复用。

`GET /api/v1/sessions/{session_id}` 的 `clock_progress` 提供 `started_at`、`current_offset_sec`、`replan_requested_sec`，并兼容旧字段 `replan_not_before_sec`、`replan_not_before_at`、`waiting_for_boundary`。新重排不再设置全局等待边界；时间偏移仍基于原会话原点。待重排状态及必要衔接持久化保存。

后台推进按桌次隔离异常；某桌错过实际工艺窗口时暂停其后续派发并显示原因，其他桌继续推进。旧版本恢复错误不能覆盖已经修正的新状态。合法库存替代可满足前置工序，不生成虚假的备料执行记录。

工作台按钮调用 `POST /api/v1/sessions/{session_id}/replan`，提交 `{}` 和 `Idempotency-Key`；服务端先同步时钟，再按当前版本登记纯重排命令，避免页面轮询稍晚就拒绝重排。人工执行反馈仍通过原事件接口提交明确版本，冲突后刷新核对，不自动改写其版本。

倒排提示以当前最晚出锅为目标，整体移动完整设备预约和关联后续，再交给 CP-SAT。出锅差仍超过300秒时，优先用剩余预算改善出锅差，保留完整合法候选和既有流程上界。发布前压紧所有尚未开始的设备预约，包括中间炒制；完整前缀、内部紧密衔接的步骤一起后移，优先清除最长空档，并在需要时保留人工休息。该整理在原共享预算内最多分配200ms，仍保留独立校验时间，不延长请求总预算。工艺时长、同温三层条件和人工约束不变。限时求解不保证任意菜单达到五分钟，也不将 UNKNOWN 当作不可行证明。灶眼一、灶眼二及冷藏、冷冻区按真实部件分别显示；悬停保持菜色。

每个操作完成时，执行事件和 `OPERATION_COMPLETED` 通知在同一事务提交。通知含菜名、操作名、`task_ids`、`execution_id`、`source`、`completed_at` 和逻辑时间偏移。工作台和接口测试页显示完成横幅与持久通知列表，按通知身份去重；断线重连可用游标补收。

## 比赛初排与加菜

比赛使用同一个接口：

```http
POST /api/competition/plan?task_id=meal-001
Content-Type: application/json
Idempotency-Key: meal-001-initial

[{"name":"低温牛排","id":"61e6c51fec6e1d65587067e1"}]
```

首次任务可传一道或多道菜。已存在的同任务追加时只传新增的一道，并使用新的请求身份：

```http
POST /api/competition/plan?task_id=meal-001
Content-Type: application/json
Idempotency-Key: meal-001-add-1

[{"name":"酿苦瓜","id":"6492a7a5933a4b7277dee0cf"}]
```

成功顶层恰好为 `overview`、`cookingTimeline`、`ingredientsSummary`、`detailTimeline`、`recipeDetail`。追加后覆盖累计活动菜单，时间区间相对首次会话原点；分钟使用 HALF_UP 保留一位小数，内部仍为整数秒。查询参数位置、累计响应与固定原点是用户授权的项目设计。

`task_id` 关联同一桌菜，`Idempotency-Key` 标识一次请求。重复请求保持相同键和内容；同键异内容返回冲突。已有任务传多项明确拒绝。省略 `task_id` 时每个新身份独立初排。ID 用于身份判断，名称用于核对；同名菜按各自 ID 选择。

出现超时、503 或结果未确认时，工作台可用原请求身份重试。只有实际提交且通过独立校验的完整计划返回成功；重排失败会保留已接受事实，并显示实际结果。HTTP 响应提供 `X-Request-ID` 和 `Server-Timing` 供排查与计时。

比赛加菜直接尝试即时发布；作业繁忙或本次预算未完成时返回 HTTP 503 / `PLANNING_PENDING`，表示事件已接受且尚未发布，不是不可行结论。页面显示优化中，发布后使用原幂等键取回五字段响应。

显式重排使用 `POST /api/competition/replan?task_id=meal-001`，JSON为 `{}`，携带新的 `Idempotency-Key`。未完成计算时返回 HTTP 202 / `PENDING`，后台继续处理；用相同键重试可获取最终结果。完成通知使用 `GET /api/competition/notifications?task_id=meal-001&after=0`，实时订阅使用 `GET /api/competition/notifications/stream?task_id=meal-001`，支持 `Last-Event-ID` 断点续读。这些独立接口不增加原比赛排程响应的顶层字段。项目 profile 为用户授权的 `p5-task-clock-v2`，不是官方动态协议已联调的声明。

## 内部接口与重排触发

| 方法与路径 | 用途 |
| --- | --- |
| `GET /health/live`、`GET /health/ready` | 存活、知识/状态库/求解进程就绪 |
| `GET /api/v1/recipes` | 固定菜谱目录和设备事实 |
| `GET /api/v1/recipes/{recipe_id}/graph` | 只读工艺子图 |
| `POST /api/v1/sessions` | 创建自动时钟、人工或模拟会话并初排 |
| `GET /api/v1/sessions/{session_id}` | 当前事实、菜单和版本 |
| `POST /api/v1/sessions/{session_id}/recipes` | 同步服务端时钟后追加一道菜，核对计划版本 |
| `POST /api/v1/sessions/{session_id}/events` | 提交普通业务事件 |
| `GET /api/v1/sessions/{session_id}/plans/{version}` | 只读已发布计划、问题与展示 DTO |
| `GET /api/v1/sessions/{session_id}/operations/{task_id}/feedback` | 准备开始草稿；`completed=true` 准备完成草稿 |
| `POST /api/v1/sessions/{session_id}/language-events` | 自然语言转明确业务意图或澄清 |
| `GET /api/v1/sessions/{session_id}/notifications?after={cursor}` | 持久提醒补读 |
| `GET /api/v1/sessions/{session_id}/notifications/stream` | SSE；支持 `Last-Event-ID` |
| `GET /api/v1/competition-tasks/{task_id}` | 比赛任务对应的会话 |

内部初排示例：

```json
{
  "event_id": "workbench-initial-001",
  "mode": "SCHEDULE_CLOCK",
  "recipes": [{"id":"61e6c51fec6e1d65587067e1","name":"低温牛排"}]
}
```

工作台加菜命令提交到 `POST /api/v1/sessions/{session_id}/recipes`，先读取当前 `base_plan_version`，同一请求重试保留原 `event_id` 与请求体。服务端同步时钟后绑定最新状态版本；旧计划版本和重复菜品仍拒绝。

```json
{
  "event_id": "workbench-add-001",
  "base_plan_version": 1,
  "recipes": [{"id":"6492a7a5933a4b7277dee0cf","name":"酿苦瓜"}]
}
```

加菜命令复用持久事件链。取消未开始菜品、明确开始时间偏好、实际剩余时长和设备/物料异常通过普通事件接口处理，仍带唯一 `event_id`、当前 `expected_state_revision` 和 `base_plan_version`；不自动改写人工反馈的版本。事实先在短事务中提交，必要重排在事务外执行，发布前检查状态与计划版本。响应区分 `PUBLISHED`、`NO_REPLAN`、`PENDING`、`FAILED`、`EVENT_REJECTED`。开始/完成等反馈是否重排由服务判断；读取计划、子图、提醒不会写执行事实。

人工反馈应先读取草稿、核对实际数量再提交 `/events`。模拟会话通过 `ADVANCE_SIMULATION` 显式推进，不能把服务器经过的时间或提醒到达当作完成。设备恢复保留实际占用，清空需确认相应 `execution_id`。

自然语言默认关闭。启用时设置 `SMART_COOKING_LANGUAGE_ENABLED=1`，凭据从本地 `.env` 或环境变量读取。明确意图仍须通过当前知识和版本校验；模糊、无效或超时不提交业务事件。语言归档分别保存模型解析与实际业务处理结果，成功业务结果关联事件及发布身份。

## 验收

前端独立检查：

```powershell
npm --prefix web run typecheck
npm --prefix web run format:check
npm --prefix web run test:unit
npm --prefix web run build
```

完整当前开发验收需实际停止本机 Neo4j，结束后恢复原状态：

```powershell
$p5GraphWasRunning = (docker inspect --format '{{.State.Running}}' smart-cooking-knowledge-neo4j-1).Trim()
$env:SMART_COOKING_TEST_RELEASE_ROOT = (Resolve-Path -LiteralPath '.tools/p2-regression/releases').Path
try {
    if ($p5GraphWasRunning -eq 'true') { docker stop smart-cooking-knowledge-neo4j-1 }
    & '.venv\Scripts\python.exe' -X utf8 scripts/verify.py --phase P5 --gate development
    $p5VerificationExit = $LASTEXITCODE
} finally {
    if ($p5GraphWasRunning -eq 'true') { docker start smart-cooking-knowledge-neo4j-1 }
}
if ($p5VerificationExit -ne 0) { throw 'P5 开发验收失败，请查看报告。' }
```

本机历史 P2 发布目录权限异常，测试使用经内容校验的同版本副本；生产仍读取固定 P4 发布。完整入口实际执行 P3/P4 前置回归、P5 八任务、前端工具链及三条真实浏览器流程，报告为 `benchmarks/reports/verification/P5-development.json`。真实模型测试与离线阶段验收单列；原正式入口 `--phase P5` 和最终官方外部联调门槛保留。
