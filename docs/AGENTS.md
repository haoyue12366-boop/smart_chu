## 1. 工作方式与变更范围



- **C01 先读任务再修改。** 每次实现读取本文件、task.md 中目标任务及其前置任务结果，以及目标任务引用的架构章节。以任务编号定位工作，不凭聊天摘要重新设计接口。

- **C02 依赖通过再接入。** 执行依赖某个接口或输入的工作前，该依赖必须已经存在并满足约定；不能用临时假接口绕过缺失依赖。可以使用明确标注的测试替身验证尚未接入的外部服务。P1-09 的数据补齐允许提前推进，但依赖 P2 的全量单菜验收必须等 P2 通过。

- **C03 任务范围。** 修改目标任务的生产文件、对应测试和必要的包导出、配置、锁文件及验收登记。必要的局部修复可以随任务完成并记录原因；公共契约变化同步修改直接调用方、测试与任务记录。

- **C04 授权范围内连续推进。** 阶段验收是证据门槛，不是默认要求每个任务、每个阶段重复向用户申请许可。按用户当前授权范围推进；真实缺失的工艺依据、协议语义或外部权限不能由等待时间代替确认。

- **C05 不扩大项目。** 首版不引入微服务集群、Redis、Celery、Kubernetes、Neo4j GDS 强制依赖、真实硬件控制、自训练模型或未经任务定义的新菜谱。

- **C06 保留材料。** 根目录比赛资料、聊天图片、原始 CSV 和设备文件作为只读证据；不解压或读取用户排除的项目 ZIP。处理结果写入 data/，不覆盖原始文件。

- **C07 如实交付。** 文档写出命令不代表命令已经运行；实现完成不等于验收通过；样本成功不等于 100 道全量通过；内部模拟重排不等于官方动态协议已联调。

- **C08 设计冲突处理。** 用户明确的新要求优先于项目文档；官方事实与项目默认策略分别记录。发现架构、任务或代码冲突时定位证据并作最小一致修正；涉及新增业务规则或尚未明确的官方语义时保留问题，不自行编造。

- **E03** 用户于 2026-10-02 明确选择本机 Node.js 25；P5 开发基线固定为当前 Node 25.8.1 / npm 11.11.0，使用 Vite 并提交 package-lock.json。TypeScript 开启 strict；组件测试使用 Vitest，浏览器端到端使用 Playwright，具体入口见 task.md。接入时以实际安装、构建和测试验证兼容性，禁止依赖浮动 latest。Node 版本属于项目工程选择，比赛材料未限定版本；本条取代原 Node 24 LTS 选型。

- **E04** 用户于 2026-10-04 明确选择“完全使用 Windows，调整 P6-07 验收要求”。开发、测试和最终部署目标均为 Windows，P6-07 验证 Windows 独立目录安装、离线启动、持久化和重启恢复，不再要求 Linux 或容器。使用 pathlib 和跨平台子进程参数数组；不硬编码本机盘符、用户目录、路径分隔符或默认系统编码。此条替代原 Linux 容器部署选择；比赛要求 API 公网可访问，未强制操作系统。

- **E05** Python 源文件使用 UTF-8、4 空格缩进、snake_case 函数与变量、PascalCase 类型。所有公开函数和领域字段提供类型标注。文档、错误说明和面向用户的文案使用清楚的中文，协议字段和代码标识保持稳定英文。

- **E06** 代码按职责拆分。单文件约 500 行、单函数约 80 行作为检查是否需要拆分的提醒，不作为机械拆文件的硬指标；复杂度应来自实际约束，不能把多个模块塞进一个 service.py。

- **E07** 禁止在模块导入时连接数据库、调用模型、启动工作进程、读取会话或运行排程。配置装配和资源生命周期统一由应用入口管理。

- **E08** mypy 对项目代码检查；第三方类型缺口以局部适配器或有说明的局部忽略处理，不整体关闭检查。禁止用全局 Any、宽泛 except 后返回成功或大量 type: ignore 掩盖契约问题。



## 3. 目录职责与依赖方向



项目根目录就是代码仓库根目录，不再额外套一层 project/。架构文档附录中的 project/ 表示根目录占位。下表是可执行的导入边界：



| 目录 | 职责 | 可依赖的项目模块 | 禁止事项 |

| --- | --- | --- | --- |

| app/domain/ | 标识、时间、数量、契约、枚举与端口协议 | 本层公共类型 | 数据库连接、HTTP、LLM、OR-Tools 求解器对象 |

| app/pipeline/ | 抽取、规范化、审核、发布、快照导出 | domain、llm、knowledge 的离线投影接口 | 在线请求临时修改已发布知识 |

| app/knowledge/ | 图谱投影、规则、快照及索引 | domain | 在线 Repository 查询 Neo4j；导入包即连接图数据库 |

| app/compiler/ | 菜谱实例化、候选、依赖、边界、约束目录 | domain、内存规则与快照接口 | 写运行库、调用在线 LLM、调用求解器选择结果 |

| app/scheduling/ | Greedy、CP-SAT、目标、预算、诊断 | domain、共享的纯数学工具 | 直接查图、读取 SQL 会话、生成官方 JSON、写执行事实 |

| app/validation/ | 独立检查知识覆盖和候选计划 | domain、正式知识事实 | 以求解器或 Compiler 的约束生成函数代替独立校验 |

| app/runtime/ | 执行事件、物料账、状态机、恢复和模拟 | domain、存储端口 | 把未标记的计划推算冒充设备或人工反馈；从状态转换中同步运行求解器 |

| app/storage/ | SQLite 仓储、事务和迁移 | domain | 定义菜谱工艺、决定排程顺序 |

| app/llm/ | 供应商适配与结构化调用记录 | domain | 直接修改会话、发布菜谱、决定最终数值计划 |

| app/services/ | 初排、事件处理及重排编排、条件发布 | 上述应用模块和端口实现 | 绕过 Validator 发布；成为领域规则的第二份来源 |

| app/api/ | 协议 DTO、路由、错误和时间投影 | services、domain | 内嵌优化算法、直接操作业务表 |

| web/ | 菜谱选择、甘特图、子图、事件反馈 | 后端公开接口 | 直接连接 Neo4j 或 SQLite；自行重算权威计划 |

| tests/、benchmarks/、scripts/ | 测试、实验、验收命令 | 对应公开接口和测试辅助模块 | 在成功路径中依赖伪造数据替代真实发布知识 |



- **A01** 共享业务事实定义在 domain 和已发布知识中，不能复制一份设备温度表到 UI、Compiler 或 Solver。

- **A02** 使用依赖注入装配 Provider、Repository、Clock 和 Planner；Protocol 定义在 domain/ports.py，具体实现位于各自模块。避免为每个小函数新增无意义接口。

- **A03** 对外数据使用 Pydantic 契约；算法内部可使用 dataclass、tuple 和紧凑映射。ORM 对象不得跨出存储边界进入 Solver。

- **A04** SchedulingProblem 创建后不可变；problem_hash 绑定菜单、知识、策略、状态及时间原点。求解后的实际模型统计与 proto 索引写 SolverBuildReport，不回填修改问题。

- **A05** 独立校验可以共用只读领域事实和基础单位转换，但必须独立扫描覆盖、资源、物料、热过程及历史，不直接接受“求解器说可行”。



## 4. 数据、知识与版本约束



- **D01** 固定 100 个菜谱 ID，两个同名菜保持不同身份。recipe_id、recipe_instance_id、task_id、carrier_id、execution_id 不得混用；数据库唯一性和 API 校验按 ID 执行。

- **D02** 原文、模型建议、审核估计、实测及人工修改分别保留来源。字段缺失产生 DataIssue，未知时长不能默认成 0。AI 生成字段不能自行标为人工 APPROVED。用户于 2026-09-29 明确授权代审后，允许以 DELEGATED_AGENT 身份批准绑定内容哈希的完整路径；必须记录授权原文、代理身份和检查证据，不伪装人工实测。底层来源不改写，批准范围与功能验收分别记录，详见 [P4 准备基线](P4准备与规则基线.md)。

- **D03** 正式发布仅包含通过审核的执行路径。开发样本发布使用 sample 标识，禁止以它通过 100 道正式验收。

- **D04** 规范化 JSON 是知识重建来源；Neo4j 用于离线关系与规则维护；SchedulingKnowledgeSnapshot 是在线静态知识来源；SQLite 保存运行事实。在线初排、重排、启动和就绪检查不依赖 Neo4j 可用。

- **D05** 图谱、快照、索引、manifest、来源与审核引用必须版本一致。构建新发布失败保留原发布；会话绑定固定知识版本，缺失该版本时不能自动换成最新版本。

- **D06** 模板依赖、可共享规则、候选选择与实际执行关系分开。相同食材不自动形成工序先后；相同模式不自动选择共批。

- **D07** 抽取归档保存实际渲染输入、原始返回、模型标识、参数、Schema、解析与规则版本、审核补丁和哈希。哈希不能代替原始内容；本地重放与重新调用外部模型分别报告。

- **D08** 归档、实验和固定用例注明真实或合成来源。测试数据不能悄悄流入正式 knowledge_release；原材料哈希用于追溯，不代表工艺已经验证正确。

## 6. 运行事实与异常边界



- **R01** plan_version、state_revision 和 knowledge_version 含义不同；事件到达后先短事务确认事实，再在事务外计算重排，以原 state_revision 条件提交新计划。

- **R02** 实际开始、完成、失败和物料变化必须有事件来源。手动或设备模式不因计划时间到达而自动完成；模拟事件标记 SIMULATED。用户于2026-10-08明确授权默认 SCHEDULE_CLOCK：首次成功发布后自动计时，推算的开始、完成及物料变化明确标记“计划时钟推算”，不冒充人工或设备实测；人工、设备反馈可修正当前进度。重排不重置时钟，过去和已开始的时间/资源事实冻结；用户随后要求立即重排，故保留在途操作及必要衔接约束后直接计算未来计划，不等待烹饪结束。新增任务不得早于插入及发布生效时刻。

- **R03** 同 event_id 的重复请求产生同一次业务效果；同 ID 不同载荷返回冲突。实际消费、产出、损耗和重做不得因重试重复发生。

- **R04** 物料分配记录预约与实际消费的区别；已消费不回滚为可用，未知半成品不当作合格库存；所有数量使用明确单位和缩放规则。

- **R05** availability_status 与 occupancy_status 分开。设备故障、工序失败或设备恢复均不单独证明腔体已清空；释放需对应 execution_id 的有效确认。

- **R06** 重做创建新 execution_id，保留旧失败记录；续做必须存在审核过的工艺路径。没有恢复规则则明确阻塞或失败，不现场发明工艺。

- **R07** 人工修正限白名单，不直接覆盖已完成时间、物料或工艺约束；历史录入问题采用有来源的追加纠正记录。

- **R08** 未提交的事务不返回成功；提交结果不明时查询持久化身份。通知记录与计划发布原子写入，以去重键投递，重排撤销失效提醒。

- **R09** 服务重启恢复已提交事实与固定知识版本。数据库迁移逐版本保留，不用删除运行库解决迁移或状态错误。

- **R10** SQL 锁期间不运行 Solver 或等待 LLM；CPU 求解在常驻进程运行，不阻塞 FastAPI 事件循环。



## 7. 性能预算与资源限制



以下是初始工程目标，不是已经测得的成绩或对任意输入的保证：



| 参数 | 初排 | 重排 |

| --- | ---: | ---: |

| 服务内总预算 | 4200 ms | 2400 ms |

| Greedy 总预算 | 150 ms | 100 ms |

| CP-SAT 全阶段总预算 | 3000 ms | 1500 ms |

| 校验、发布、序列化预留 | 400 ms | 300 ms |



- **P01** 所有阶段共享单调时钟截止时间；重试、变体及优化阶段不能重复领取完整预算。最后校验和发布需保留时间。

- **P02** 默认一个 API 实例、一个并发调度作业、一个常驻 Solver 工作进程，搜索线程最多 4；改变资源须重新压测，不能默认多并发达标。

- **P03** SQLite busy_timeout 初始 100 ms，写重试最多 2 次，仍服从全链路和发布剩余预算。超时不返回未提交计划。

- **P04** 深度诊断默认离线按需执行，预算 2000 ms、单搜索线程、最多 6 次冲突缩减检查；不占用比赛实时调度队列。

- **P05** 记录编译、知识提取、Greedy、CP-SAT、校验、发布及序列化耗时；分开记录服务内、客户端、冷启动和已预热结果。

- **P06** 在固定硬件和数据集上报告 P50、P95、最大耗时、超时率、回退率及失败原因。模型规模、截断与最优界必须带版本和目标阶段。

- **P07** 若无法在预算内得到完整合法计划，返回诚实失败；不得省略工序、跳过检验或只输出旧计划来满足耗时目标。



## 8. API、大模型与展示



- **I01** 比赛 POST /api/competition/plan 接收直接菜谱数组；成功响应只包含 overview、cookingTimeline、ingredientsSummary、detailTimeline、recipeDetail，不添加 code/message/data 包装。

- **I02** 官方数组请求主体不擅自增加 session_id 或事件字段；9 月 30 日答疑建议用 task_id 关联多轮排程，首次排程后同任务单菜输入为加菜。P5 开发采用显式上下文 profile，查询参数位置、响应范围与时间原点属于项目草案，见 [P5 准备基线](P5准备与接口基线.md)。内部 /api/v1 接口可显式会话化，两者由 Adapter 隔离；业务 task_id 不得与工序 TaskId 混用。

- **I03** 名称用于展示与核对，身份仍按 ID。日期和秒级信息内部保留；跨日及官方 HH:mm 的表达问题不得静默丢失。

- **I04** 结构化比赛请求不依赖在线 LLM。自然语言入口先解析与校验，明确意图后生成普通业务事件；不理解或超时不声称已完成操作。

- **I05** 通知、甘特图、指标和比赛 JSON 均来自同一已发布计划；UI 不自行重排，LLM 不另行生成权威时间和设备参数。

- **I06** LLM、数据库凭据通过环境变量提供；.env.example 只包含变量名与无效示例值，不提交密钥、运行库、真实会话或大量原始调用日志。

- **I07** U01—U14 外部问题以设计第 23 节及 9 月 30 日答疑为依据：任务关联已有 task_id 建议，排程后单菜增量输入已明确；具体传递位置、执行进度、动态响应范围和时间原点仍待确认。使用显式开发 profile 和内部协议推进测试，官方联调保持单列状态，不能因输入答疑已明确而宣称全部动态协议已验证。



## 9. 测试与验收纪律



- **T01** 每个涉及行为的任务先写能暴露目标错误的测试，再实现并验证。修正文档、格式等低影响工作不机械新增镜像测试。

- **T02** 固定工序正确性、数量守恒、事件幂等、资源释放、旧版本拒绝及强制工艺必须在对应任务内验收；不能全部留到 P6。

- **T03** 测试分单元、契约、集成、属性、状态机、故障和实验。纯测试默认不访问外部服务或收费模型；真实 Neo4j/LLM 检查显式标记，缺少所需环境记为未执行，不能算通过。

- **T04** 代表真实样本与合成反例分开。可行见证生成器、结构合法生成器、已知矛盾生成器分别定义预期，不要求随机问题必然可行。

- **T05** 检查 Validator 能拒绝故意错误计划；不能只测试正常样例。精确最优性用小规模独立枚举核对，不用同一 Solver 充当自己的标准答案。

- **T06** 端到端验收必须使用真实 Compiler、Greedy、CP-SAT、Validator 与存储路径；测试替身可以验证局部接口，不可充当全链路交付证据。

- **T07** 证据包含命令、退出状态、用例数、版本/数据哈希、随机种子、实际耗时及报告位置。跳过、预期失败、环境不可用和结果不确定单独列出。

- **T08** 不设脱离行为的“覆盖率越高越正确”目标；重要不变量和失败路径必须覆盖。禁用测试、放宽硬约束或篡改基准来变绿属于验收失败。

- **T09** 设备验收覆盖架构 8.6 矩阵：既拒绝同资源冲突，也接受合法跨设备并行、冰箱共享和审核共批；包含同腔体别名、单人人工介入、模式转换、故障未释放及可选设备实际通道。真实样本与补足边界的合成反例分别记录。



P0-01 建立以下统一命令入口，此前这些命令仅是待实现的接口：



~~~text

uv sync --locked

uv run --locked ruff check .

uv run --locked ruff format --check .

uv run --locked mypy app

uv run --locked pytest tests/unit tests/contract
~~~

uv 的 --locked 在锁文件与项目配置不一致时应报错而非更新；依据见 [uv 锁定与同步](https://docs.astral.sh/uv/concepts/projects/sync/)。Ruff 的检查和格式化入口分别见[检查文档](https://docs.astral.sh/ruff/linter/)与[格式化文档](https://docs.astral.sh/ruff/formatter/)；mypy 的目录检查依据见[官方文档](https://mypy.readthedocs.io/en/stable/running_mypy.html)。



scripts/verify.py 是阶段验收工具，不承担业务逻辑。它按 task.md 的阶段登记执行检查；找不到必需测试、依赖服务或产物时返回非零，不因跳过检查而报成功。P1 区分 --gate core 和 --gate full，后续阶段依赖见 task.md。



## 10. 任务完成与交接



一个任务满足以下全部条件才能标为 VERIFIED：



1. 前置任务及输入版本符合约定，生产代码和必需测试实际存在。

2. 任务验收断言、相关回归与质量检查通过，未绕过硬约束。

3. 没有生产路径占位实现、未处理的必需分支或仅靠 mock 的交付。

4. 接口和直接消费者一致，配置与迁移可复现。

5. 在 task.md 对应任务记录完成内容、实际验证命令、证据及仍存在的外部限制。

6. 核对文件范围；不夹带未授权的材料改写、无关重构或生成文件。



阶段 VERIFIED 还必须通过该阶段明确的入口、出口及集成验收。P1 的 core 检查只允许后续样本开发，不能把 P1 全量状态改为 VERIFIED。用户授权完成当前阶段时，交付到该阶段边界；用户授权整体实施时，符合下一阶段入口后继续推进。



任务量或接口确需调整时，在 task.md 修订记录中说明拆分、合并、依赖及验收影响，保持旧任务 ID 可追溯。不要仅因预计文件数或测试数量变化就重新规划整个项目。
