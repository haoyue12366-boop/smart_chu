# 智能烹饪调度项目技术方案与架构设计

版本：1.5  
日期：2026 年 10 月 2 日  
对应赛题：ZX-2026-0302 智能烹饪调度 Agent  
文档性质：供项目开发、数据整理、实验评估和参赛技术说明共同使用的设计基线。文中的性能数值是目标或初始配置，不表示已经实现或通过测试。

本项目面向固定 100 道菜谱，为一次选中的多道菜生成满足设备、人工、物料和工序依赖的并行烹饪计划，并在执行中支持新增菜品和动态重排。采用“大模型辅助知识整理、知识图谱管理工艺关系、统一调度模型编译、Greedy 构造可行解、CP-SAT 限时优化、独立校验、事件驱动执行”的组合方案。

数据准备与在线调度分开。最终参赛服务读取已经补全、审核并发布的菜谱数据，不在每次请求中重新解析 100 道原文，也不等待人工审核。在线服务从离线发布的不可变知识快照提取本次请求所需知识；共享前处理与共同加热是否实际采用，由调度算法结合本次菜单和执行状态决定。

## 1 目标与交付范围

### 1.1 核心目标

1. 将固定菜谱转换为可追溯的原子工序和物料转换关系。
2. 在两灶眼、蒸箱、烤箱、冰箱等资源条件下安排多菜并行制作。
3. 发现并选择合法的跨菜共享前处理和共同加热方案。
4. 综合控制总耗时、菜品完成时间差、累计人工用时和连续人工忙碌时长；累计人工目标为 P4 待实现增补。
5. 重调度时保留已执行事实，重新优化未完成部分。
6. 输出符合比赛要求的 JSON，并形成可操作的步骤说明和通知。
7. 通过独立校验与受控实验说明方案正确性、性能和各机制的贡献。

### 1.2 功能范围

| 类别 | 纳入正式方案的内容 |
| --- | --- |
| 数据工程 | 100 道菜谱解析、缺失补全、冲突处理、审核、版本发布 |
| 知识管理 | 菜谱、工序、物料规格、设备配置、前置关系、规则与证据 |
| 初始排程 | 工序内外并行、人工与设备约束、预热、长准备时间 |
| 共享加工 | 可选共享前处理、单独加工回退、共同蒸烤和批次取放 |
| 动态执行 | 会话、执行状态、物料库存、设备状态、计划版本 |
| 重调度 | 新增菜品为核心；同一事件框架支持延迟、取消与状态修正 |
| 输出 | 比赛接口、计划解释、通知、甘特图和重排差异 |
| 评估 | 数据质量、可行性、优化效果、响应耗时、消融实验 |

首个可验收版本完成规范化数据通路、单独排程、共享切配、同温同模式同时长批次及模拟执行重排。原菜谱已经明确的中途加料、取出翻拌、分批加工属于必须解析的工艺事实，不因通用批次能力分阶段建设而被省略。

本次通用跨菜蒸烤限定为严格共同批次，不实现任意不同菜品的自由中途加入、取出或自动推导复杂温度曲线；原菜谱明确的固定分段程序必须保留。后续扩展这些能力需要另行修订工艺规则、调度模型及验收边界。实际物联网设备控制、硬件通信协议、自训练大模型、微服务集群不作为本次比赛核心交付前提。

### 1.3 三类对象必须分开

- **知识模板**：一道菜通常包含什么工序，需要什么物料和设备。
- **本次计划实例**：本轮菜单中的工序、候选分组、资源预约与计划时间。
- **实际执行事实**：已经完成的操作、产出的物料、真实开始结束时刻和当前设备状态。

模板不能因一次重排被覆盖；计划不能被直接当作实际完成记录。

### 2.3 原始数据特征及影响

现有 CSV 有 100 个唯一 ID、99 个唯一名称、762 个原始编号步骤。编号步骤常包含多个动作，因此 762 不是最终调度任务数。76 条菜谱含屏幕提示类描述，说明需要补足其中未明确的信息，不意味着这些菜谱所有参数都缺失。

两条“麻辣对虾”的 ID 不同，不能按菜名合并。香菇烤芦笋包含菜内并行；家常鲈鱼、鸡翅包饭涉及设备接力；亲朋欢聚套餐含中途加料；糯米烧麦明确分两批；鸡仔饼、广式叉烧等包含超过或达到 24 小时的准备。以上案例进入设计验收集。

菜谱与设备清单存在温度、档位、模式和设备缺失冲突。正式数据发布前逐条处理，不进行未经依据支持的温度裁剪或设备替换。问题与默认处理见第 5、23 节。

## 3 技术选型与决策理由

### 3.1 方案比较

| 方案 | 优点 | 对本项目的不足 | 决策 |
| --- | --- | --- | --- |
| 大模型直接生成时间表 | 原型交互快、解释方便 | 难稳定保证全局约束和动态一致性 | 用于语言处理，不作为最终排程器 |
| 结构化 JSON 加 CP-SAT | 组件少，易做算法基线 | 工艺关系、规则证据和跨菜查询需另外组织 | 保留为受控实验和可移植数据通路 |
| 规范化数据加图谱、编译器、Greedy、CP-SAT | 知识维护与求解解耦，支持共享候选与解释 | 需要治理两种模型并控制候选规模 | 采用 |

采用图数据库的依据是关系管理、规则追溯和共享机会组织。相同图算法也可以在内存 DAG 上运行；不把图数据库本身写成加速求解的保证。

### 3.2 技术栈

| 层次 | 选型 | 职责与边界 |
| --- | --- | --- |
| 服务语言 | Python 3.12 | 数据管道、规则、调度、API 共用类型与领域模型 |
| API | FastAPI、Uvicorn | 请求校验、路由、内部管理接口、事件流 |
| 数据契约 | Pydantic 2 | 字段类型、枚举和结构校验；业务合法性由规则层负责 |
| 求解器 | Google OR-Tools CP-SAT | 整数时间变量、可选区间、互斥、条件约束和限时优化 |
| 图数据库 | Neo4j Community 单实例，官方 Python Driver | 离线知识维护、规则校验、审核和快照导出 |
| 图预处理与快照 | Python 内存邻接表、拓扑算法、版本化 JSON 快照 | 离线知识索引、在线 DAG 检查、闭包和候选筛选 |
| 运行状态 | SQLite，SQLAlchemy 2，版本化迁移 | 会话、事件、计划、实际工序、库存与通知 |
| 大模型 | 供应商无关的 LLMProvider 接口 | 离线抽取、可选在线意图和语言说明 |
| 前端 | Vue 3、TypeScript、ECharts | 菜谱选择、甘特图、子图、执行模拟、重排差异 |
| 测试 | pytest、Hypothesis；固定数据集与小规模精确枚举器 | 契约、属性与状态机测试、故障注入、回归和对比实验 |
| 部署 | Windows 固定运行时、离线依赖、PowerShell 启停 | 可复现部署与公网服务，固定发布产物；2026-10-04 用户修订 |

Python 3.12 是本设计的目标运行版本。其他依赖在实现时通过兼容性检查后固定精确版本，形成锁文件；Windows 交付固定运行时、离线依赖和部署包哈希。文档不将浮动的 latest 标签作为部署版本。

FastAPI 的异步接口负责 I/O 协调；CPU 求解放到常驻工作进程，不直接阻塞事件循环。[FastAPI 官方并发说明](https://fastapi.tiangolo.com/async/) Pydantic 提供结构化数据验证，但“某模式下温度是否合法”“批次是否过度加热”等由领域校验器检查。[Pydantic 模型文档](https://docs.pydantic.dev/latest/concepts/models/)

### 3.3 数据存储选择

规范化 JSON 发布包是菜谱知识的可重建来源；Neo4j 承担离线关系维护、审核和发布校验；SchedulingKnowledgeSnapshot 是在线调度唯一的静态知识入口；SQLite 是执行事实和计划版本的主要存储。在线服务从本地发布快照启动，初排与重排均不实时查询 Neo4j。

Neo4j 支持 ACID 事务。这里拆出运行状态库是为了简化事件、计划发布、幂等和日志查询，而非数据库不具备事务能力。[Neo4j 事务文档](https://neo4j.com/docs/operations-manual/current/database-internals/transaction-management/)

首版 SQLite 使用本地持久卷、WAL 和短写事务。WAL 允许读与写并行，但同一时刻仍只有一个写者，不据此设计多写者集群。[SQLite WAL 文档](https://www.sqlite.org/wal.html)

## 4 总体架构与模块职责

### 4.1 总体架构

~~~mermaid
flowchart TB
    subgraph Offline["离线知识整理与发布"]
        Raw["原始菜谱与设备文件"] --> Extract["大模型辅助抽取"]
        Extract --> Review["规则校验与人工审核"]
        Review --> Canonical["规范化 JSON 发布包"]
        Canonical --> Graph["Neo4j 关系维护与校验"]
        Graph --> Export["快照导出与一致性校验"]
        Export --> Artifact["知识快照与 KnowledgeIndex 文件"]
    end
    subgraph Online["在线调度"]
        Artifact -->|启动或显式版本加载| Snapshot["不可变内存快照"]
        API["比赛请求或内部事件"] --> Adapter["接口适配器"]
        Adapter -->|规划请求| Service["调度应用服务"]
        Adapter -->|执行与异常事件| Runtime["运行事件处理"]
        Runtime -->|事实提交| State["运行状态库"]
        Runtime -->|触发重排| Service
        State --> Service
        Snapshot --> Compiler["调度问题编译器"]
        Service --> Compiler
        Compiler --> Problem["SchedulingProblem 与约束目录"]
        Problem --> Greedy["Greedy"]
        Problem --> Solver["CP-SAT"]
        Greedy --> Hint["可行方案与提示"]
        Hint --> Solver
        Greedy --> Validate["独立调度校验器"]
        Solver --> Validate
        Validate --> Publish["版本检查与计划发布"]
        Publish --> State
        Publish --> Output["比赛 JSON 与展示投影"]
    end
    subgraph Execution["执行与重排"]
        Output --> UI["甘特图与操作提醒"]
        UI --> Event["确认 模拟与异常事件"]
        Event --> Adapter
    end
    Problem -. "失败快照与约束目录" .-> Diagnose["独立诊断任务"]
~~~

在线主流程在完成校验和发布后立即返回结果。重调度由后续事件触发。图谱导出发生在离线发布阶段；在线使用静态知识快照，并结合实时状态生成本次候选。深度诊断作为离线或独立维护任务，不进入实时调度工作进程的等待队列。

### 4.2 模块契约

| 模块 | 输入 | 输出 | 核心责任 |
| --- | --- | --- | --- |
| RecipePipeline | 原文、人工补全、设备规则 | 审核记录、数据发布包 | 数据抽取、规范化与发布 |
| SnapshotExporter | 通过审核的图谱版本与发布清单 | SchedulingKnowledgeSnapshot、KnowledgeIndex | 离线导出并校验静态知识与证据索引 |
| KnowledgeRepository | 已加载快照、菜谱 ID 集合 | MenuKnowledgeView | 从内存提取固定版本知识，不进行数据库查询 |
| RuleEngine | 工序、物料规格、设备配置 | 规则判断及证据 | 判断配置与候选是否合法 |
| ProblemCompiler | 知识快照、菜单、运行快照、策略 | SchedulingProblem | 实例化、生成候选、边界和冻结约束 |
| GreedyScheduler | SchedulingProblem、截止时间 | 可行候选或构造失败说明 | 快速构造与有限修复 |
| CpSatScheduler | SchedulingProblem、提示、预算 | 求解状态、候选计划、界与诊断引用 | 联合选择方案与安排时间 |
| InfeasibilityAnalyzer | 问题快照、约束目录、失败阶段 | DiagnosticReport | 快速预检与独立限时深度诊断 |
| ScheduleValidator | 问题、计划、知识和状态依据 | ValidationReport | 独立核对领域不变量 |
| PlanningService | 规范化请求 | 发布结果或明确错误 | 编排流程、版本校验与预算 |
| RuntimeService | 已去重的执行事件 | 新运行快照 | 状态迁移、物料账与设备状态 |
| CompetitionAdapter | 官方请求、发布计划 | 官方 JSON | ID 解析、协议和时间投影 |
| NotificationService | 已发布计划及执行状态 | 通知记录、事件推送 | 生成、撤销、去重与触发提醒 |
| BenchmarkRunner | 固定用例、配置、种子 | 可复现指标 | 正确性与效果评估 |

### 4.3 依赖约束

1. 求解模块只接收 SchedulingProblem，不直接读取 Neo4j、调用大模型或修改数据库。
2. 编译器生成中立领域对象，不能把 OR-Tools 变量写进持久化菜谱。
3. 运行状态只能通过 RuntimeService 和事务发布路径修改。
4. 校验器共用数据契约与设备事实，不调用 CP-SAT 约束构造函数判断正确性。
5. 比赛输出来自已校验计划；前端展示和通知共用同一计划版本。
6. 在线调度的启动、初排、重排与健康就绪检查使用已发布的本地快照，不依赖 Neo4j 可用；只有离线发布和独立知识管理工作访问 Neo4j。
7. 在线大模型输出经过校验后形成请求或文字；不得直接写入资源预约和实际完成状态。


<a id="s05"></a>
## 5 离线数据整理和发布

### 5.1 执行时机

离线流水线按数据版本运行。首次整理覆盖 100 道菜；后续修正只重新处理受影响的菜谱和规则。服务重启读取本地发布包与 SchedulingKnowledgeSnapshot，不重新调用大模型，也不重新要求人工审核。

离线流程：

~~~mermaid
flowchart LR
    A["原文与设备清单"] --> B["字段抽取和工序拆分"]
    B --> C["结构与领域校验"]
    C --> D["问题清单"]
    D --> E["人工补全与审核"]
    E --> F["规范化菜谱"]
    F --> G["图谱构建与一致性检查"]
    G --> H["发布清单与内容哈希"]
    H --> I["激活新知识版本"]
~~~

### 5.2 原子工序拆分规则

工序的粒度由调度需求决定。出现以下任一变化时拆分：

- 操作所需资源改变，例如人工切配转为无人腌制。
- 物料状态形成可供其他工序使用的明确产物。
- 存在可单独安排的并行分支。
- 设备配置发生变化，或加热过程要求中途人工介入。
- 原文明确分批、取出、翻拌、再放回。
- 某一部分具有独立的最小等待、最大间隔或不能中断要求。

不将每个动词机械地拆成任务，也不将整段“准备、腌制、烤制、装盘”作为一个资源占用区间。原文编号用于证据定位，实际依赖由物料流和工艺要求确认。

例如“腌制期间准备酱汁”形成两个分支；“另取一锅”必须核实是否存在实际物料依赖；原文次序本身不自动生成所有相邻硬约束。

### 5.3 补全与冲突处理

| 问题 | 处理方式 | 发布条件 |
| --- | --- | --- |
| 缺少人工操作时长 | 大模型或规则提出估计，人工确认计划用值与依据 | 已审核，有时长来源 |
| 设备屏幕提示但缺少模式或时长 | 建立待补字段，逐条查阅和审核 | 所需参数完整 |
| 温度、火力超出设备范围 | 记录冲突；审核具体替代工艺或参数映射 | 有明确修订依据，不自动截断数值 |
| 缺少设备，例如原文要求微波 | 审核是否存在原文可选工艺或可接受的替代工艺 | 至少一条完整合法执行路径 |
| 食材与步骤用量冲突 | 保留两个来源，人工确定执行用量 | 已记录选用值与理由 |
| 数量为适量、少许 | 保存定性量，不强行换算为克 | 可执行；涉及数量敏感共享时禁用该候选或补足用量 |
| 工序依赖形成环 | 定位物料或拆分错误，返回数据修订 | 前置依赖投影无环 |
| 原文有 24 小时准备 | 保留时长与跨日属性 | 时间域和输出策略可承载 |
| 纯装盘描述 | 保留输出里程碑；必要取出和浇汁独立建模 | 不在加热结束前完成取出或收尾 |

具体已发现问题包括 240℃ 超过参考烤箱上限、8/9 档超过灶具 1 至 7 档、35℃ 发酵模式缺失、独立上下火温度未描述等。不得用“清单最终参数”推导出“直接把所有越界值改成边界值”。

### 5.4 审核状态与来源

审核状态采用 DRAFT、NEEDS_REVIEW、APPROVED、RETIRED。发布包只包含 APPROVED 的正式执行路径。

来源分为原文显式值、原文推导、人工估计、人工实测、外部依据、模型建议。审核人员确认一个估计值可以用于计划，不等于确认它绝对准确。

confidence 若保留，必须同时说明它是抽取启发评分还是经过标定的概率。初版不将模型自报的 0.95 解释成 95% 正确，也不让 confidence 自动缩短加工时长。

### 5.5 数据发布包

~~~text
knowledge_release/
  manifest.json
  recipes.json
  material_specs.json
  device_types.json
  device_profiles.json
  processing_rules.json
  duration_models.json
  provenance.json
  review_records.json
  extraction_runs.json
  extraction_artifact_index.json
  compatibility_report.json
  scheduling_knowledge_snapshot.json
  knowledge_index.json
  snapshot_validation_report.json
~~~

manifest 记录 schema_version、knowledge_version、rule_version、snapshot_schema_version、snapshot_id、exporter_version、创建时间、原始文件哈希、各产物哈希、菜谱数和审核结果。一个发布包对应不可变内容；修改数据产生新版本。

发布过程先构建新版本图节点，完成全量一致性检查，导出知识快照与索引并核对内容哈希；全部产物校验通过后才切换 active_release。在线进程验证并加载新快照后向新会话提供该版本；快照生成失败时旧版本继续服务。已有 CookingSession 固定原知识版本，直至结束；紧急工艺纠正通过显式迁移或重排事件处理，不能静默修改历史计划。

### 5.6 正式发布门槛

- 100 个菜谱 ID 全部覆盖，两个同名菜保留不同身份。
- 所有必需工序都有经过审核的时长、资源和输入输出定义。
- 模型抽取字段可反查原始返回及人工修订；归档完整，本地处理重放检查通过。
- 每道菜至少有一条符合设备清单的完整执行路径。
- 所有精确加热参数、必要介入及显式批次可表达。
- 菜谱、规则、图谱投影及导出快照版本一致，引用无悬空。
- 离线关闭 Neo4j 后，在线服务仍能从有效快照冷启动，并完成初排、重排和子图读取。
- 单菜可行性和代表性多菜组合检查通过。
- 比赛分钟格式可表达的数据通过兼容性检查。
- 正式服务不存在“等人工补全后再回答”的正常请求路径。

## 6 统一菜谱与物料数据模型

### 6.1 CanonicalRecipeModel

规范化模型描述菜谱知识，不包含本轮 session_id、已完成状态或排程时间。

| 对象 | 核心字段 | 说明 |
| --- | --- | --- |
| Recipe | recipe_id、name、recipe_version、operations、ingredient_requirements | recipe_id 保留源数据身份 |
| OperationTemplate | operation_id、action、duration、material_inputs、material_outputs、resource_requirements、execution_policy | 原子工序模板 |
| Dependency | predecessor_id、successor_id、min_lag_sec、max_lag_sec、reason、evidence_refs | 明确前置关系与间隔 |
| DurationSpec | nominal_sec、execution_sec、lower_sec、upper_sec、model_id、quantity_basis、source_ref | 区分原始描述、计划值与不确定性 |
| MaterialSpec | spec_id、ingredient_id、state、shape、size、treatment、composition | 物料规格，用于兼容性判断 |
| MaterialRequirement | requirement_id、spec_id、quantity、unit、quantity_kind | 工序输入或输出的需求 |
| ResourceRequirement | resource_type、units、profile_options、occupation_policy | 人工、设备或温区需求 |
| ExecutionPolicy | interruptible、interventions、batch_policy、holding_policy | 工艺边界和介入规则 |
| Provenance | source_file、record_id、step_number、text_span、origin、review_status | 字段级证据 |
| DataVersion | schema_version、knowledge_version、rule_version | 可重现发布与解释 |

DurationSpec 中的不确定区间用于审核、敏感性实验或配置明确的稳健策略。默认求解使用确定的 execution_sec，不能让求解器自由挑选区间下限来获得更好分数。

物理动作的计划时长必须为正；只有不占资源、不表示实际加工的逻辑里程碑可为零。

### 6.2 标识设计

| 标识 | 生成方式 | 稳定性 |
| --- | --- | --- |
| recipe_id | 保留 CSV 原 ID | 跨知识版本稳定 |
| recipe_version_key | release_id 与 recipe_id 组合 | 唯一指向发布版本 |
| operation_id | 菜谱内稳定工序标识，如 op_004_cut | 数据修订显式维护映射 |
| recipe_instance_id | session_id 与菜谱实例序号 | 区分同轮不同实例 |
| task_id | recipe_instance_id 与 operation_id 组合 | 未改工艺的重排中稳定 |
| candidate_id | 候选类型、排序后成员、配置、规则版本的摘要 | 同一问题可重现 |
| material_lot_id | 实际或计划产物批次 ID | 不与食材名称混同 |
| event_id | 调用方或服务生成的唯一事件 ID | 用于幂等 |
| plan_version | 会话内递增整数 | 每次发布递增 |
| state_revision | 运行事实更新序号 | 区分状态更新与计划更新 |

外部 id 接受整数或字符串，但内部不能不加规则地将任意整数解释成 CSV 行号。优先按正式菜谱 ID 解析；赛方另有数字 ID 映射时使用显式映射表。名称用于一致性检查，不自动替代 ID。

### 6.3 物料规格与实际物料批次

本设计将《设计3.docx》中的 MaterialState 具体化为 MaterialSpec 节点：状态与食材、形状、尺寸、处理方式共同定义一种可匹配规格。状态不只保存在菜谱描述字符串中，也不把不同食材的“已清洗”误当成相同物料。

物料规格可以表达：

~~~text
ingredient_id = carrot
state = washed
shape = dice
size_mm = 5
treatment = raw
~~~

实际 MaterialLot 还必须包含：

~~~text
lot_id
spec_id
produced_by_execution_id
produced_at
quantity_produced
quantity_available
quantity_reserved
unit
storage_state
source_lot_ids
version
~~~

同一 MaterialSpec 可以对应多批不同时间产出的实际物料。两道菜需要相同规格，不代表已经共享了一批实际产物。

数量采用明确单位和定点表示。g 与 kg、ml 与 L 可按确定比例转换；缺少密度时不将 ml 自动换成 g。个、片、汤匙等单位只有存在审核过的换算规则时才转换。实际批次守恒考虑明确记录的损耗或出成率，不能把同一份余量分配两次。

### 6.4 结构示例

以下是说明字段语义的合成工序片段，不是对实际比赛菜谱或人工时长的标注结果。

~~~json
{

  "operation_id": "op_cut_carrot",
  "action": "CUT",
  "material_inputs": [
    {
      "spec_id": "carrot_washed_whole",
      "quantity": 100,
      "unit": "g",
      "quantity_kind": "EXACT"
    }
  ],
  "material_outputs": [
    {
      "spec_id": "carrot_raw_dice_5mm",
      "quantity": 100,
      "unit": "g",
      "quantity_kind": "EXACT"
    }
  ],
  "duration": {
    "nominal_sec": 120,
    "execution_sec": 120,
    "model_id": "manual_cutting_v1",
    "source_ref": "evidence_demo_manual_estimate"
  },
~~~

清洗和切配若被拆成独立工序，必须在 Recipe 的 Dependency 中保留实际先后关系。示例省略菜谱外层及依赖集合，是字段片段而非可单独发布的完整菜谱。

### 6.5 模板、需求与执行载体

共享加工会使“原菜谱逻辑工序”和“实际执行动作”不再一一对应，因此增加 ExecutionCarrier：

- LogicalTask：原菜谱中必须满足的加工需求。
- CandidateCarrier：一种可选执行方式，可以覆盖一个或多个需求。
- SelectedCarrier：本轮计划实际选择的执行方式。
- ExecutionRecord：该载体实际开始、完成及产物记录。

库存替代满足的是逻辑需求，不应伪造一次没有发生的“切配完成”。实际操作状态与需求满足方式分别保存。

## 7 知识图谱设计

### 7.1 节点与关系

| 节点 | 关键属性 | 用途 |
| --- | --- | --- |
| KnowledgeRelease | release_id、hash、status | 发布版本 |
| RecipeVersion | recipe_version_key、recipe_id、name | 菜谱版本 |
| OperationTemplate | operation_key、action、duration_ref | 工序 |
| Ingredient | ingredient_id、canonical_name | 食材概念 |
| MaterialSpec | spec_id、state、shape、size、composition | 加工前后物料规格 |
| DeviceType | device_type_id、name | 能力类型 |
| DeviceProfile | profile_id、mode、temperature、humidity | 经过审核的可执行配置 |
| ProcessingRule | rule_id、type、version、status | 共享、批次、转换等规则 |
| Evidence | evidence_id、origin、locator | 来源和审核依据 |

| 关系 | 语义 | 调度中的用途 |
| --- | --- | --- |
| HAS_RECIPE / HAS_OPERATION | 版本包含菜谱、菜谱包含工序 | 提取本次知识 |
| PRECEDES | 必须先于另一工序 | 硬时间约束 |
| CONSUMES / PRODUCES | 消耗或产出某种物料规格 | 物料流和候选生成 |
| BASED_ON | 规格属于某食材概念 | 检索，不直接产生前置约束 |
| REQUIRES_PROFILE | 工序允许的配置 | 设备选择域 |
| SUPPORTS_PROFILE | 设备支持配置 | 能力合法性 |
| GOVERNED_BY | 工序适用规则 | 共享与批次判断 |
| SUPPORTED_BY | 字段、关系或规则的证据 | 追溯和解释 |

RecipeVersion、OperationTemplate、MaterialSpec、DeviceProfile、ProcessingRule 分别建立稳定唯一键约束；常用 release_id、recipe_id、spec_id 等建立查询索引。所有请求使用参数化 Cypher。

### 7.2 依赖图与完整知识图谱

完整图谱允许存在食材关联、版本关系等形成的环。只有选定菜谱的 PRECEDES 以及由真实物料需求导出的依赖投影必须是 DAG。

DAG 校验要求访问节点数等于投影中的全部节点数；不能只取得部分拓扑结果就视为成功。最早开始下界、后续最长路径和受影响闭包在内存快照上计算。Neo4j GDS 也提供 DAG 算法，但首版不将 GDS 插件作为部署依赖。[Neo4j DAG 文档](https://neo4j.com/docs/graph-data-science/current/algorithms/dag/dag-algorithms/)

### 7.3 共享规则不固化为必然执行关系

以下四种关系分别处理：

1. 真正前置：先切配才能下锅，作为硬约束。
2. 资源竞争：两道菜使用同一灶眼，由调度决定先后。
3. 可共享加工：存在候选，不强制合并。
4. 语义关联：都含土豆，仅支持检索和说明。

ProcessingRule 可以长期存储“同规格切丁允许共同处理”的规则。当前请求中是否组成一个组，还取决于数量、就绪时间、执行状态和目标。候选列表属于请求实例，不反向覆盖图谱模板。

允许缓存规则评估结果，但缓存键必须含知识版本、规则版本、物料规格、配置以及相关输入。含时间或库存条件的判断不能用不带状态版本的全局缓存。

### 7.4 查询边界

Neo4j 查询用于离线图谱校验、知识管理和快照导出。导出时取得固定版本的菜谱、工序、输入输出规格、设备配置、规则和证据；在线请求不执行 Cypher。

离线提取查询示意：

~~~cypher
MATCH (r:RecipeVersion {release_id: $release_id})
WHERE r.recipe_id IN $recipe_ids
MATCH (r)-[:HAS_OPERATION]->(o:OperationTemplate)
OPTIONAL MATCH (o)-[p:PRECEDES]->(succ:OperationTemplate)
RETURN r.recipe_id, o, p, succ
~~~

在线 KnowledgeRepository 从已加载的 SchedulingKnowledgeSnapshot 中按 recipe_id 提取 MenuKnowledgeView。固定 100 道菜的知识可以全部加载内存，但只实例化本次菜单对应的任务。展示端的只读菜谱子图也从该快照生成，独立知识管理界面可访问 Neo4j。

<a id="s07-5"></a>
### 7.5 知识快照与索引发布

SchedulingKnowledgeSnapshot 是离线发布产物，至少包含：

| 内容 | 字段或结构 | 在线用途 |
| --- | --- | --- |
| 身份与完整性 | snapshot_id、snapshot_schema_version、knowledge_version、rule_version、source_hashes、content_hash | 拒绝版本混用和损坏文件 |
| 菜谱与工序 | recipe_id 到规范化工序的映射 | 实例化本次任务 |
| 依赖与物料流 | 前置邻接表、输入输出规格、时间间隔 | 生成调度约束 |
| 设备能力 | 设备类型、合法配置、审核后的转换规则 | 筛选配置与批次 |
| 共享规则 | 规则定义、适用范围、证据引用 | 在线计算分组合法性 |
| 静态索引 | 食材规格桶、配置桶、规则反向索引、已核实依赖信息 | 缩小候选搜索范围 |
| 来源与审核 | 字段及关系证据、审核状态、原始抽取引用 | 解释与故障定位 |
| 构建信息 | exporter_version、schema_version、build_time、validation_report_hash | 重建和兼容性核对 |

KnowledgeIndex 与快照分别保存为确定性序列化的 JSON 文件，manifest 绑定两者的内容哈希。content_hash 对规范化内容计算，不包含自身字段；exporter_version 与输入发布版本共同标识构建过程。

依赖关系和兼容规格可以离线索引。菜单成员、实际数量、库存、设备当前配置、时间窗口和正在运行的批次影响最终候选，因此不能把离线兼容桶直接当作本次已经选中的共享方案。与共享时长有关的关键路径只在其下界有效性得到证明时用于裁剪，否则只作为启发信息。

发布流程为：

1. 从审核通过的规范化数据构建指定图谱版本；知识管理中的修订必须回到规范化数据与审核记录，不能只改图谱。
2. 校验工序覆盖、关系、参数、证据和引用，导出快照与索引。
3. 用导出文件重新加载，并与规范化源数据比较 ID、工序、物料及约束集合。
4. 完成兼容性与代表案例检查，在同一发布清单中登记产物哈希。
5. 显式激活新版本；在线进程加载、校验后只向新会话提供新版本。
6. 旧会话继续引用固定版本，直到引用计数归零后才允许卸载对应内存快照。

同一会话使用同一知识快照和规则版本。程序重启时必须能取得仍活动会话所需的固定版本文件；缺少该版本的会话标记为数据不可用，不能自动替换成最新知识。

有有效发布文件时，Neo4j 关闭不影响在线冷启动、初排和重排。文件损坏、缺失或 Schema 不兼容时拒绝加载；可继续服务已经加载且仍有效的旧版本，不静默跨版本恢复。没有任何有效快照时 ready=false。

## 8 资源与时间模型

### 8.1 资源表

| 资源 | 默认实例或容量 | 调度方式 |
| --- | --- | --- |
| 人工 | 唯一 human_1，固定容量 1 | 全菜单所有主动操作区间共同互斥，不能按菜品创建独立人工资源 |
| 灶眼 | burner_1、burner_2 | 每个灶眼独立互斥；一个连续烹饪区间不任意换灶 |
| 烤箱 | oven_1，三层 | 各层预约独立互斥，同腔体只允许同温同模式及兼容配置复用；不同菜时长独立 |
| 蒸箱 | steam_oven_1，独立蒸制设备，三层 | 与烤箱采用相同的层位规则，使用蒸箱自身能力 |
| 冷藏温区 | 1 个共享温区，按比赛不设容积上限 | 可同时存放多道菜，温区设定需兼容 |
| 冷冻温区 | 1 个共享温区，按比赛不设容积上限 | 与冷藏分开建模 |
| 烟机 | 共享辅助设备 | 兼容档位下共享排烟，启停及必要切换按实际人工与状态规则安排 |
| 洗碗机、净咖一体机 | 参考配置中的设备 | 展示与场景属加分功能；实际参与执行时必须约束其程序、通道及人工占用 |

完整设备竞争策略与物理映射见第 8.6 节；本表列出默认资源，不能把设备能力名称直接当作新增物理实例。

两个灶眼状态及能力等价、且可以恢复一致实例分配时，也可以用容量为 2 的 Cumulative 表达其容量限制；首版选择显式灶眼实例，以便甘特图、提醒和运行状态保持一致。

冰箱不应采用“整个冰箱每次只能放一道菜”的互斥模型。冷藏、冷冻温区各自保持稳定配置；同一温区不同设定温度的需求不能在模型中假装各自独立成立。清单未说明的特殊解冻行为需审核映射。

### 8.2 人工占用与设备占用

人工数量是本项目硬边界：human_count 必须是整数 1，human_resource_id 固定为 human_1。启动配置、内部请求和编译结果均不得增加第二个人；发现人力需求超过单人能力且没有已审核单人路径时，报告数据问题或不可执行路径，不隐式创建额外操作者。

- 全主动任务：切配、翻炒等，全区间占用人工；翻炒同时占灶眼。
- 纯等待：腌制、静置等不占人工；需要冷藏时仍占用相应温区状态。
- 设备自动运行：拆出装入、启动、必要介入、取出等人工段，设备运行段持续占设备。
- 间歇翻拌：生成多个明确介入窗口；不能只用一个 requires_human=false 抹去介入。

介入窗口示例：加热开始后第 10 至 12 分钟内翻拌 1 分钟。窗口和操作时长来自审核数据。精确要求“第 10 分钟翻拌”时，不能私自放宽成两分钟窗口。

### 8.3 设备状态

DeviceState 保存设备实例、当前配置、温度或温度估计、状态来源、观测时间、当前批次和预约边界。另分别保存 availability_status、occupancy_status、active_execution_id、expected_recovery_at 和 release_confirmation_event_id；故障可用性和物理占用按第 16.9 节独立处理。

同一模式和目标温度不自动意味着无需预热。只有明确处于有效保持状态、连续批次能够沿用配置时，才允许使用经过审核的转换时长。设备已关机、停放时间不明或状态未知时，按已审核的冷启动策略处理。

不同配置的先后切换采用状态转换表。没有依据的温度转换，不通过线性温差公式自行估计成事实。

### 8.4 时间表达

内部使用相对于 session_start 的整数秒。每个运行事件同时保存带时区的绝对时间戳；时区默认 Asia/Shanghai。耗时测量使用单调时钟，业务时刻使用系统时间。

时间区间统一为左闭右开 [S, E)，因此 E_A = S_B 不构成资源冲突。

时间域根据菜谱时长、等待、运行状态和可行基线动态生成，允许跨越多天。不能把整个问题的上限固定为两小时。

### 8.5 比赛分钟兼容策略

**2026-09-29 更新：** 用户确认秒级调度可以用小数分钟表达。当前默认 `time_grid_sec=1`、`minute_output_mode=DECIMAL`，不改动固定工艺时长。以下整数分钟策略仅适用于显式启用的兼容配置，不再是当前默认值；官方 HH:mm 的秒和跨日语义仍须确认。

比赛输出含整数分钟设备时长，因此正式服务提供 competition_minute 配置：

1. 内部仍以秒存储，待排任务的计划网格为 60 秒。
2. 对估计型人工时长，可以在求解前向上规范到分钟，并保存 nominal_sec 与 execution_sec 的差异。
3. 原文明示的精确加热时长或最大允许时间，不允许仅为输出格式而直接向上取整。
4. 对不能表达的精确工艺，必须在离线阶段审核可接受的分钟方案，或列入协议待确认项。
5. 最小间隔向上对齐，最大允许间隔向下对齐；造成不可行时报告兼容性问题。
6. 先在可表达的时间模型上求解，再输出整数分钟；不能对已经求好的每个区间分别取整而产生重叠。
7. 展示与内部事件接口支持秒级；与比赛分钟计划混用时必须经过明确的时间映射和复核。

比赛初次请求以服务端收到请求的时间为原点。内部绝对时间保留秒，HH:mm 是不含秒和日期的展示投影，比较与校验基于完整时间，而非字符串大小。

### 8.6 全设备竞争策略与物理资源映射

设备竞争覆盖每个实际加工阶段，不能只检查一道菜的主要设备或只检查烤箱。规则分为比赛明确事实与项目建模策略：赛方答复明确灶眼 2 个、其他设备不考虑容量、同温同模式允许共蒸共烤；“不同加工时长的所有设备任务都必须串行”不是已取得的比赛规则。具体来源见[项目资料阅读纪要](../../../项目资料阅读纪要.md)。

2026-10-08用户确认蒸箱、烤箱各三层，允许按各菜时长分层进出，并要求不同层只有相同温度才能复用。新分层版本按完整设备预约占一层，同一层互斥，跨层同时在场最多三份，温度必须明确一致，模式、湿度等配置也须兼容。放入、介入和取出保持原工序、时长和唯一人工约束；配置中途变化的预约保留整腔独占。旧版本的STRICT_TOGETHER仅接受有效加热时长一致的合法共同批次，新策略关闭该可选合批而使用独立层位，不把不同时长统一加热。原菜谱固定程序和历史版本事实保留。

| 设备或资源 | 竞争单位与策略 | 可以并行或共用的条件 | 必须错开或拒绝的情况 |
| --- | --- | --- | --- |
| 灶具 | burner_1、burner_2 分别为独占资源 | 不同灶眼可同时运行各自合法火力和不同时长的任务；人工需求仍受 human_1 限制 | 同一灶眼两个独立加工区间重叠；两个全主动翻炒争用唯一人工 |
| 烤箱 | 实际烤制腔体三层；每层完整预约互斥 | 不同层温度相同且模式、必要湿度等配置兼容，可按各菜时长独立进出 | 同层重叠；超过三层；温度或配置冲突；独占预约未释放 |
| 蒸箱 | 独立实际蒸制腔体三层；每层完整预约互斥 | 与烤箱采用相同的层位判定，参数使用蒸箱自己的能力范围 | 同层重叠；超过三层；不同蒸制模式或温度及其他配置不兼容 |
| 蒸烤一体机或设备别名 | 依审核映射关联同一 physical_resource_id | 映射为独立物理设备时才可分别预约 | 把同一腔体的蒸与烤能力当成两台可并行设备 |
| 冰箱冷藏温区 | 共享状态资源，不设菜品数量上限 | 重叠期间具有共同合法温度；不同冷藏时长可重叠 | 同一温区同时要求不兼容的设定温度；未知状态被当作已达到目标温度 |
| 冰箱冷冻温区 | 独立的共享温区，按审核配置与冷藏区区分 | 各任务温度要求相容，不要求冷冻时长相同 | 为每道菜虚构一个独立冷冻温区；占用期间随意改变温区状态 |
| 冰箱解冻功能 | 按审核规则映射其实际占用部件和模式 | 只有明确能力与占用关系时才安排 | 不依据资料就假设独立解冻设备，或反过来一律锁住整个冰箱 |
| 烟机 | 共享辅助状态资源 | 多个灶眼可共享排烟；同时存在的需求能由同一个合法档位满足 | 同一时刻输出互相冲突的档位；无依据认定强档一定满足精确弱档要求 |
| 洗碗机 | 同一洗涤腔体的程序批次 | 启用该加分功能且规则明确时，同程序兼容对象可共批；不私增容量上限 | 同一腔体同时执行不同程序；忽略装卸人工或使用未知程序时长 |
| 净咖一体机 | 按审核映射的实际出水/制作通道 | 明确独立的物理通道才可并行，或者存在审核过的共同加工规则 | 在同一通道同时输出不兼容温度或制作程序；凭名称创建不存在的独立出口 |

蒸箱与烤箱为两台独立设备、各三层是2026-10-08用户确认的项目设备事实，不是对所有“蒸烤一体机”原文的自动解释。设备清单中的能力名称、API展示名称与物理实例身份分开：层位互斥和同腔配置约束按实际物理资源或部件归并，而不是按字符串名称各建一台设备。

不考虑容量意味着不额外限制同批食物或温区存放数量；它不会凭空增加物理设备或独立通道，也不会允许同一腔体同时维持两个相冲突的工作状态。洗碗机和净咖一体机仍为加分功能；核心交付不因此新增专用展示功能，但已选菜谱一旦实际引用某设备，其必要占用就必须进入模型。缺少合法参数、占用规则或审核路径时产生数据问题，不能省略设备阶段或赋零时长。

#### 8.6.1 统一资源契约

DeviceInstance 与 ResourceUse 至少表达：

~~~text
device_instance_id / physical_resource_id / component_id
capability_refs / profile_constraints / rule_version / evidence_refs
conflict_policy = UNARY | BATCH_EXCLUSIVE | STATE_COMPATIBLE | SHARED_AUXILIARY
carrier_id / phase_id / presence_condition
occupancy_start / occupancy_end
human_interventions
availability_status / occupancy_status
~~~

- UNARY：同一资源的独立预约互斥；两灶眼各一份日历。
- BATCH_EXCLUSIVE：批次之间互斥，合法成员共享同一批次外层预约；不能把内部每道菜重新独占整个设备。
- STATE_COMPATIBLE：存放任务可重叠，但每一时段的共享配置必须同时满足所有在场任务；无共同配置时选择错开、合法其他路径或报告不可行。
- SHARED_AUXILIARY：共享运行区间可取需求并集，但档位等控制状态必须可共同满足；启停与切换所需人工按审核阶段计入 human_1。

不同层的实现共用同一份资源事实和策略定义，Validator 使用独立扫描验证。设备映射、模式、时间、实际占用与状态版本进入问题哈希，不能复用与当前物理资源不同的缓存结果。

#### 8.6.2 设备竞争如何影响执行顺序

对争用同一独占资源或同一腔体的两个不同批次 a、b，必须满足：

~~~text
E_a <= S_b  或  E_b <= S_a
~~~

先后由 Greedy 构造及 CP-SAT 限时优化决定，并同时考虑各自前置准备、出菜差、预热切换和唯一人工的可用时段。资源竞争是需要选择的先后关系，Compiler 不能随意把菜谱 ID 顺序写成永久 PRECEDES。

例如 A、B 均为同模式 180℃、20 分钟，C 为同模式 180℃、10 分钟：A/B 在其他条件合法时可以形成一个批次，C 独立成批。求解器比较“A/B 后 C”“C 后 A/B”及不合并 A/B 等方案；等待 B 准备的代价可能使合批更差。时长相同不是强制合批指令。

这条顺序规则只约束实际争用的资源。C 等烤箱期间可以在合法条件下切配其他菜、用另一台设备加工或执行被动等待。重排时已完成事实、运行中预约和未确认释放的故障占用优先固定，再为未执行阶段重新选择顺序。

#### 8.6.3 全设备验收矩阵

至少验证：两灶眼并行与单灶重叠拒绝；两灶全主动任务争抢单人；新分层版本同温同配置的不同时长跨层进出、同层和第四层拒绝；旧版本同时长合法共批与不同时长分批；同时间不同模式或温度拒绝；同一物理蒸烤腔体的别名竞争；不同时长但同温的冷藏合法重叠；同温区不兼容温度拒绝；烟机共享与控制状态冲突；启用的洗涤/出水通道的程序竞争；故障和重排后的设备占用保留。

每个成功计划必须通过实际资源零冲突检查；另外用已知可行见证验证模型保留合法共享和并行的能力。具体计划是否选择合批或并行仍由依赖和优化目标决定，不能要求所有可共享工序必定同时运行。规则来源、参数有效性、竞争策略、分配和资源释放均可追溯；不能仅以总时间更短作为设备竞争正确的证据。

### 9.2 编译步骤

1. 检查菜谱 ID、版本及数据完整性，构建实例。
2. 将已完成物料和运行中工序映射到实例，区分实际事实和未来计划。
3. 展开复合工序、必要人工段、固定菜内批次。
4. 建立物料依赖和 PRECEDES 投影，检查 DAG。
5. 筛选设备配置，消除明显不合法的备选。
6. 为每个未满足需求生成单独执行方案。
7. 依据规则生成共享前处理、热加工批次和库存替代候选。
8. 校验候选全组兼容性及与已有执行事实的关系。
9. 生成资源、数量、时间和冻结约束所需的领域数据。
10. 计算适用于全部保留候选的安全边界、启发优先级和基线。
11. 输出候选统计、数据版本与规则证据；生成领域约束目录、规模预估、剪枝记录和时长策略引用。

### 9.3 候选规模控制

候选只针对本次未完成工序生成。单独候选始终保留；运行中和已完成载体不能重新合并。

初始策略为先按加工规格或设备配置分桶，再生成双成员候选以及整组兼容的较大候选。对规模较大的桶，采用确定性排序截取候选，每个需求最多保留 12 个非单独候选，单问题最多 256 个非单独候选，作为实验起点。

截断不能删除原菜谱必须执行的固定批次或硬依赖，也不能把最多 12 或 256 误写成食品加工限制。日志明确记录是否截断。求解器的最优性结论只针对保留候选的模型。

当所有成员不具备共同配置交集时，不能根据两两相连关系直接合为整组。工序之间存在祖先后继关系时，不生成要求它们同步执行的共享候选；多组选择形成的潜在新环，还需要时间约束和最终校验兜住。

### 9.4 图谱预处理的边界

有效的预处理包括 DAG 检查、无关知识裁剪、设备域过滤、合并规则筛选，以及对全部候选有效的时间下界。

采用固定工序时长计算的关键路径，不能直接作为含可变共享时长模型的强下界。必须使用适用于所有候选的最小合法时长，或仅用于 Greedy 排序。

资源争用关系不强制转成先后边；可共享关系不强制转成合并；当前就绪较晚不等于永远不兼容。预处理删除方案的理由必须可解释并可复测。


<a id="s09-5"></a>
### 9.5 候选支配剪枝与模型规模控制

候选去重、支配剪枝和预算截断分开记录。去重删除语义等价的重复表达；支配剪枝必须证明删除不损失所需的合法方案和目标表现；预算截断只是限制搜索范围。

定义候选 a 支配 b：在所有需要保留的上下文中，任何使用 b 的完整可行计划都能通过明确的替换映射改为使用 a，仍满足全部硬约束，且当前目标向量不变差。只有覆盖相同需求、时长更短或资源数量更少，不能单独构成这一证明。

检查项包括：

| 维度 | 必须证明的内容 |
| --- | --- |
| 覆盖与物料 | 覆盖需求相同；输出规格、数量、出成率、分配与可用时刻兼容 |
| 时间端口 | 外部可见的开始、结束、产物释放与介入边界可以合法映射 |
| 依赖窗口 | 最小等待、最大间隔、固定时刻和同步关系仍成立 |
| 设备配置 | 能力、温度、模式、湿度和前后转换不变差 |
| 资源阶段 | 人工、设备的实际占用可替换，不增加与其他任务的冲突 |
| 运行事实 | 不修改已发生操作、已经承诺的分配或正在运行的载体 |
| 目标 | 完成差、总耗时、人工忙碌和重排扰动均符合替换条件 |
| 规则范围 | 证明适用于本次知识、规则、策略和相关状态版本 |

一个反例：某工序必须在第 0 分钟开始，其后继又必须在第 10 分钟开始，且要求前后无等待。10 分钟的候选可行，5 分钟候选并不能直接替代它。因此不能按“同覆盖、耗时更短”无条件删除较长候选。

首版默认执行完全等价候选去重；非等价支配剪枝只对经过独立验证的白名单替换规则开放，初始配置关闭通用非等价支配删除。候选不足以证明可替代时，保留它或降低 Greedy 排序优先级。

每次删除产生 PruningRecord：

~~~text
removed_candidate_id
replacement_candidate_id
pruning_kind = EQUIVALENT | CERTIFIED_DOMINANCE | BUDGET_TRUNCATION
proof_rule_id
assumptions
preserved_time_and_material_ports
knowledge_version / rule_version / policy_version
state_dependency_hash
~~~

BUDGET_TRUNCATION 的 replacement_candidate_id 可以为空，并明确记录“可能损失最优解”。单独执行候选与原菜谱强制批次不因支配优化或预算截断被删除；等价单独候选至少保留一个规范代表。

### 9.6 模型规模观测与降级

Compiler 先估计潜在阶段和顺序边数量，CP-SAT 建模后再统计实际模型。两套统计均保存，避免只看候选数。

建模前的 ModelSizeEstimate 与建模后的 ModelSizeReport 分开保存。ModelSizeReport 包含 logical_tasks、selected_path_alternatives、total_variables、boolean_variables、intervals、optional_intervals、total_constraints、constraints_by_type、sequence_arcs、fixed_executions、serialized_proto_bytes、build_time_ms 和 pruning_counts。预估字节数使用 estimated_proto_bytes，不能把它当作实际序列化大小。

初始软门槛为总变量 6000、布尔变量 4000、可选区间 1500、约束 20000、顺序边 8000。它们是实验起点，不是求解速度保证；若代表性数据表明门槛不合理，通过 policy_version 调整。

预计或实际超过门槛时，按顺序执行：

1. 去重和已经证明安全的剪枝。
2. 按第 9.3 节策略减少非单独优化候选，并记录截断。
3. 不启用额外的精确人工忙碌顺序模型。
4. 重新估计或构建模型，压缩后续优化阶段的预算。
5. 在截止时间内保留已验证的完整方案；仍无法建立合适模型且没有合法方案时，报告明确失败。

每个建模组件完成后检查单调时钟预算。不能把巨大模型完全构造结束后才检查是否超时。不得通过删除必要依赖、物料守恒、冻结事实或资源约束降低模型规模。

剪枝正确性通过小规模完整枚举比较，以及第 21.8 节的替换属性测试验证。统计“剪枝前后解集或最优值是否保持”与“计算时间是否改善”两个不同结果。

## 10 跨菜共享前处理

### 10.1 共享含义

共享前处理是一次真实操作满足多个菜品的加工需求，并产生可以追溯和分配的物料。共享机会不是跨菜硬依赖；选中共同处理之后，才形成“共同产物完成后分别进入后续工序”的执行关系。

首批规则覆盖经过审核的同规格清洗、切配。腌制、混合、焯水分别定义输入状态、配方和时间模型，不能套用“相同食材即可合并”。

### 10.2 候选合法性

一个共享前处理候选必须满足：

1. 输入物料和加工前状态兼容。
2. 加工动作、目标规格和必须一致的参数兼容。
3. 总数量可计算，或存在经过审核的定性数量处理规则。
4. 加工时长模型适用于该数量范围。
5. 成员之间不存在禁止同步的前置关系。
6. 合并产物可以按数量和规格分配给各需求。
7. 候选涉及的工序均未开始执行。
8. 不覆盖仍被其他分支需要、却没有替代产出的中间工序。
9. 时间窗口和物料可用时刻能够在求解中表达。

“B 较晚就绪”本身不是工艺不兼容；可保留该候选，由调度判断等待成本。只有经过证明不可能满足硬窗口时才提前排除。

### 10.3 精确覆盖建模

设 G 为候选集合，covers(g) 为候选 g 满足的逻辑需求集合，y_g 为是否选择：

~~~text
对每个尚未满足的逻辑需求 i：
sum(y_g for g if i in covers(g)) = 1
~~~

合成示例：菜 A 需要 100g 胡萝卜丁，单独切配估计 2 分钟；菜 B 需要 200g，单独估计 3 分钟；共同处理 300g 的审核估计为 4 分钟。

~~~text
g_A  covers {A_cut}
g_B  covers {B_cut}
g_AB covers {A_cut, B_cut}

y_A + y_AB = 1
y_B + y_AB = 1
~~~

合法选择是 g_A 与 g_B，或 g_AB。没有选中的候选不占资源、不产出物料、不生成执行通知。

共享时长采用：

~~~text
duration(group) =
    preparation_overhead
  + approved_processing_time(total_quantity, operation_spec)
  + allocation_and_cleanup_time
~~~

时长模型可以是分段函数或数量档位表。它不普遍等于单独时间之和，也不普遍等于最大单独时间。

### 10.4 时间映射与资源占用

对整批完成后才释放产物的共享切配：

~~~text
y_g = 1  =>  S_i = S_g, E_i = E_g   对所有被覆盖需求 i
~~~

逻辑需求 i 原来的单独时长只在单独候选中生效。共享候选被选中时，不能同时强制 E_i - S_i 等于原来的单独时长。

原前置关系仍约束 S_i，因此共享操作等待所有必需输入；原后继通过 E_i 等待对应产物。共享载体中的实际人工区间计入资源约束，被替代原操作不重复占用资源。

若允许边切边释放部分产物，需要引入多个释放里程碑和数量分段。首版不自动推断这种行为。

### 10.5 物料分配

对于单一输入、无损耗的示例：

~~~text
shared_output = 300g
allocation_to_A = 100g
allocation_to_B = 200g
sum(allocations) <= shared_output
~~~

实际使用按已审核出成率或损耗计算。已分配、已消费和剩余数量分别记录；计划分配是预约，实际消费必须对应运行事件。

共享不得产生虚假的先后：A 的原料分配和 B 的原料分配完成后，两道菜的后续工序仍可并行。

### 10.6 Greedy 与 CP-SAT 的分工

Greedy 比较分别处理和共同处理的预计结果，包括节省人工、等待输入的代价、后续关键链和设备窗口。CP-SAT 同时决定 y_g、开始时间和资源，不固定 Greedy 的共享选择。

共享候选采用可选区间并以布尔变量控制存在性，属于 CP-SAT 可表达的方案选择结构。[OR-Tools 可选执行方案示例](https://github.com/google/or-tools/blob/stable/examples/python/flexible_job_shop_sat.py)

## 11 同温同模式批量加工

### 11.1 两层时间结构

共同加热分为设备批次和成员加工区间：

~~~text
设备预约：
[必要状态转换／预热 | 装入 | 加热与允许的介入 | 最后取出]

成员：
  菜 A 的有效加工区间
  菜 B 的有效加工区间
~~~

外层设备批次在同一蒸箱或烤箱上互斥；批次内部成员按规则重叠。单独加热也表示为单成员批次，统一资源模型。

### 11.2 批次兼容条件

批次必须存在共同设备实例及共同允许配置，配置包含模式、温度和必要湿度。不同模式即使温度相同，也不能未经审核直接合并。

若某工序允许多个配置，整批所有成员的允许配置集合必须有共同交集。不能将兼容关系的连通分量直接视为合法整批。

菜谱要求的明确分批和中途操作继续保留。比赛“不考虑其他设备容量”的规则，意味着不添加未经要求的托盘容量上限，不意味着可以删除已给出的加工程序。

### 11.3 三种批次执行策略

| 策略 | 时间关系 | 适用条件 |
| --- | --- | --- |
| STRICT_TOGETHER | 同时开始、同时结束 | 时长相同，或存在审核确认的共同允许时长 |
| COMMON_START | 同时开始、分别结束 | 允许中途取出，人工及温度影响明确 |
| COMMON_FINISH | 分别开始、共同结束 | 允许中途加入，人工及温度恢复影响明确 |

合成示例：普通蒸 100℃，A 加热 20 分钟，B 加热 8 分钟。

- COMMON_START：A、B 加热起点相同，B 在第 8 分钟结束，A 在第 20 分钟结束。
- COMMON_FINISH：A 从第 0 分钟加热，B 从第 12 分钟加热，两者第 20 分钟结束。

以上是有效加工时间示意，不能直接当作包含预热、装卸的完整排程。

对应关系：

~~~text
COMMON_START:
S_i = S_heat_batch
E_i = S_i + d_i
E_heat_batch = max(E_i)

COMMON_FINISH:
E_i = F_heat_batch
S_i = F_heat_batch - d_i
~~~

d_i 是该菜品自己的经过审核的加工时长，不统一改成整批最长时长。

本项目通用跨菜蒸烤只启用 STRICT_TOGETHER，成员最终采用的有效加热时长必须相同。COMMON_START、COMMON_FINISH 在这里用于解释分时加工的时间关系，不作为当前实现可自行开放的自由跨菜合批能力。原菜谱明确的分时放入和翻拌仍编译为固定复合批次或分段工序，不能因关闭通用跨菜优化而删除。

### 11.4 装卸与热暴露边界

成员的有效加热开始、结束必须与实际装卸事件关联。仅把“加热结束”写在第 8 分钟，而让食物继续在运行设备内等待人工到第 12 分钟取出，不是合法实现。

ProcessingRule 规定装入或取出动作中何时视为进入、退出有效加热环境；实际热暴露时间必须满足允许窗口。若工艺无法精细确定，采用审核过的保守装卸模型，并在数据中记录假设。

同时结束的多道菜若需一个人逐一取出，应计入实际人工次序和时间，不能假定多个独立动作瞬间完成。可以使用审核过的共同托盘取出动作，但要保留该共享操作的真实时长。

共同批次载体覆盖被替代的加热、装入、取出需求；其内部人工段只计一次。不能保留原来的装卸任务，再额外添加批次装卸造成重复。

### 11.5 预热与批次切换

每个选中批次包含自己的必要状态转换段。后一个批次的转换时间取决于前一个实际批次及设备保持状态。

若 b 是 c 的直接前驱：

~~~text
S_c >= E_b
transition_duration_c = transition(profile_b, profile_c, state_policy)
heat_ready_c = S_c + transition_duration_c
~~~

转换段包含在 c 的外层设备预约内，不再在 S_c >= E_b 后额外重复加一次同样的转换时间。第一个批次根据初始 DeviceState 计算转换。

直接前驱可以通过带虚拟起终点的批次序列变量表达。未选中批次不进入序列。OR-Tools 提供使用 circuit 约束表达顺序相关转换的示例；本项目仍需验证具体设备转换规则。[转换建模示例](https://github.com/google/or-tools/blob/stable/examples/contrib/scheduling_with_transitions_sat.py)

### 11.6 决策原则

共同加工不必然更快。等待另一道菜备料、增加装卸操作、延误关键菜品，都可能抵消预热或设备时间收益。每个需求保留单独批次候选，求解器联合选择批次成员、配置、时间和人工安排。

## 12 CP-SAT 约束模型

### 12.1 符号与变量

| 符号 | 含义 |
| --- | --- |
| I | 本次尚未满足的逻辑需求集合 |
| G | 可选执行载体集合，包含单独、共享与批次 |
| y_g | 是否选择载体 g |
| S_i、E_i | 逻辑工序的加工边界或产物释放边界 |
| S_g、E_g | 载体外层时间边界 |
| I_gp | 载体内部第 p 个实际资源阶段 |
| x_gr | 载体是否选择资源或配置 r |
| C_k | 菜品 k 的必要末端任务完成时刻 |
| Cmax | 全部菜品完成的最晚时刻 |
| H | 当前问题时间域上界 |
| a_bc | 批次 b 是否直接先于批次 c |

时间变量为整数秒。固定的比赛分钟计划满足 S = 60u，E = 60v，其中 u、v 为整数；实际历史时刻单独保留，不能反向改写。

OR-Tools 的 interval、optional interval、NoOverlap、Cumulative 和条件约束为这些模型提供基础构件；业务含义由编译器和本节规则确定。[CP-SAT API](https://or-tools.github.io/docs/pdoc/ortools/sat/python/cp_model)

### 12.2 覆盖与可选存在性

对每个未满足需求，所有覆盖它的候选选择之和等于 1。

如果载体还有设备备选：

~~~text
sum(x_gr for allowed r) = y_g
~~~

选中载体恰好选一个合法执行配置；未选中载体的资源备选全部不激活。内部阶段的存在性跟随载体，必要时再结合具体配置选择。

### 12.3 工序依赖与时长

对硬前置 i -> j：

~~~text
S_j >= E_i + min_lag_ij
~~~

有经过审核的最大间隔时：

~~~text
S_j <= E_i + max_lag_ij
~~~

单独候选激活时满足 E_i = S_i + d_i。共享和批次候选激活时，采用其对应的时间映射；不能同时施加矛盾的单独时长等式。

成菜完成时刻 C_k 定义为该菜所有必要终端产物及收尾动作的最晚完成时间。不能以“最长设备加热结束”代替还需要热油、浇汁或取出的菜品完成时间。

### 12.4 资源约束

- 对每个灶眼的选中占用区间施加 NoOverlap。
- 把全菜单所有被选中的主动人工区间放入唯一 human_1 的同一个 NoOverlap，包括跨菜切配、翻炒、蒸烤装卸、中途介入及运行中冻结人工段；不得为每道菜分别创建互不约束的人工资源。
- 对烤箱、蒸箱实际物理腔体的外层批次施加 NoOverlap；若蒸烤是同一腔体的不同能力，须归并到同一资源。占用覆盖实际预热、装入、加工、必要取出及释放边界。
- 批次内部合法共同加热区间不重复放入同一设备的 NoOverlap。
- 同时需要人工和灶眼的同一个操作，其两个占用区间必须有一致的时间边界。
- 运行中区间形成固定或条件明确的剩余预约，未来工序不得与其真实占用及配置冲突；允许共享的温区仍按状态兼容规则处理。
- 冷藏和冷冻按温区配置兼容检查；不使用菜品数量为 1 的互斥。
- 烟机与实际使用的洗碗机、净咖一体机等按第 8.6 节资源策略建模；独占或批次互斥、共享状态相容分别实现，不因设备属于加分功能而遗漏实际加工占用。
- 对允许重叠的共享资源，配置约束作用于同一时段的全部实际在场任务；可选任务未选中时不强加其状态要求，配置切换也必须有可行时间及工艺依据。
- 容量资源以审核确认的物理限制建模；本比赛不额外增加其他设备的食品容量上限，不将设备目录中的种类数当作容量或并行通道数。

### 12.5 时间域与状态约束

所有未来实体动作的开始时刻不早于 now_offset_sec，并满足时间网格及资源可用时刻。

已完成操作保存实际时间、产物和所属载体，不再作为可改变的决策。运行中非中断操作固定已发生部分和资源；剩余计划来自明确的剩余时长或执行规则。

已确认的 deadline 才构成硬上限。未给定的出菜时刻不能凭空加入为硬约束。候选截断、时间域裁剪和资源禁用均要在问题报告中说明。

### 12.6 物料约束

对于数量明确、单位一致的物料批次 l：

~~~text
sum(reserved_or_consumed_quantity_for_selected_demands)
    <= usable_quantity_of_l
~~~

每个被选择的产物分配必须匹配 MaterialSpec，并且在被消费时已经产生。一个需求若由多个批次供应，需显式记录分配，不把一个布尔“有库存”当作无限供应。

计划中的共享产物只有在载体选择且执行完成后才能成为实际库存。运行中产物不提前记为可用。

### 12.7 对称性与规模

两个等价灶眼可以在保证不删去合法类别的前提下增加资源编号对称性规则。规则必须不改变设备状态不对称时的可行域。

候选相同成员、相同配置、相同时间模型时去重。添加关键路径下界前验证其适用于所有备选，避免错误剪枝。

H 可由已经验证的完整可行计划及目标允许的额外时间构造；尚无可行计划时使用覆盖全部必要时长与转换的保守界。带最大间隔或复杂库存的情况不能宣称“简单串行必然可行”。

### 12.8 独立校验接口

求解器输出 ScheduleCandidate，至少包含选中载体、成员映射、阶段资源占用、物料分配、菜品完成时刻和原始求解状态。校验器根据领域事实重新计算指标与合法性，不直接信任输出中的 Cmax 或“零冲突”标志。

## 13 多目标优化与指标

2026-10-07本轮用户授权修订：新默认 `p6-cook-continuous-v1` 使用版本化出锅锚点，目标为 `max(0, CookingFinishSpread - 300)`、`MaxHumanBusyBlock`、`Makespan`，移除累计人工优化；旧版本策略保留。工序段粒度、库存时间缺口及使用方法见[P5运行说明](P5运行与接口说明.md)。下文旧策略是历史基线，不能将其总人工目标应用到新默认。

`cooking_finish_spread_sec` 与 `recipe_cooking_finishes` 存在 ScheduleMetrics 中；原 `completion_spread_sec`、`recipe_completions` 继续表示含冷却/装盘的完整流程。新目标保留第13.2节的硬约束T_parallel<=T_serial，不为了插入休息发布负timeSave；该上限可能限制纯主动单菜的连续人工改善。新策略先用较轻模型搜索出锅达标候选，失败后在剩余预算中优化真实超标量，再用精确人工顺序模型改善连续操作。合法完整计划的人工顺序仅作为hint，不限制后续交换顺序。取得达标候选后沿用5%且不超过120秒的额外总流程上限；所有阶段共享原预算。

### 13.1 指标定义

| 指标 | 定义 |
| --- | --- |
| Makespan | 从本轮时间原点到全部必要菜品完成的跨度 |
| RemainingMakespan | 重排事件时刻到剩余全部任务完成的跨度 |
| FinishSpread | max(C_k) - min(C_k) |
| TotalHumanWork | 所有实际选中人工区间的时长总和 |
| MaxHumanBusyBlock | 按项目休息间隔阈值划分后，最长忙碌块的跨度 |
| ScheduleDisruption | 原有未开始需求的开始时刻变化及资源、批次改变 |
| ResourceUtilization | 选中实际占用区间的并集长度除以明确的统计窗口 |
| SolverTime | CP-SAT 计算阶段耗时 |
| EndToEndLatency | 接收请求至输出完成的服务内耗时，另记录客户端观测耗时 |

重排同时报告包含已完成菜品的全桌 FinishSpread 和尚未完成菜品的剩余 FinishSpread。求解时已完成菜品时刻是固定事实，不能通过删除它们获得虚假的全桌改善。

### 13.2 串行参考与节省时间

默认串行参考按请求顺序逐道完成菜品，同一道菜内部保留其合法工艺和必要并行，不进行跨菜共享；使用相同数据、资源能力、初始状态及设备转换规则。

~~~text
T_serial = 该逐道执行参考计划的实际跨度
T_parallel = 本次发布并行计划的实际跨度
timeSave = T_serial - T_parallel
time_ratio = T_parallel / T_serial
saving_ratio = (T_serial - T_parallel) / T_serial
~~~

三个指标分别保存。比赛 overview.timeSave 输出节省分钟数；聊天中并行/串行比例另行记录，不能混用。

串行参考必须可行。简单将所有原编号时长相加，可能重复计算共享、漏掉预热，或破坏最大间隔，因此不能作为无条件正确基线。

初始排程存在经验证串行参考时，发布方案要求 T_parallel <= T_serial，以满足 timeSave 非负。不能仅通过 max(0, difference) 掩盖计算错误。基线、并行方案必须使用同一时间量化规则。重排串行参考的起点和历史归属见第 18、23 节。

可选 `FEASIBILITY_FIRST` 重排也必须在提前发布前取得同一 `SchedulingProblem` 的合法串行参考。完整候选本身已满足剩余工序的逐道顺序时，可复用本轮独立校验；否则在共享截止时间和 Solver 总额度内计算并校验参考。将参考纳入完整候选比较，保证发布方案的真实总用时不大于参考，省略人工、稳定性及出菜差的后续可选优化。没有合法参考时返回明确失败，不用旧状态参考补足字段。合法空菜单以其已验证空计划作为参考。用户于 2026-10-06 授权新版本可选策略将重排总预算放宽至 3000ms；原 2400ms 策略保留，初排预算和资源能力不变。

### 13.3 初始优化策略

2026-10-07 用户确认五分钟出菜优先，并明确初排五秒内优秀、最多七秒；随后授权“现在可以切换了”启用已复测的五秒重排策略。当前在线默认另版本为 `p6-quality-v2`：初排共享总预算 7000ms（构造300/求解5000/发布预留600ms），重排共享总预算5000ms（构造400/求解2800/发布预留1400ms）；目标顺序为超出300秒的出菜差、总人工、总流程。未增加人工、设备、并发或搜索线程。旧策略和已有会话绑定保留；以下阶段描述作为原版本基线，不能据此把当前预算退回旧值。实际验证见 [提醒与排程质量修复验收](2026-10-07-提醒与排程质量修复验收.md)，阶段状态仍登记在 task.md。

采用有限时间的分阶段优化，并保留每阶段的最佳已验证可行解。

1. **阶段 A：缩短总耗时。** 求得当前最好可行值 C_ref；未证明最优时不称为理论最优。
2. **确定总耗时容忍范围。** 初始配置：
   delta = min(120 秒, 向上对齐到时间网格的 5% × C_ref)。
   C_cap = min(T_serial, C_ref + delta)，无有效串行参考时不使用该最小项。
3. **阶段 B：改善出菜达标程度。** 在 Cmax <= C_cap 内，最小化 E_spread = max(0, FinishSpread - 240 秒)。
4. **阶段 C：缩短达标水平下的总耗时。** 保持 E_spread 不劣于阶段 B 已取得的可行值，再最小化 Cmax。
5. **阶段 D1：减少累计人工用时（P4 待实现）。** 保持上层结果，最小化实际选中人工段时长总和；共享只计一次、纯等待不计、已执行部分固定，全程与剩余分别报告。
6. **阶段 D2：改善连续人工忙碌。** 保持上层和 D1 已达到的指标界，按剩余预算优化最长人工忙碌块。
7. **阶段 D3：重排稳定性。** 保持上层结果，再减少未开始任务的扰动；各阶段超时和未执行分别报告。

该策略允许为接近同时完成付出有上限的总时间代价。4 分钟差值与 0 分钟差值都在项目目标区间时，不优先为归零而显著延长做饭时间。

最终候选比较在同一个 C_cap 和数据版本下，按 E_spread、Cmax、TotalHumanWork、MaxHumanBusyBlock、ScheduleDisruption 的顺序进行（TotalHumanWork 是 P4 待实现增补，当前代码尚不按它比较）。相同指标用稳定 ID 排序打破平局。阶段 A 是建立合理耗时范围的过程，不等同于最终全局词典序目标。

每个阶段受总预算约束。前一阶段只是找到可行解时，后续锁定的是“已达到的界”，不是已证明最优值，实验报告必须区分。

### 13.4 连续人工忙碌

将选中的人工区间按时间排序。如果相邻人工操作间隔小于 rest_gap_sec，则属于同一忙碌块；否则开启新块。初始 rest_gap_sec = 60 秒。

忙碌块跨度包含其中不足阈值的短间隙；另行记录块内主动工作总时长，便于适配后续官方定义。重排时携入当前正在持续的人工忙碌块起点和必要历史区间，不能把事件时刻当作一次并不存在的休息；全程指标与剩余计划指标分别报告。

小规模实例的 CP-SAT 人工优化可以引入选中人工段的直接后继变量：

~~~text
若 b 直接接在 a 后，且 S_b - E_a < rest_gap：
    block_start_b = block_start_a
否则：
    block_start_b = S_b

B_max >= E_b - block_start_b
~~~

直接后继形成按时间排序的有效链；不选中的人工段不参与。边界比较用整数网格精确表达。

该模型可能增加二次规模的顺序变量。潜在人工段数超过初始阈值 120 或剩余预算不足时，跳过人工目标的精确求解阶段，保留通过独立扫描准确计算的人工指标，并可采用保持上层指标的有限局部修复。报告 human_objective_optimized=false，不能声称已优化到最优。

### 13.5 重排扰动

对原计划中仍未开始且身份稳定的逻辑需求计算：

~~~text
D_time = sum(abs(S_i_new - S_i_old))
D_resource = changed_resource_count
D_group = changed_execution_group_count
~~~

新增需求不纳入旧计划位移惩罚。完成和运行中的不可变部分作为硬约束，不通过加大惩罚替代。

批次改变时，使用成员 task_id 的映射比较，而不是因为 candidate_id 变化就丢失可比性。扰动指标记录成向量，默认晚于完成时间和人工指标处理。


<a id="s13-6"></a>
### 13.6 时长不确定性与稳健排程策略

首版求解器仍采用确定性时间模型。时长不确定性由有版本的时长估计策略和执行反馈处理，不要求首版实现随机规划，也不允许求解器在一个估计区间内自由挑选最短时长。

先区分三类时间：

| 类别 | 典型内容 | 处理边界 |
| --- | --- | --- |
| 必须遵守的工艺时间 | 审核确认的有效加热时长、最短腌制时间、最大工序间隔 | 作为工艺约束保留；不能为提高鲁棒性随意延长或缩短 |
| 待估计的操作时间 | 切配、装卸、人工搬运、达到目标温度前的预热 | 使用审核估计或观测统计；保留适用条件与不确定性来源 |
| 实际执行时间 | 真实开始、完成、暂停和设备反馈 | 进入执行记录与重排状态；不被预测值覆盖 |

每条 DurationEstimate 至少记录 operation_template_id、phase_type、quantity_range、device_profile、估计值、估计来源、适用条件、sample_count、数据版本及审核信息。只有存在适用的观测样本时，才记录经验 P50/P90；缺少样本时使用“审核估计范围”或“合成实验范围”，不能将主观上下界写成统计分位数。

样本必须按任务、数量和设备条件判断可比性；人工操作还应记录操作人员或速度分组。初始以每个可比组 30 条样本作为是否尝试计算经验分位数的工程门槛，这不是 P90 稳定性或概率覆盖率的保证。稀疏组采用明确标注的审核估计，跨组借用参数需记录映射规则，不静默混合。

提供两个可复现实验策略：

- **NOMINAL**：使用当前发布版本的名义估计，作为首版默认值。
- **BUFFERED**：仅对允许估计的阶段采用经过审核的偏保守估计，或者在允许等待的位置加入显式缓冲。一个阶段选择一种表示，避免“P90 时长加同一份缓冲”重复计入。

偏保守人工时长属于该场景的计划工作时间；单独的缓冲区间标记 BUFFER，不当作已经发生的人工劳动。缓冲是否保留设备或人工必须明示 resource_reservations，不能既占着资源又在冲突检查中忽略。人工忙碌指标分别报告计划工作段、缓冲预约和实际执行工作段，不把未发生的缓冲自动算入实际人工负担。

固定热加工时长保持原有语义。不能为了防止切菜延迟，把一道必须加热 8 分钟的菜改成加热 10 分钟；可选择调整前序安排或预留允许的等待空间。预热的到温估计和有效加热时间分别建模，到温事件确认后才允许满足对应启动条件。所有时长调整和缓冲仍接受最小等待、最大间隔、物料有效期及取放规则检查；不可行时回报该策略不可行，不放松工艺约束。

时长策略生成新的 problem_hash，并携带 duration_policy_id、duration_data_version 和 buffer_decisions。执行中以实际事件修正剩余时长及资源状态，再按第 16 节重排。实际事件发生前，算法不能读取模拟器事先生成的未来耗时。

BUFFERED 是否适合正式提交由[时长扰动实验](#s21-7)决定。它可能减少重排，也可能增加总耗时或出菜差，不能预先宣称一定改善比赛指标。

<a id="s14"></a>
## 14 Greedy 算法

### 14.1 职责

Greedy 负责快速构造候选、为 CP-SAT 提供提示，以及在已有合法方案的情况下提供可返回结果。它不是任意复杂约束问题都有解的保证。

### 14.2 排程就绪与执行就绪

排程过程中“就绪”表示前置工序已有确定的预计完成边界，可以计算该任务的最早可行时刻。运行时 READY 则要求前置事实实际完成、物料实际可用。两者必须分开。

### 14.3 选择策略

对尚未满足的需求维护候选集合。每次计算少量候选的最早可行插入方案，优先考虑：

1. 具有硬时间窗口且剩余余量较小的任务。
2. 后续关键链较长、推迟会影响全桌完工的任务。
3. 能利用当前设备配置、减少必要转换的方案。
4. 能节约人工且不会显著拖延成员的共享方案。
5. 对完成时间差和连续人工忙碌更有利的安排。

比较同时包含单独方案，不以“组越大越好”为规则。可生成关键链优先、时间窗口优先、批次利用优先三种构造结果，使用统一比较器挑选；构造数受预算限制。

### 14.4 伪代码

~~~text
greedy(problem, deadline):
    schedule = initialize_with_fixed_executions(problem)
    uncovered = all_unfulfilled_requirements(problem)

    while uncovered is not empty and before(deadline):
        candidates = candidates_with_schedulable_predecessors(uncovered)
        placements = []

        for candidate in bounded(candidates):
            placement = find_earliest_feasible_placement(
                candidate, resources, dependencies, material_availability)
            if placement respects all hard windows:
                placements.append(placement)

        if placements is empty:
            try bounded rollback or a standalone reconstruction
            if still unavailable:
                return CONSTRUCTION_FAILED with reasons

        chosen = rank_and_select(placements)
        reserve actual phases and material allocations
        mark covered logical requirements
        update predicted completion boundaries

    if uncovered is not empty:
        return BUDGET_EXHAUSTED_WITHOUT_COMPLETE_PLAN

    return independently_validated(schedule)
~~~

有限回退可以撤销最近的未执行分组或改变资源顺序，但不得修改运行事实。单独构造、逐道参考计划也必须接受同样的校验。资源空档搜索、锚点推进、评分、平局处理和回退上限按第 14.6、14.7 节执行。

### 14.5 提示与候选池

提示包括已选载体、设备配置和开始时间；对未提供的变量允许求解器自由搜索。提示在构建最终模型后核对变量映射，避免把旧版本 task_id 对应到新变量。

提示是建议，不是约束。即使把完整可行计划提供为 hint，也要在应用层独立保存该计划，不能假定限时调用必然返回这份提示。

<a id="s14-6"></a>
### 14.6 确定性插入实现

find_earliest_feasible_placement 返回 PlacementResult，包含 carrier_id、profile_id、resource_bindings、phase_intervals、logical_time_mapping、material_allocations、transition_changes、projected_metrics 和 rejection_reasons。失败表示当前有限搜索未找到插入点，不是不可行证明。

#### 14.6.1 资源日历

每个资源维护按 start、end、carrier_id、phase_id 排序的左闭右开预约表。记录包含需求数量、是否属于运行事实、配置和状态来源。单个人工与单设备使用区间扫描；容量资源使用带增减需求的事件扫描。

Greedy 对全菜单只维护一份 human_1 日历，所有主动阶段共同查找空档；独立校验器也按这一资源合并扫描，并拒绝额外人工 ID 或容量大于 1 的输入。

CalendarState 还保存：

- 当前选中候选与被满足需求。
- 每个逻辑工序的预计边界和对应实际阶段。
- 物料产出、可用时刻及本次局部预约。
- 设备相邻批次和配置转换。
- 决策序列及可撤销变更记录。

这些对象属于本次内存试排，不直接写数据库。已完成、运行中和明确冻结部分只读。

#### 14.6.2 先确定配置和设备空档

按稳定 ID 顺序枚举允许配置、具体设备和相邻预约之间的空档。对每个空档固定前驱与后继批次，使用已审核转换规则计算载体内部阶段偏移。

若插入改变后继批次的必要转换，必须重新核对其已有预留是否足够。不能在默认插入操作中移动已安排后继的开始时刻；需要改变既有计划时进入第 14.7 节的有限回退。已发生的转换和运行中批次不能重写。

本项目 Greedy 与 CP-SAT 都不生成自由跨菜的 COMMON_START、COMMON_FINISH 候选；原菜谱已有固定程序由审核模板展开为确定的成员与人工阶段关系。Greedy 不搜索任意内部取放排列，其额外搜索限制不能删除 CP-SAT 其余合法备选。

#### 14.6.3 计算载体锚点窗口

将当前配置下各阶段及逻辑端口表示为相对于锚点 t 的偏移。已安排前驱 i 与待插入工序 j 满足：

~~~text
t + start_offset_j >= E_i + min_lag_ij
若存在 max_lag：
t + start_offset_j <= E_i + max_lag_ij
~~~

与已固定后继、物料可用时刻和设备空档有关的约束同样转换为 t 的上下界。汇总得到 [t_min, t_max]，下界向上、上界向下对齐到当前时间网格。上下界倒置时，记录关联 constraint_id 并尝试下一个配置或空档。

尚未安排的后继不能被当作已经满足；检查已知的安全时间边界，并在其实际插入时再次验证 max_lag。

#### 14.6.4 多资源共同可用点

从 t_min 开始，把候选所有实际阶段放入各资源日历试探。内部阶段互相冲突时拒绝该布局；与已有预约冲突时，把锚点推进到下一个可能解除冲突的事件点。

若相对偏移为 a 的阶段与已有预约 [u,v) 冲突，且在当前设备空档中阶段偏移固定，则向前搜索的候选跳点为向上对齐后的 v-a。容量资源取过载事件解除时刻。对本轮冲突求必要的最大推进量，移动锚点后重新检查所有阶段。

只在固定前后批次、配置和阶段布局的空档内应用该跳点公式；跨空档后必须重新计算设备转换和阶段偏移。扫描资源事件边界，不逐秒遍历长时间腌制的时间域。

~~~text
find_earliest_feasible_placement(candidate, calendars, problem, deadline):
    feasible_placements = []

    for layout in deterministic_allowed_layouts(candidate):
        for gap in deterministic_device_gaps(layout):
            phases, ports = expand_with_transitions(layout, gap)
            lo, hi = derive_anchor_window(ports, gap, problem)
            t = align_up(lo)

            while t <= hi and within_gap_check_budget() and before(deadline):
                trial = instantiate(phases, ports, t)
                conflicts = scan_all_required_calendars(trial)

                if conflicts is empty:
                    if check_dependencies_materials_and_successor_setup(trial):
                        feasible_placements.append(trial)
                        break
                    record_exact_rejection_reason()
                    advance_to_next_justified_event_or_reject_layout()
                else:
                    t = next_conflict_release_anchor(conflicts, phases, t)

    return earliest_valid_placement_with_stable_tie_break(feasible_placements)
~~~

相同 t 再次出现而没有新的布局或状态时立即退出该分支，防止死循环。资源检查通过之后仍需检查物料、依赖、热暴露和后继转换，不以“找到设备空档”代替完整可行性检查。

### 14.7 候选评分与有限回退

Greedy 的预计完成指标由已安排部分加上未安排部分的合法最早界估计，不作为完整计划的最终指标。最终选择仍使用第 13 节的统一比较器和独立校验。

默认窗口优先构造使用以下升序键：

~~~text
(
  hard_window_class,
  remaining_slack_sec,
  projected_spread_excess_sec,
  projected_makespan_sec,
  added_transition_sec,
  projected_max_human_busy_block_sec,
  negative_remaining_critical_tail_sec,
  negative_estimated_human_saving_sec,
  candidate_id,
  resource_ids,
  anchor_start_sec
)
~~~

具有明确紧时间窗口的候选 hard_window_class 优先；无有限硬窗口时 remaining_slack 使用统一的最大排序值。预计人工节省只在同样覆盖范围的单独执行比较中计算。critical_path_first 变体将后续链优先级前移；batch_reuse_first 变体将配置复用代价前移；变体定义和 ID 固定在策略版本中。

初始搜索上限：

| 参数 | 默认值 | 限制对象 |
| --- | ---: | --- |
| max_variants | 3 | Greedy 构造变体数 |
| max_placements_per_iteration | 24 | 每轮评估的候选插入方案数 |
| max_gap_checks_per_candidate | 32 | 每个候选的锚点试探与空档检查总数 |
| rollback_depth | 3 | 最多回退最近几次可撤销决策 |
| rollback_attempts | 8 | 每个构造变体的回退尝试总数 |
| max_standalone_restarts | 1 | 全单独方案重建次数 |

全部上限同时受第 15 节的 Greedy 总时间预算控制，不能让每个变体各用完整 100 或 150 ms。有限方案搜索只是 Greedy 的启发式，不删除 CP-SAT 的候选。

回退按决策序列逆序撤销最近未执行载体，原子撤销其资源预约、物料分配、逻辑满足标记及尚未实际产生的产物。禁止只撤销时间表而留下库存占用。试排的已安排后继若依赖被撤销决策，必须一起撤销；超出允许回退范围就放弃该回退分支。

每次回退将该分支的候选及位置选择记入局部分支排除记录，防止立即做出同样选择。冻结事实不能回退。回退耗尽后可尝试一次保留原菜谱强制批次的单独构造；仍失败则返回结构化构造失败，让 CP-SAT 在剩余预算内寻找可行解。

确定性验收条件：相同问题快照、策略和搜索步数预算，在没有墙钟提前截断时产生相同构造决策。墙钟时限可能改变实际完成的搜索步数，记录截断位置后再比较，不能承诺限时结果永远逐字相同。

## 15 求解预算与失败处理

### 15.1 初始预算

下表是服务内的初始预算分配，须在实际部署硬件和代表性数据上校准。

| 阶段 | 初始排程 | 动态重排 |
| --- | ---: | ---: |
| 接收、状态与知识、编译 | 350 ms | 250 ms |
| Greedy 与可行候选准备 | 150 ms | 100 ms |
| CP-SAT 全阶段合计 | 3000 ms | 1500 ms |
| 校验、事务发布、序列化 | 400 ms | 300 ms |
| 余量 | 300 ms | 250 ms |
| 服务内目标合计 | 4200 ms | 2400 ms |

这不是对每个请求的性能承诺。若编译或校验实际更慢，按剩余截止时间压缩求解预算，不能挤掉最终校验。网络是否计入官方耗时仍待确认，分别记录服务内和客户端延迟。

CP-SAT 剩余时间按 A/B/C/D 阶段分配为初始 40%/30%/20%/10%；提前完成的时间可交给后续阶段。某一阶段没有时间，则保留前面结果。限时参数在每次调用前按单调时钟重算。[OR-Tools 限时文档](https://developers.google.com/optimization/cp/cp_tasks)

### 15.2 返回策略

| 情况 | 行为 |
| --- | --- |
| CP-SAT 得到更好的合法解 | 经独立校验后加入候选池并选择 |
| CP-SAT 仅有 FEASIBLE | 可以使用，标明未证明最优 |
| CP-SAT 超时、无新解，但已有合法候选 | 返回候选池最佳结果 |
| Greedy 失败 | 允许 CP-SAT 在剩余预算内直接寻找可行解 |
| 没有任何完整合法候选 | 返回明确的规划失败，不拼装伪造计划 |
| MODEL_INVALID | 视为程序或编译错误，记录诊断 |
| INFEASIBLE | 标明当前模型及阶段不可行，返回诊断引用；深度冲突定位按第 15.4 节独立执行 |
| UNKNOWN | 表示尚未获得结论，不解释为已证明无解，也不生成确定的无解根因 |
| 候选在校验器中失败 | 丢弃；使用其他合法候选并保留错误证据 |
| 计划基于过期状态 | 不发布，按第 16 节有限重算或返回状态冲突 |

状态语义遵循 CP-SAT 官方定义。[求解器状态说明](https://developers.google.com/optimization/cp/cp_solver)

### 15.3 进程与超时

调度工作使用常驻独立进程，避免每次请求支付启动成本。首版同时运行一个调度作业；API 进程仍可处理健康检查、事件确认和展示读取。

求解工作进程正常使用限时参数结束。异常超过应用截止时间时，父进程拒绝过期结果并重建失效工作进程。不能只对一个正在运行的线程调用取消，就假定底层计算已经停止。

任何回退计划必须适用于当前菜单、状态、知识版本与时间原点。新增菜后，原计划缺少新菜，不能直接当作完整成功结果返回。


<a id="s15-4"></a>
### 15.4 不可行诊断与约束追溯

诊断区分 INPUT_INVALID、PRECHECK_CONFLICT、INFEASIBLE_MODEL、NO_SOLUTION_WITHIN_BUDGET、MODEL_INVALID 和 STALE_STATE。UNKNOWN 不能输出“已证明无解”；Greedy 的插入失败也不构成不可行证明。

每个重要约束和隐式变量域都登记 ConstraintRecord：

~~~text
constraint_id
category
task_ids / carrier_ids / resource_ids
rule_id / evidence_refs
knowledge_version / rule_version / policy_version
hardness = MANDATORY | POLICY_BOUND | OPTIMIZATION_BOUND
origin = RECIPE | DEVICE | RUNTIME | COMPILER | OBJECTIVE_STAGE
expression_summary
variable_ids / proto_constraint_indices
assumption_group_id
~~~

一个领域约束可以展开为多个求解器约束，目录保留一对多映射。领域记录在编译时生成；variable_ids、proto_constraint_indices 及实际假设变量映射随 SolverBuildReport 保存，并带 solver_build_id 和优化阶段，不能混用不同建模轮次的索引。变量域、候选删除、时间网格和求解阶段的附加上界也要记录，否则可能无法解释编译器引入的冲突。

**一级为在线快速检查。** 检查无合法设备配置、依赖环、物料数量不足、最早开始晚于最晚开始、已知固定资源重叠、精确时间无法映射到分钟等确定问题。返回具体规则、任务和来源，不进行反复求解以最小化冲突集合。未知恢复时刻等状态缺失返回 STATE_INCOMPLETE，不假装已找到数学矛盾。

**二级为独立深度诊断。** 保存原问题、版本、约束目录、候选截断报告和失败阶段后，以无优化目标的诊断模型分组分析。初始诊断预算为 2000 ms、单搜索线程；默认仅离线或按维护请求执行，不纳入比赛同步响应和实时调度队列。

诊断步骤：

1. 验证模型结构，确认错误不是不支持的约束用法或非法变量域。
2. 区分基础工艺模型与附加策略模型。若失败发生在后续优化阶段，先检查该阶段新加的目标上界。
3. 检查时间域、候选截断和分钟表达是否缩小了可行域；必要时在诊断副本中恢复候选或放宽仅用于优化的界，观察冲突来源。
4. 将可以正确控制的约束组绑定假设变量，求解纯可行性模型。
5. 只有获得 INFEASIBLE 时才读取足以导致不可行的假设集合，并映射到 ConstraintRecord。
6. 预算允许时，最多进行 6 次约束组移除检查以缩小解释范围；记录分析是否完成以及是否证明不可约。

诊断副本中暂时关闭约束仅用于定位原因，不能把违反必需工艺、资源或历史事实的结果发布为成功计划。基线模型已被证明可行时，应将后续阶段冲突优先定位到附加界，而不是对外宣称“这组菜无法制作”。

CP-SAT 返回的 sufficient_assumptions_for_infeasibility 是足以导致冲突的假设子集，不保证最小，也不保证不可约。官方说明相关缩减在单线程、非优化模型下进行；其他设置可能返回全部假设。约束的条件启用能力和效率需要在固定 OR-Tools 版本上检查，不能为所有全局约束机械套用一种写法。[官方模型与假设说明](https://github.com/google/or-tools/blob/stable/ortools/sat/cp_model.proto)

空假设集合且模型仍被证明不可行，可能表示冲突已经位于未受假设控制的基础约束中；不能解释为“没有冲突”。不支持或代价较高的约束组通过正确的诊断模型展开或限次重新构建检查处理，并记录覆盖不足。

DiagnosticReport 至少输出：

| 字段 | 含义 |
| --- | --- |
| diagnostic_id、problem_hash、snapshot_id | 定位原问题 |
| original_status、failure_stage | 区分求解状态和失败阶段 |
| scope | 基础模型、策略模型或优化阶段 |
| conflict_constraint_ids、evidence_refs | 有依据的关联约束 |
| explanation_status | PROVEN_CONFLICT、SUSPECTED、INCOMPLETE |
| base_model_feasibility | FEASIBLE、INFEASIBLE 或 UNKNOWN |
| core_irreducible_proven | 是否已经证明返回冲突集合不可约，默认 false |
| minimality_proven | 是否已经证明全局最小冲突集合，默认 false |
| candidate_truncated、horizon_relaxed_in_diagnostic | 区分工程限制与工艺冲突 |
| suggested_review_actions | 核实字段、状态或策略的建议 |
| elapsed_ms、diagnosis_complete | 预算和分析完整性 |

用户解释示例应具体到“菜 A 的蒸制只允许某配置，而当前可用设备没有该配置”。只有证据足够时才指出哪两条规则冲突；模型超时不生成看似确定的根因。菜谱规则与资源冲突通过目录映射解释，一个冲突可能涉及多条规则和多个资源。

### 15.5 故障情况下的响应边界

计算进程崩溃与烹饪操作失败是两个不同事件。前者影响本次求解，不能把实际 RUNNING 工序改成 FAILED；后者由执行反馈进入第 16.9 节。

- 求解进程崩溃：丢弃未完成结果，保留可验证且适用于当前状态的完整候选；工作进程重建不修改执行事实。
- SQLite 锁竞争：采用短 busy_timeout 和剩余预算内有限重试。初始 busy_timeout 为 100 ms、最多重试 2 次，仍受发布阶段与全链路截止时间限制。超时后不发送成功发布响应。
- 事务提交结果暂时不明：按 event_id、plan_version 查询持久化结果；在确认之前返回可查询的内部错误状态，重复请求不能重复扣料或发布。
- Neo4j 不可用：在线服务使用已发布快照正常运行；新的知识发布失败或延期，旧版本保持不变。
- 知识快照损坏：不加载该版本；有仍有效的已加载版本时只服务对应会话，否则 ready=false。
- 在线 LLM 超时：结构化比赛请求不受影响；语言事件不执行未验证意图。
- 计算中 state_revision 改变：结果不发布；按既定预算重算或返回状态冲突。
- 通知推送断开：保留持久化通知与去重键，重连后恢复读取，不重复执行实际工序。

任何故障回退都必须重新确认菜单、状态版本、知识快照和时间原点一致。没有完整合法候选时，允许明确失败；不得以“容错”为由返回缺菜、旧状态或未提交的计划。

## 16 执行状态与动态重调度

### 16.1 会话与计划

CookingSession 保存：

~~~text
session_id
session_status
session_start_at
knowledge_version / rule_version / policy_version
active_recipe_instances
current_plan_version
state_revision
execution_mode
created_at / updated_at
~~~

PlanVersion 保存不可变的完整计划、生成问题哈希、基准状态版本、优化指标、求解状态、校验报告及父版本。展示端可以比较任意两个版本；实际执行记录独立保存。

### 16.2 工序状态

~~~mermaid
stateDiagram-v2
    [*] --> PENDING
    PENDING --> READY: 前置事实和物料就绪
    READY --> PENDING: 物料或前置事实失效
    READY --> RUNNING: 接受开始事件
    RUNNING --> COMPLETED: 接受完成事件
    PENDING --> CANCELLED: 需求取消
    READY --> CANCELLED: 需求取消
    RUNNING --> FAILED: 执行失败反馈
    FAILED --> PENDING: 恢复规则允许且创建新执行尝试
    COMPLETED --> [*]
    CANCELLED --> [*]
~~~

该图表示逻辑工序的当前进度；每次实际尝试另有 ExecutionRecord。READY 不代表已经开始占用资源；RUNNING 必须对应真实确认或明确标记的模拟事件。FAILED 后只有接受合法 OPERATION_RETRY_REQUESTED 才能重新进入待执行状态，必须创建新的 execution_id，旧失败记录永久保留。

运行中非中断操作不能仅因取消菜品就立刻释放设备。取消请求可以撤销未开始后续步骤，但已经运行的载体需按照明确的停止或完成规则释放资源。已完成工序不能退回 PENDING。

LogicalRequirement 另存满足方式，如 EXECUTED、SATISFIED_BY_SHARED、SATISFIED_BY_INVENTORY。库存满足不伪装为当前菜谱发生过一次实际加工。

### 16.3 状态来源

| 模式 | 时间推进与完成来源 | 使用范围 |
| --- | --- | --- |
| SIMULATED | 模拟时钟按计划及注入事件推进 | 开发、演示、可重复重排实验 |
| MANUAL_CONFIRM | 用户明确开始、完成、延误反馈 | 展示端真实操作演示 |
| DEVICE_FEEDBACK | 设备适配器提供事件 | 后续扩展 |
| COMPETITION_PROFILE | 按赛方最终明确的规则建立状态 | 正式比赛动态接口 |

模拟事件带 source=SIMULATED。人工模式中，计划结束时刻到达只能触发提醒或超时提示，不能自动把工序标为实际完成。

可选 `dispatch_guard_policy_id=TIGHT_HUMAN_V1` 在派发前保护有限最大间隔的完整工艺链。以已发布依赖、承载体及连续设备占用范围合并保护链，并补齐链内经过的依赖路径；开工前先完成外部前序、确认后续资源可用，开工后让竞争这些资源的其他阶段等待真实释放。保护逻辑只读取已观察的执行事实，不登记虚拟占用，不预测私有未来扰动，也不修改工艺时长或间隔。实际窗口纯函数由运行模拟器与实验共用，实际开始仍由状态机和资源申请验证。已开启链的合法接续不能再被风险策略阻断；偏移仍按原触发规则要求重排。该策略默认关闭，并以版本化策略声明 4200/3000ms 初排/重排预算；采用保守等待可能增加总用时和出菜差。

如果运行工序已经超过估计结束时间，且没有新的剩余时长信息，状态标记为需要更新。不能以 max(0, estimated_end-now)=0 推导设备已释放。模拟模式按模拟规则推进；人工或设备模式需要明确状态或采用经配置说明的剩余时间估计策略。

### 16.4 事件类型

| 事件 | 作用 |
| --- | --- |
| START_SESSION | 新建一轮烹饪 |
| ADD_RECIPE | 增加库内菜品实例 |
| CANCEL_RECIPE | 取消允许取消的未完成需求 |
| DELAY_RECIPE | 增加明确的最早开始或期望完成偏好 |
| OPERATION_STARTED | 记录开始及资源绑定 |
| OPERATION_COMPLETED | 记录实际结束、消费与产物 |
| DURATION_UPDATED | 更新运行中剩余时间估计 |
| OPERATION_FAILED | 记录具体执行失败、物料结果和资源占用状态 |
| DEVICE_UNAVAILABLE / DEVICE_RECOVERED | 明确设备不可用或恢复，不自动清空占用 |
| DEVICE_RELEASE_CONFIRMED | 明确设备已清空或可结束旧占用 |
| MATERIAL_SHORTAGE / MATERIAL_ADJUSTED | 处理物料不足及追加库存调整 |
| MANUAL_OVERRIDE | 白名单状态修正，保留依据与版本检查 |
| OPERATION_RETRY_REQUESTED | 根据合法恢复规则创建新的执行尝试 |
| DEVICE_STATE_UPDATED | 更新设备配置、可用性与状态来源 |
| ADVANCE_SIMULATION | 推进模拟时钟 |
| RESET_SESSION | 结束或重置会话；保留历史记录 |

每个事件包含 event_id、session_id、occurred_at、received_at、source、payload 和预期版本。重复 event_id 返回之前的处理结果，不重复加菜、扣料或发通知。

### 16.4.1 P4 触发与释放增补（设计，待实现）

以 [P4 准备基线](P4准备与规则基线.md) 第 3、4 节为准。菜单、时长、设备或物料实际变化影响余下计划才触发重排；按计划完成可仅推进状态。先去重落账，时钟到达不证明完成；仅最新状态版本可发布。

拌料完成就释放 human_1，腌制按实际起点继续计时，下一主动步骤重新申请人。重排不从零重算已进行的等待，不把整道菜生命周期当成人工占用。

### 16.5 重排冻结规则

| 对象 | 重排规则 |
| --- | --- |
| 已完成工序 | 时间、产物、消费、分组不可改写 |
| 运行中非中断工序 | 已执行部分、当前成员与设备固定；剩余预约按明确状态更新 |
| 已承诺即将执行的短窗口 | 默认作为软稳定偏好，不能阻止必要合法重排 |
| 未开始的单独或共享候选 | 可以改变资源、顺序、分组和开始时间 |
| 已完成共享操作 | 保留真实批次和数量分配，不重新扩大已加工数量 |
| 正在运行的热批次 | 保留当前配置与已进入成员；仅按已开放规则加入新成员 |
| 已发送通知 | 保存发送事实，新计划可补发变更说明 |
| 尚未发送的过期通知 | 撤销或更新，避免按旧时间触发 |

### 16.6 库存参与重调度

例：已经共同处理 300g 胡萝卜丁，其中剩余可用 80g，新菜需要 50g 同规格物料。系统可以生成供应 50g 的库存候选，并减少对应待加工需求。

库存替代不仅要跳过“切丁”节点，还要检查其前面的清洗、削皮是否只服务于这份被替代产物。只有整段前处理的输出需求被库存满足，且没有其他仍需要的分支，才可覆盖该闭合子图。否则保留仍有用途的前置操作。

对应候选记录 covers、lot_allocations、matched_spec、rule_id 和替代范围。可用量扣除其他已承诺分配；重排可释放本计划未开始的预约，但不释放已消费或运行中必需的数量。

### 16.7 受影响范围与求解范围

新事件的影响传播包括：

- 直接变化的菜品和工序。
- 真实依赖的后继。
- 与其争用同一人工、灶眼或设备的工序。
- 参与同一共享候选或热批次的工序。
- 使用同一批物料的需求。

首版对全部未完成工序重新建模，固定已完成和运行中部分。这与典型 3 至 5 道菜规模匹配，也较容易验证全局资源约束。

受影响闭包优先用于重用知识、候选和提示。后续局部重排可以只放开部分变量，但必须保留窗口外的资源预约、物料承诺和跨窗口依赖；不能把窗口外任务直接从约束中删除。

### 16.8 版本并发与原子发布

即使只有一条调度请求，也可能在求解期间收到执行反馈。使用 state_revision 与 plan_version 防止旧结果覆盖新事实。

~~~mermaid
sequenceDiagram
    participant C as 调用方
    participant A as PlanningService
    participant D as 状态库
    participant W as 调度工作进程
    C->>A: 新增菜或重排请求
    A->>D: 短事务处理事件并读取快照
    D-->>A: revision r 与 plan v
    A->>W: 不可变问题及截止时间
    Note over A,D: 求解期间允许接收执行反馈
    W-->>A: 候选计划
    A->>A: 独立校验
    A->>D: 条件发布 要求 revision=r 且 plan=v
    alt 版本仍一致
        D-->>A: 原子保存新计划和通知
        A-->>C: 新计划
    else 状态已变化
        D-->>A: 版本冲突
        A->>A: 剩余预算内有限重算或返回冲突
        A-->>C: 明确结果 不发布旧快照计划
    end
~~~

计划计算不占用长数据库事务。条件发布在同一短事务内检查版本、写 PlanVersion、更新当前计划指针、更新未来预约及通知。

状态冲突可在剩余预算内重试一次；预算不足时内部接口返回状态冲突，保留最后已发布记录并暂停受影响的自动派发，等待有效重排。不能将“旧计划还在库中”解释为“旧计划仍适合新状态”。

### 16.9 异常执行与恢复

异常通过与正常执行相同的 event_id、状态版本检查和事务路径处理。事件先登记可确认的实际事实，再评估受影响范围和重排；规划失败不能把已经发生的设备故障或物料损耗回滚成未发生。

| 事件 | 必需信息 | 工序与资源处理 | 重排触发 |
| --- | --- | --- | --- |
| OPERATION_FAILED | task_id、execution_id、实际失败时刻、原因、已消费物料、产物状态、资源释放状态（可为未确认） | 当前执行记录结束为 FAILED；未确认可用的产物不进入可用库存；设备释放独立判断 | 影响未完成需求时触发 |
| DEVICE_UNAVAILABLE | device_id、故障生效时刻、原因、预计恢复时刻（可空）及其来源 | 禁止新的设备预约；保留运行中工序的已发生事实和未知占用 | 默认触发 |
| DEVICE_RECOVERED | device_id、恢复观测、当前配置、可用时刻 | 恢复能力不等于清空占用，只有明确清空或有效完成反馈才能释放旧占用 | 可恢复被阻塞需求时触发 |
| DEVICE_RELEASE_CONFIRMED | device_id、关联 execution_id、实际清空时刻与确认来源 | 结束等待释放状态；不能释放与该执行无关的新预约 | 释放改变待排可用时刻时触发 |
| MATERIAL_SHORTAGE | lot_id 或物料规格、实有量、缺少量、发现时刻、原因 | 暂停超出实有量的未来预约；保留历史消费 | 受影响需求未满足时触发 |
| MATERIAL_ADJUSTED | lot_id、调整前后数量、原因、证据、来源 | 追加调整账，更新可用量；不删除过去消费记录 | 影响需求可行性时触发 |
| MANUAL_OVERRIDE | correction_type、目标、前后值、原因、操作者、预期版本 | 仅允许白名单字段与已定义事件语义，不绕过工艺和资源校验 | 按修正影响决定 |
| OPERATION_RETRY_REQUESTED | 原失败 execution_id、恢复规则、投入物料、目标 task_id | 为允许重做的逻辑需求创建新执行尝试，旧失败记录永久保留 | 默认触发 |

DEVICE_STATE_UPDATED 继续用于温度、模式等一般观测；涉及不可用、恢复或释放时，必须包含上述明确语义，不能仅修改一个 occupied_until 字段就默认释放设备。

#### 16.9.1 设备占用与工序失败分开

设备状态统一使用 availability_status、occupancy_status、active_execution_id、observed_at、source、expected_recovery_at 和 release_confirmation_event_id。availability_status 可为 AVAILABLE、UNAVAILABLE、UNKNOWN；occupancy_status 可为 FREE、OCCUPIED、AWAITING_RELEASE_CONFIRMATION。expected_recovery_at 只是恢复估计，可空；确认恢复及清空的实际事件另存，不因估计时刻到达而自动改成可用。

工序已经 FAILED 但食物仍在设备中时，occupancy_status 为 AWAITING_RELEASE_CONFIRMATION。故障恢复后若尚未取出或清空，不开始新的批次。已确认清空且设备能力恢复后，才按照当前配置安排必要转换和后续任务。

对具有可信恢复估计的故障，可据此生成计划中的设备不可用区间，但后续真正派发仍需满足设备恢复和占用释放条件。对未知恢复时刻，不编造立即恢复时间：该设备暂不作为新任务的候选资源。存在其他合法设备路径时使用替代路径；所有路径都依赖未知状态时返回 STATE_INCOMPLETE，保留可执行的已确认部分并暂停受影响派发，不将部分计划包装成官方完整成功响应。

DEVICE_UNAVAILABLE 不自动证明运行中工序已经失败。如果反馈只能确认设备不可用，保留工序当前状态并标注需要确认；只有明确失败反馈或经过审核的设备事件映射才转为 FAILED。

#### 16.9.2 工序与物料恢复

异常载体可能属于共享前处理或共同热批次，影响范围必须包括全部被覆盖需求及实际物料分配。

- 明确已经合格产出的部分物料，可按审核后的产出记录建立独立批次。
- 状态未知的半成品标记为不可用于计划供应，直至得到明确判断。
- 确认损耗或报废的数量进入库存调整账，不重新加回原料库存。
- 只有存在经过审核的可续做工艺时才能生成续做路径，否则按合法重做路径处理。
- 重新加工需要新的实际投入，不把失败工序的原料当作尚未消费。
- 物料减少导致 READY 需求失去满足条件时，退回 PENDING 并记录 blocked_reason；已运行工序的实际消费不反向撤销。

MATERIAL_ADJUSTED 采用追加式账目保留 before、delta、after 和原因，可用量不能为负。盘点发现实物低于既有预约时，先标记受影响预约无效并重排，而不是维持不存在的可用量。

MANUAL_OVERRIDE 初始只允许修正未发生的计划偏好、明确的剩余时长估计，以及通过正式设备或物料事件更新观测。它不能覆盖已完成执行记录的实际时间、消费、产物或清除校验失败。确有历史录入错误时，走单独审核的追加纠正记录，不在普通调度请求中直接改写历史。

#### 16.9.3 事务与重复事件

异常处理在一个短事务内完成事件去重、状态更新、库存账与受影响标记。事务提交后发起重排，重排失败仍保留真实异常状态。事件重试返回相同业务处理结果，不重复报废、扣减、创建重做尝试或释放设备。

同一执行的失败、完成、恢复事件若乱序到达，按 execution_id、状态迁移规则和版本检查处理。完成已确认后再收到早期失败反馈时，不自动覆盖完成事实，而是登记冲突供明确校正；无法判定的冲突暂停受影响的自动派发。

重复或过期通知在新状态提交后撤销。状态变化触发的重排与并发反馈仍遵守第 16.8 节的条件发布。

#### 16.9.4 恢复验收案例

1. 共同切配中途失败：两道菜的待满足需求和剩余原料均正确，既有消费不恢复。
2. 烤箱不可用但未清空：不得为新菜释放腔体。
3. 设备恢复但原工序结果未知：不自动标为完成，不自动续烤。
4. 原料实有量低于预约：只撤销尚未发生的分配，历史消费保持不变。
5. 同一失败事件发送两次：只记一次失败和损耗。
6. 正式重做后保存两个 execution_id：一个失败记录、一个新的执行记录。
7. 异常提交后重排失败：故障与库存调整仍然存在，旧计划不能继续无条件派发。

## 17 大模型与通知设计

### 17.1 离线大模型

输入包括原文、设备能力、已定义 Schema 和少量审核示例。输出包括工序、物料转换、依赖、人工介入、参数与缺失字段。

约束要求：

- 为抽取字段提供原文定位或明确标注为估计。
- 无法确定的设备、单位和时间输出问题项，不填成确定事实。
- 原文中的屏幕提示不当作已取得屏幕参数。
- 不新增菜谱库以外的菜品，也不按同名自动合并 ID。
- 关键工艺字段经规则和人工审核后才进入正式发布包。

### 17.2 在线大模型

在线语言入口只在自然语言交互中调用，例如“再加一道菜”“把鱼晚一点开始”“取消还没做的汤”。模型产生结构化意图，由应用层解析为内部事件。

“晚一点”可能表示推迟开始或推迟上桌，存在多种实际含义时展示可理解的澄清选项。不能自动把模糊偏好变成未经确认的硬截止时间。

结构化比赛请求直接走调度主链。LLM API 不可用时，该主链仍可工作。语言入口失败应明确报告未理解或调用失败，不能声称加菜已经完成。

### 17.3 输出校验

流水线分三层：

1. Schema Validator：字段、类型、枚举、引用结构。
2. Domain Rule Validator：温度模式、数量单位、动作与资源含义。
3. Knowledge Validator：菜谱 ID 存在、工序关联成立、规则属于当前版本。

离线关键字段还需人工审核；在线事件需满足会话状态和业务权限。模型生成文本不作为设备指令直接执行。

### 17.4 解释与通知生成

发布计划形成结构化 Notification：

~~~text
notification_id
session_id / plan_version
related_task_ids / carrier_id
trigger_at / event_type
recipe_instance_ids
action / device_id / profile / duration
template_id
rendered_text
status
deduplication_key
~~~

主要通知包括开始备料、预热、放入、翻拌、取出、完成以及计划变更。文字明确动作、对象、设备参数和时间。

基础通知由审核模板填入计划事实，保证可离线生成。大模型可以形成易读说明，但温度、时长、顺序和菜品 ID 必须与已验证计划一致。可保留离线生成并审核的步骤说明，在运行时填入时间。

这保留了大模型在菜谱拆解和用户可理解内容中的作用；演示材料应如实说明哪些内容离线生成，哪些在线处理，不将模板输出描述成实时模型推理。

### 17.5 通知版本与投递

计划发布事务同时写入待发送通知记录。单进程通知任务读取这些记录，以 SSE 推送展示端，并允许按 event_id 恢复读取。

新计划撤销过期未发送通知；时间和内容未变的通知可以保留去重身份。已发送提醒保留历史，需要时发送清晰的变更通知。

网络传输按可重复投递设计，客户端通过通知 ID 去重，不承诺网络环境下天然恰好一次送达。事件定时依据完整时间戳，不能依赖按 type 排序的比赛 detailTimeline 数组。


<a id="s17-6"></a>
### 17.6 大模型抽取追溯与重放

抽取结果必须能够追溯到“哪份原文、哪次调用、哪版提示词、经过哪些修订”。仅保存最终菜谱 JSON 和一个 model_name，不足以解释错误来源或重建数据加工过程。

建立 ExtractionRun 及其产物索引：

| 分组 | 必需字段或记录 | 用途 |
| --- | --- | --- |
| 调用身份 | extraction_run_id、provider、requested_model、resolved_model_revision（服务有返回时）、provider_request_id、调用时间、状态 | 区分不同调用和实际可获得的模型版本信息 |
| 输入证据 | source_file_hash、source_recipe_id、source_spans、输入文件或内容归档引用 | 定位原文及其版本 |
| 提示与契约 | prompt_version、完整渲染提示的归档引用与哈希、schema_version、完整工具或结构化输出契约的引用与哈希 | 保留实际输入，避免只保存模板名称 |
| 生成参数 | 实际提交的 temperature、top_p、最大输出限制、seed（若服务支持）、其他影响输出的参数 | 描述调用条件；不支持的参数标记不适用 |
| 原始返回 | raw_response_ref、raw_response_hash、finish_reason、服务返回的模型标识及错误信息 | 保留截断、拒绝、工具参数和失败调用的证据 |
| 本地处理 | parser_version、normalizer_version、rule_version、代码版本、依赖锁版本、结构化结果引用及哈希 | 对固定原始返回重放本地处理 |
| 人工审核 | review_id、reviewer、审核时间、字段修改前后值、修改理由、采用的证据、批准版本 | 解释模型输出如何变成正式知识 |
| 发布关系 | knowledge_release_id、snapshot_id、关联字段的 provenance_id | 从在线知识反查审核和抽取来源 |

resolved_model_revision 无法取得时明确记为 unknown，不能将可变模型别名当作已经锁定的权重版本。提示词归档必须包含实际渲染后的消息、示例及相关工具契约；哈希用于校验完整性，不能代替内容本身。凭据通过运行环境提供，不写入归档。

追溯链为：

~~~text
原文版本与片段
  -> ExtractionRun 与原始返回
  -> 解析 / 规范化结果
  -> 校验问题与人工修改
  -> 审核通过的 CanonicalRecipeModel
  -> KnowledgeRelease / SchedulingKnowledgeSnapshot
  -> 计划中引用的工艺字段与规则
~~~

发布包保存 extraction_runs.json 和 extraction_artifact_index.json；原始请求、返回和审核补丁由离线归档目录按内容哈希管理，随数据维护交付物保存。在线快照只携带需要的 provenance_id、摘要及引用，不加载全部大模型原始文本。发布检查确认引用完整、哈希匹配，不能出现只有一个无法解析的 run_id 的孤立字段。

重放分两种，并在报告中分开：

1. **本地处理重放**：读取已归档的原始返回，使用指定解析器、规则和审核补丁，重建规范化结果并比较哈希。参与结果的时间戳、随机 ID 等外部值需固定或与内容哈希分离。
2. **外部模型重新生成**：用同一归档输入重新调用模型，形成新的 extraction_run_id，比较字段差异。它是稳定性实验；相同提示、temperature=0 或 seed 不能单独保证外部服务逐字相同。

在线自然语言意图同样记录 intent_run_id、输入引用、结构化意图、校验结果和最终 event_id。模型返回成功不代表业务事件已经提交；事件被拒绝或状态过期时，追溯记录必须保留实际处理结果。

### 18.3 CompetitionAdapter 的模式

| 模式 | 明确语义 | 使用条件 |
| --- | --- | --- |
| INDEPENDENT_REQUEST | 每个数组创建独立初始计划，以接收时刻为原点 | 当前明确可支持的初始排程契约 |
| QA0930_TASK_INSERT_DEVELOPMENT | 显式 task_id 首轮非空菜单初排，后轮恰好一个菜谱为追加；完整求解原菜单与新菜 | 9 月 30 日已明确单菜追加语义；任务传递、累计响应和时间投影为显式开发选择，待提交协议确认 |
| EXPLICIT_CONTEXT | 会话由明确的调用上下文或附加协议关联 | 使用已确认上下文，或明确标注的开发草案 |
| SINGLE_ACTIVE_FULL_MENU_SIMULATED | 数组表示当前完整菜单，单活动会话，按声明的模拟时钟推进 | 仅在该语义被确认或用于明确标注的演示时启用 |

不会根据“数组有重叠菜名”“请求时间很接近”“单并发”自动断言重排关系。初次任务的单菜输入也可以是初排；同一已有任务的单菜输入才按答疑解释为追加。无 task_id 保留独立初排兼容；已有任务的多项输入暂不自动推断为全量菜单。INDEPENDENT_REQUEST 不代表官方动态接入，QA0930 开发 profile 也不代表全部未决规则已得到赛方确认。

### 18.4 官方字段映射

| 输出 | 映射规则 |
| --- | --- |
| overview.finishTime | 发布计划最晚菜品完成的完整时刻投影为 HH:mm |
| overview.timeSpent | 对应输出原点下的并行跨度，分钟字符串 |
| overview.timeSave | 经验证的串行参考减并行跨度，分钟字符串 |
| overview.recipeCount | 静态契约等于输入数组长度；QA0930 开发累计响应按有效累计菜单计数，动态官方口径待确认 |
| cookingTimeline.name | 原请求名称，不改别名 |
| cookingTimeline.product | 展示用主要设备；内部保留全部实际设备 |
| cookingTimeline.startTime/endTime | 该菜实际计划边界的绝对时间投影 |
| cookingTimeline.timeSpent | 该菜最早相关任务到必要完成的跨度 |
| ingredientsSummary | 按荤菜、素菜、调味品合并原料需求，不因共享切配重复累加 |
| detailTimeline | 由实际选中载体与阶段生成，先按 type，再按相对开始时间排序 |
| recipeDetail | 每个请求菜谱一项，步骤来自实际选择的执行路径与成员映射 |

9 月 30 日答疑只补充动态输入，尚未修改原规范“仅覆盖当前请求菜谱”的响应要求。开发累计菜单输出应使用单独的 profile 和校验上下文，不静默改写静态规则；若评测要求 REQUEST_ONLY，内部仍规划累计菜单，再按该范围投影。五个顶层字段保持相同。

共享工序在详细执行时间线中体现为一次实际操作。共同热批次的成员时长不同时，detailTimeline 按成员的实际加工区间展开，预热与真正共享的人工动作仍只安排一次；不能用整批最长区间让所有菜看起来都加热了相同时间。每道菜的 recipeDetail 可说明其由共同加工提供的步骤。校验时通过内部 task_id 判断覆盖，不按重复出现的文字统计实际执行次数。

主要设备使用离线审核的展示字段；多设备接力不因该字段只有一个值而丢失约束。无主要设备的特殊菜谱展示值需在数据和协议中统一，不能临时捏造其使用烤箱。

### 18.5 参数与文本规则

- type 范围 1 至 6，映射遵循官方枚举。
- 设备工作步骤带 recipeNames；参数中的 recipeName 必须属于该列表。
- 预热有真实正时长，并输出温度和时间。
- 正式烹饪按协议允许省略的参数可省略，但 recipeDetail 的设备步骤仍必须有 mode、temperature、time 字符串。
- parameters.time 为整数分钟；温度按协议使用数值或明确火力文本。
- 标题和描述遵循“准备……备用”“将……腌制……”“将……放入设备，设置……”“出锅/装盘……”等要求。
- 不将校验错误、调试信息或模型推理文字混入成功 JSON。
- 官方示例存在先装盘后完成加热的疑点，测试只复用结构要求，不复用该时间顺序作为正确答案。

### 18.6 跨日、秒级和重排时间原点

内部保留完整时间戳与相对秒数；同一天的 HH:mm 不能表达跨日顺序，因此以数值时间校验全部关系。

对于跨日初排，relative minute 可以超过 1440；HH:mm 按官方格式输出，完整日期只在内部和展示端提供。不能通过截断总耗时把 24 小时腌制改成当天完成。

动态比赛输出尚缺少以下契约：重排是否继续使用原会话原点，是否重新以当前请求接收时刻为零，是否输出历史工序，以及串行参考如何计算。内部统一使用原会话绝对事实；适配器在明确协议后执行投影。

9 月 30 日“不考虑具体插入时间点”表示无需调用方提供插入时刻，未定义自动完成旧工序。P5 开发默认 PLAN_ONLY，未反馈的工序保持未执行；真实或模拟进度均通过已标注来源的事件推进。开发累计输出采用 SESSION_ORIGIN，属于项目选择，不作为官方时间原点已经确认的结论。

若采用请求时刻重置原点，必须明确历史信息在哪里表达以及如何统计当前请求全部菜品；不能把历史任务转成负分钟后直接输出，也不能把已完成任务再次安排到零时刻执行。

### 18.7 错误与失败

内部接口采用明确错误码：INVALID_REQUEST、UNKNOWN_RECIPE、RECIPE_NAME_MISMATCH、DATA_NOT_READY、STATE_CONFLICT、STATE_INCOMPLETE、NO_FEASIBLE_PLAN、SOLVER_MODEL_ERROR、SERVICE_NOT_READY。

建议内部 HTTP 状态分别使用 422、404、409、503 等表达参数、状态和服务问题。官方失败响应结构未定义，CompetitionAdapter 将失败格式作为独立配置并在提交接口文档中说明，不伪造 HTTP 200 的空成功计划。

两个不同 ID 但同名的菜谱可以在内部准确区分，官方 recipeNames 仅有名称时仍有消歧局限。不得删除其中一个或修改官方菜名；最终外部表示按赛方确认方案执行。

## 19 存储与一致性

### 19.1 数据所有权

| 数据 | 主要存储 | 可重建性 |
| --- | --- | --- |
| 原始材料 | 原始文件，只读保留 | 原始依据 |
| 问题诊断资料 | 版本化问题快照、约束目录与诊断记录 | 可离线重放失败模型 |
| 审核规范化知识 | JSON 发布包 | 图谱和缓存的重建来源 |
| 知识关系与证据 | Neo4j | 从指定发布包重建 |
| 会话与运行事实 | SQLite | 从事务记录和事件恢复 |
| 历史计划 | SQLite 不可变记录 | 与问题快照对应 |
| 在线知识快照文件 | 本地只读发布文件 | 从固定版本图谱和规范化数据重新导出 |
| 内存知识索引 | API 进程内存 | 从已验证快照和 KnowledgeIndex 加载 |
| 本次求解问题 | 工作进程内存，必要时保存快照 | 从请求、版本和状态复现 |
| 大模型调用、原始返回和审核补丁 | 离线内容归档及 ExtractionRun 索引 | 固定输入重放解析与审核链；不作为未经审核的在线事实 |
| 展示视图 | 发布计划的投影 | 可重新生成 |

图谱与关系数据库不做每个执行事件的双写。只有知识发布维护图谱；执行状态更新只影响状态库，避免为一次切配完成引入跨数据库分布式事务。

### 19.2 运行库表

| 表 | 关键内容 |
| --- | --- |
| knowledge_releases | 版本、文件哈希、snapshot_id、Schema、图谱与快照构建状态 |
| cooking_sessions | 会话、当前计划、state_revision、数据版本 |
| recipe_instances | 会话内菜品身份、启用或取消状态 |
| runtime_events | event_id、来源、发生与接收时间、处理结果及异常因果关联 |
| recovery_records | 失败执行、恢复规则、新尝试、资源释放与审核信息 |
| material_adjustments | 物料调整前后数量、损耗、原因、证据及关联事件 |
| diagnostic_reports | 问题哈希、约束目录、冲突集合、证据与诊断状态 |
| operation_executions | 实际开始结束、资源、载体、状态 |
| material_lots | 产物规格、数量、来源、储存状态 |
| material_allocations | 计划预约、实际消费、对应需求 |
| device_runtime_states | 当前配置、可用性、占用、执行身份、恢复估计、释放确认与观测来源 |
| plan_versions | 计划正文、问题哈希、父版本、指标 |
| plan_task_mapping | task_id 与载体、阶段、逻辑满足方式 |
| notifications | 触发时刻、版本、去重键、投递状态 |
| benchmark_runs | 用例、配置、种子、耗时、解与界 |
| audit_records | 数据发布和关键状态修正记录 |

大型计划正文可以保存为规范化 JSON，同时保留会话、版本、task_id 等常用索引。Schema 版本写入记录，迁移脚本与程序版本绑定。

### 19.3 一致性与幂等

- runtime_events.event_id 唯一，重复请求不重复执行业务变化。
- cooking_sessions 使用递增 state_revision 执行乐观并发控制。
- plan_versions 的 session_id 与 version 组合唯一。
- 计划发布、未来预约更新和通知更新位于同一事务。
- 读取快照后释放事务，再进行耗时求解。
- 使用条件更新判断版本是否仍一致，不能只在内存中检查一次。

SQLAlchemy 提供版本计数机制；若采用显式条件 UPDATE，需要检查受影响行数，批量写入不能绕开版本约束。[SQLAlchemy 版本控制文档](https://docs.sqlalchemy.org/en/20/orm/versioning.html)

### 19.4 快照加载与缓存策略

SchedulingKnowledgeSnapshot 与 KnowledgeIndex 是在线静态知识的正式来源，不只是 Neo4j 不可用时的临时缓存。每个 API 进程启动时验证并加载所需发布文件；菜单子图通过内存索引提取。初排与重排的图数据库请求次数应为零。

内存映射键包含 snapshot_id、knowledge_version、rule_version 和 snapshot_schema_version。已加载对象不可变；版本切换创建新对象，并保留活动会话正在使用的旧版本。内存对象与本地发布文件的哈希写入请求追踪记录。

候选缓存还包含菜单实例参数、设备能力和适用状态信息。实际开始时间、库存余量和运行中批次不可从没有 state_revision 的缓存中复用。规则评估结果也必须明确哪些字段依赖运行状态。

不缓存带有过期 HH:mm 的最终响应供另一次请求直接使用。若复用相对时间计划模板，必须重新适配当前状态与原点并校验；首版优先缓存静态知识和不依赖运行状态的规则索引。


初始压测环境以 4 个 CPU 核心、8 GB 内存作为起点，属于容量验证假设，不是已实测最低配置。核心调度不依赖本地 GPU。模型通过外部 API 或已经生成的审核数据工作。

首版 API 实例数与调度作业并行数均为 1。OR-Tools 搜索线程数初始为 min(4, 已分配 CPU 核数)，记录配置。可复现实验另设单搜索线程和固定随机种子；不承诺多线程运行每次产生完全相同的解。

Windows 交付包固定 Python 运行时、按锁文件校验的离线依赖、已构建 Vue 静态文件、知识快照及策略，使用 PowerShell 安装、启动、核验和停止。运行库放入独立可写状态目录，知识文件保持只读。前端运行不需要 Node，构建工具版本仍记录在交付清单。知识维护独立执行，在线服务启动依赖本地快照、状态库和求解进程，不依赖 Neo4j 健康检查。维护和深度诊断进程不进入实时调度队列；同机运行时在维护窗口执行，避免后台分析抢占比赛计算预算。

### 20.2 启动与恢复

启动顺序：

1. 检查配置、状态库迁移和发布 manifest。
2. 从本地加载指定 SchedulingKnowledgeSnapshot 与 KnowledgeIndex，验证版本、哈希和 Schema；此步骤不连接 Neo4j。
3. 加载活动会话固定的数据版本并恢复版本引用，校验库存和执行状态。
4. 启动求解工作进程并运行一个小型预热问题。
5. 恢复通知派发；先撤销版本过期或状态已不适用的提醒。
6. 必需的快照、状态库和求解进程检查完成后 ready=true。

在线服务恢复与新知识发布分别执行。若需要构建新快照，由维护流程访问 Neo4j；构建失败不破坏现有发布文件。

重启不能自动把未确认运行工序标为完成。SIMULATED 会话根据保存的模拟时钟恢复；实际反馈模式保留状态来源，并对故障设备、未知占用和未完成恢复流程重新获取明确状态。

Neo4j 和状态库不直接暴露到公网。管理和审核接口采用访问控制，模型凭据由环境或机密配置注入。请求结构、数量规模与输入长度设置明确上限；这些上限按比赛负载验证，不能因随意限流拒绝正常评测。

### 20.3 展示端范围

Vue 3 负责页面和交互，ECharts 负责时间区间与关系图展示。[Vue 文档](https://vuejs.org/guide/introduction.html)、[Apache ECharts 项目](https://github.com/apache/echarts)

展示端包括：

- 菜谱选择：通过 ID 选择，名称重复时展示能区分的菜谱信息。
- 总览：预计完成时间、完成时间差、总耗时和连续人工忙碌。
- 甘特图：人工、两个灶眼、蒸箱、烤箱等分泳道显示。
- 共享说明：选中共同切配或共同加热时展示成员与原因。
- 知识子图：查看工序前置和物料变化，不默认显示全库复杂网络。
- 执行控制：模拟时间、开始与完成确认、延误注入。
- 动态加菜：展示原计划和新计划的变化。
- 数据审核视图：查看原文、补全值和证据，作为开发工具。

计划差异的状态颜色之外同时使用标签和图例：旧计划灰色、新计划蓝色、新增橙色、完成绿色。颜色不作为唯一信息通道。按用户2026-10-07的甘特图要求，时间区块改用每道菜固定的不同颜色，并以独立图例对应菜名；共同批次按成员菜品分色。执行中、完成、失败通过边框及文字区分，冻结/历史采用淡色虚线；同名菜保留身份后缀。提示卡支持换行、滚动和鼠标移入，未变化的会话轮询不重绘图表。

长腌制计划可按小时、天缩放，短人工步骤可以放大到分钟；不把跨日任务压成难以辨认的一条细线。默认使用完整日期说明跨日结果。

### 20.4 日志与观测

每个请求记录 request_id、session_id、problem_hash、snapshot_id、数据与策略版本、state_revision、菜品数、逻辑工序数、候选数、截断标志、各阶段耗时、求解状态、最佳目标值、界、校验结果和回退原因。关联 ModelSizeReport、PruningRecord 和 diagnostic_id，记录变量、区间、约束、顺序边规模及删除原因。

分别记录内存知识提取、编译、Greedy、CP-SAT、校验、发布和序列化耗时。快照加载和离线图查询单独计时，在线 Neo4j 请求次数应为零。仅有 SolverTime 不能证明达到端到端响应目标。

发布产物记录程序版本、依赖锁、数据库 Schema、知识发布包和策略配置。针对可复现的问题保存脱离数据库连接的 SchedulingProblem 快照。

异常事件记录 event_id、execution_id、caused_by_event_id、恢复规则及资源和物料变更；时长实验记录 duration_policy_id、扰动数据版本与种子。数据问题通过 provenance_id 关联 ExtractionRun 和审核记录。大段原始模型文本放在内容归档中，运行日志仅保存必要摘要与引用。

## 21 校验和实验评估

### 21.1 独立调度校验器

校验器输入包含发布包内的原规范化知识依据、运行快照、编译结果和候选计划。知识依据从校验过的本地文件或保留完整来源映射的只读快照取得，不查询 Neo4j。除了检查候选是否满足 SchedulingProblem，还检查 Compiler 是否遗漏原知识中的必需需求或约束。

| 类别 | 必查不变量 |
| --- | --- |
| 身份与覆盖 | 请求菜谱不漏不增；每个需求恰好被一种执行或供应方式满足 |
| 工序依赖 | 原菜谱必需依赖、最小等待与最大间隔满足 |
| 资源 | 人工不冲突；每个灶眼互斥；同腔体不同批次不冲突 |
| 设备参数 | 模式、温度、湿度、时长符合该设备与工艺路径 |
| 热加工 | 成员各自加热时间、介入、实际取放边界合法 |
| 共享 | 全组兼容；未双重占用；被替代子图完整 |
| 数量 | 物料规格匹配，供需、损耗、预约和消费守恒 |
| 时间 | 无非法负时间；未来动作不早于状态时刻；完成时刻正确 |
| 历史 | 已完成事实未改写，运行中资源未提前释放 |
| 目标 | 从实际区间独立重算耗时、完成差、人工忙碌和扰动 |
| 输出 | 五个顶层字段、数据类型、排序、名称、参数和时间投影一致 |

资源校验采用独立事件扫描：区间结束与另一区间开始相同时按左闭右开语义处理。批次校验先验证外层资源预约，再验证内部成员关系，不能把内部合法重叠判成冲突。

开发时故意构造依赖缺失、重复覆盖、过度加热、库存双分配和历史改写的错误计划，确保校验器能够拒绝。校验器应独立于求解器约束代码，但不重复维护另一份设备参数事实。

### 21.2 基础测试集

- **单菜集**：100 道菜全部运行，检查数据完整和至少一条可行执行路径。
- **人工场景集**：至少 20 组覆盖关键边界的多菜案例。
- **组合集**：以固定种子生成至少 200 组 3 至 5 道菜组合，确保覆盖所有菜谱 ID。
- **重排集**：至少 20 个明确事件脚本，覆盖加菜、延误、已完成共享和运行中批次。
- **错误输入集**：ID 重复、同名异 ID、名称不匹配、非法状态版本、重复事件。
- **小规模精确集**：少量工序和短时间域，独立枚举可行选择和顺序，验证最优值及约束含义。
- **时长扰动集**：按第 21.7 节比较名义、缓冲与动态重排策略。
- **属性与状态机集**：按第 21.8 节验证生成问题及连续事件的不变量。
- **故障注入集**：按第 21.9 节覆盖求解、存储、快照、语言入口和执行异常。

具体数量是首版验收规模，可增加；在没有完成这些运行前，不填写“全部通过”。

### 21.3 必须覆盖的代表案例

| 编号 | 场景 | 验证目标 |
| --- | --- | --- |
| T01 | 相同食材但切丝、切块不同 | 不产生错误切配共享 |
| T02 | 合法相同规格共享 | 一次实际加工、正确分配数量 |
| T03 | 一个成员很晚就绪 | 保留单独执行并正确比较等待成本 |
| T04 | 同温同模式同时长 | 合法共同批次，预热不重复 |
| T05 | 同温同模式 20 分钟与 8 分钟 | 不把短时菜统一加工 20 分钟 |
| T06 | 同温不同模式或不同温度 | 不错误共批 |
| T07 | 两灶同时工作并需要人工 | 设备可并行，但人工按真实需求互斥 |
| T08 | 香菇烤芦笋 | 保留菜内并行 |
| T09 | 家常鲈鱼、鸡翅包饭 | 保留多设备接力和真正完成边界 |
| T10 | 糯米烧麦 | 保留泡发与明确两批蒸制 |
| T11 | 亲朋欢聚套餐 | 保留固定程序中的中途加料 |
| T12 | 鸡仔饼、广式叉烧 | 保留长准备与跨日输出 |
| T13 | 两个不同 ID 的麻辣对虾 | 内部身份和请求覆盖不混淆 |
| T14 | 共享切配已完成后加菜 | 使用合法余量，不能重写已加工量 |
| T15 | 热批次运行中加菜 | 只有允许的加入规则生效 |
| T16 | 重排计算中收到完成事件 | 旧 state_revision 结果不能发布 |
| T17 | 重复 ADD_RECIPE 事件 | 不重复加菜或消耗库存 |
| T18 | 求解超时但已有合法候选 | 在预算内返回完整合法结果 |
| T19 | Greedy 失败且 CP-SAT 未找到解 | 不假报成功，不把 UNKNOWN 当 INFEASIBLE |
| T20 | 秒级操作转换成比赛分钟输出 | 不因独立取整产生冲突或过度加热 |
| T21 | 旧通知等待发送时计划变化 | 旧提醒撤销，当前提醒与计划一致 |
| T22 | 设备温度或模式数据冲突 | 发布前拦截，不静默裁剪 |

表中实际菜谱只说明原资料存在的工艺特征；具体时长以最终审核数据为准。合成数值案例单独标注，不混入真实数据标注。

### 21.4 对比实验

首先比较完整系统的效果：

| 组别 | 求解方式 | 跨菜共享 |
| --- | --- | --- |
| A | 经验证的逐道参考计划 | 关闭 |
| B | Greedy | 关闭 |
| C | CP-SAT，无 Greedy 提示 | 关闭 |
| D | Greedy 加 CP-SAT | 关闭 |
| E | Greedy 加 CP-SAT | 仅共享前处理 |
| F | Greedy 加 CP-SAT | 共享前处理与共同热批次 |

全部组别使用同一份工艺事实、时长、资源与硬约束。关闭跨菜共享不代表删除原菜谱本来就有的固定组合加工或批次。

再做受控实验：

- D 对 C：判断 Greedy 提示对找到可行解的速度和解质量的贡献。
- E 对 D：判断共享前处理的贡献。
- F 对 E：判断共同热批次的贡献。
- 相同候选模型下启用或关闭有效图预处理：判断域过滤和边界的求解贡献。
- 离线从 Neo4j 导出与从等价规范化 JSON 构建同一知识快照：核对语义及 SchedulingProblem 一致，比较知识维护、导出和编译成本。在线正式路径统一读取已发布快照；若另测直接查询数据库的成本，标为实验路径。相同模型不宣称数据库改变了数学最优值。
- 等价去重、有证明的支配规则和预算截断分别消融：报告模型规模、编译耗时、首次可行解时间和解质量；不把截断造成的搜索变小表述为无损剪枝。
- 不同候选数量上限：比较候选覆盖、排程质量和求解开销。

这样可以分别证明知识组织、预处理、提示、共享机制的价值，避免把多个因素同时变化后的改善全部归因于知识图谱。

### 21.5 指标报告

报告可行率、发布校验通过率、接口契约通过率、Makespan、FinishSpread、人工指标、重排扰动、P50/P95/最大响应耗时、超时率、回退率、候选数、模型规模、求解节点与界。诊断另外报告状态分类准确性、证据覆盖和分析耗时；执行实验另外报告时长偏差、异常恢复及失败轨迹。

冷启动和已预热服务分别测试；按单路请求运行主要性能评估。固定数据版本、硬件、线程数、随机种子和预算。相同测试条件多次运行，呈现波动而非只报最好结果。

对小规模精确实例可以报告与已证明最优解的差距。对大实例只报告当前可行值和对应模型、对应目标阶段的有效界；阶段 C 在完成差约束下的界，不等同于原始无附加约束问题的总耗时最优界。

正式比赛的隐藏标注和理论最优基准未公开，本地结果只表示项目自测，不直接换算成官方得分。

### 21.6 验收标准

1. 全部发布菜谱通过数据发布门槛。
2. 全部成功发布的计划通过独立约束和接口校验。
3. 代表性单菜、多菜和重排场景无工序遗漏、资源冲突及历史改写。
4. 同版本重放结果的事实、约束和指标可解释；允许多线程产生不同但合法的等价计划。
5. 实测服务内延迟达到设定目标，另明确客户端和网络耗时。
6. 官方动态接口的会话与时间语义落实后，完成实际协议重排联调。
7. 对共享收益无改善的案例也保留结果，不筛掉不利案例。
8. Neo4j 关闭时，基于有效发布文件完成在线冷启动、初排、重排与子图读取；错版或损坏快照被拒绝。
9. 工序失败、设备恢复、释放确认和物料调整满足第 16.9 节，不提前释放资源、不恢复已损失物料、不改写历史执行。
10. 不可行诊断能追溯约束和来源；UNKNOWN、附加策略冲突及真正基础矛盾得到区分，不宣称未经证明的最小冲突集合。
11. 抽取归档与审核链完整，固定本地处理过程可重放；外部模型重新生成单独比较差异。
12. 第 21.7 至 21.9 节实验按声明规模执行并保存报告；所有成功计划通过不变量检查，注入故障时保持一致性或返回明确失败。

### 21.7 时长扰动与鲁棒性实验

这一组实验验证“执行时间与计划估计不同”时的表现，不把求解器对固定时长模型的最优性当作实际做饭时的保证。

**实验输入与分组。** 从已审核菜单中固定选择至少 40 组代表性 3 至 5 道菜组合，覆盖人工密集、蒸烤密集、共享收益明显、长准备和紧最大间隔等特征。每组生成 100 条扰动轨迹，构成每种策略至少 4,000 次离线模拟的初始规模。对以下四组使用相同菜单、随机种子、设备、事件轨迹及求解预算：

| 组别 | 初始时长策略 | 执行后的处理 |
| --- | --- | --- |
| R-A | NOMINAL | 保持已选分组和相对顺序，按执行事实顺延 |
| R-B | NOMINAL | 按已声明的触发策略动态重排 |
| R-C | BUFFERED | 保持已选分组和相对顺序，按执行事实顺延 |
| R-D | BUFFERED | 按与 R-B 相同的触发策略动态重排 |

不重排组的执行器仍检查真实前置、人工和设备可用性，未满足时等待，不能按旧时间戳强行启动并制造资源重叠。顺延若导致强制最大间隔等约束无法满足，应记录失败或进入规定恢复流程，不能忽略硬约束以凑齐完成结果。

**扰动生成。** 有足够适用观测数据时，从固定版本的经验样本生成场景；无数据时，明确标记为合成压力实验。初始合成方案对允许估计的人工和到温阶段使用名义时长的 0.8、1.0、1.2、1.5 倍，并说明抽样权重；取值还应服从已审核的适用范围。它们不是已证实的概率分布。不得缩短工艺最小时长，也不得对固定有效加热时间任意乘系数。

同时设计整轮操作人员变慢的相关扰动，以及单工序局部延误，避免仅测试所有工序独立波动。不同候选的实际时长用同一轨迹中的公共速度因子和稳定工序标识派生；共享任务沿用对应成员和共享工艺的已声明生成规则，不能因为某方案少调用一次随机数而失去可比性。设备故障和物料损坏作为第 21.9 节单独的异常场景，不能混称为普通时长波动。

模拟器保存完整扰动轨迹；调度服务只能看到已发生的开始、完成、延迟和到温事件。重排触发、事件合并时间窗和次数限制属于实验配置，四组间只有待比较因素不同。竞赛分钟输出场景仍使用同一网格策略，另可用秒级模拟记录真实偏差，不能将不同量化策略的收益归入缓冲收益。

**报告指标。**

- 实际总完成时间、出菜完成差，以及超过官方 300 秒要求和项目 240 秒目标的比例，分别报告。
- 相对初始计划的完成延迟、资源等待、最长实际人工忙碌块。
- 重排次数、各次响应耗时、计划改变数量及已发提醒的变更数量。
- 执行失败率、恢复成功率、约束违规次数及失败原因分布。
- BUFFERED 引入的初始计划延长量，及其换取的延迟或重排变化。

保留全部轨迹，给出配对差值及分布。未完成案例计入失败率，完成时间统计注明“已完成子集”及样本数，不能通过删除失败轨迹美化均值。正式策略只有在同一口径下显示可接受的正确性、耗时和体验取舍时才启用 BUFFERED。没有观测样本时，结论限于声明的合成场景。

<a id="s21-8"></a>
### 21.8 属性测试与状态机测试

使用 pytest 承载测试，Hypothesis 生成输入、动作序列并缩减失败案例。状态机测试通过生成多步操作检查事件之间的不变量，能力依据见 [Hypothesis 状态机测试文档](https://hypothesis.readthedocs.io/en/latest/stateful.html)。它用于发现组合边界错误，不代替真实菜谱验收或对任意规模的形式化证明。

生成器分成三类，避免对随机输入提出错误的可行性预期：

| 类别 | 构造方法 | 可以断言的结果 |
| --- | --- | --- |
| 结构合法问题 | 生成无环依赖、合法 ID、资源和数量约束 | 结构检查通过；不保证全部硬约束存在共同解 |
| 已知可行问题 | 先生成满足资源和物料规则的执行见证，再由见证构造工序、时间窗与约束 | 编译和校验不得丢失该见证；限时求解未找到解不能证明实例不可行 |
| 已知矛盾问题 | 注入可独立证明的时间冲突、负可用数量或无合法设备路径 | 不得发布成功计划；预算内未完成证明时允许 UNKNOWN，但不能谎报合法解 |

核心性质包括：

1. **计划正确性**：所有成功结果均满足需求完整覆盖、依赖、资源、数量、时间网格和运行历史不变量。校验使用独立扫描或小规模参考实现。
2. **编译完整性**：原知识中的强制需求、显式批次和规则均可在 IR 中追踪；更换快照读取方式不得丢失约束。
3. **快照一致性**：规范化数据经过图谱投影、导出、加载后，调度相关实体、规则及引用相同；比较语义内容而非对象顺序或生成时间。
4. **剪枝保真**：小规模问题独立枚举完整计划，对每项等价或有证明的支配删除验证替换仍可行、覆盖相同且目标不劣；同时加入第 9.5 节“更短却不可替换”的反例。预算截断不被标记为安全支配，也不要求保持全局最优值。
5. **Greedy 插入与撤销**：加入载体后资源、物料和满足映射一致；撤销返回原状态哈希；候选顺序与步数预算固定时结果可重复，墙钟截断差异单独标识。
6. **执行幂等与历史**：重复 event_id 不产生第二次加菜、消费、产出或失败处理；旧 state_revision 不能发布；完成及失败执行记录不被新计划改写。
7. **通知与发布**：通知引用存在的已发布版本；旧提醒被撤销或明确更正；重试不能产生同一去重身份的多个有效提醒。
8. **重放链**：归档请求、返回、审核补丁和发布引用完整；固定本地处理版本能够重建规范化结果，外部模型重新生成的差异不误报为本地重放成功。

状态机动作包含加菜、开始、完成、延迟、工序失败、设备停用与恢复、释放确认、物料不足、人工修正、重试及重排。生成器同时包含合法动作和明确非法动作；非法动作被拒绝后，业务状态应与拒绝前一致。另生成重复和乱序事件，使用简单参考账本核对资源释放、物料余额、执行身份和版本，而非调用被测实现自己的状态转换函数作为答案。

初始每次常规检查运行每类关键性质不少于 200 个样本；较长的定期检查运行至少 100 条、每条最多 50 步的状态机序列，并受测试总时限控制。保存工具版本、配置、种子、最小失败输入及事件序列到回归用例库。有限样本未发现错误不等于证明整个系统无缺陷；测试结果需报告实际运行数量和覆盖内容。

<a id="s21-9"></a>
### 21.9 故障注入测试

故障注入验证发布和恢复边界。它与正常调度性能测试分开统计，但每次在线请求仍受同一端到端预算约束。故障时允许返回明确失败，不能为保持成功率输出未验证或未持久化的计划。

| 注入点 | 具体场景 | 必须观察到的行为 |
| --- | --- | --- |
| 求解工作进程 | 启动前不可用、求解中退出、超过预算、结果传回前退出 | 使用主进程持有且对当前状态仍有效的已验证候选；没有候选则明确失败；回收任务后可处理后续请求 |
| SQLite 锁等待 | 另一连接持有写锁，覆盖事件接收与计划发布 | 等待和重试在预算内；没有部分写入；不把尚未提交的业务状态返回为成功 |
| 事务提交边界 | 提交前中断、提交后响应丢失、调用方无法判断提交结果 | 用持久化事件或发布身份查询最终状态；重试效果幂等；未知状态不能凭内存推断已成功 |
| 知识图数据库 | 在线运行中关闭 Neo4j；Neo4j 关闭时冷启动在线服务 | 有效发布快照足以完成启动、初排和重排；离线维护任务单独报告不可用 |
| 快照与版本 | 文件截断、哈希错误、Schema 不兼容、会话版本缺失 | 不加载损坏或错版知识；有效在用版本可继续服务，无法恢复的会话明确失败；不静默切换知识 |
| 并发状态变更 | 求解期间完成操作、确认故障或再次加菜 | 过期结果被条件发布拒绝；有剩余预算时重新计算，否则返回明确的版本冲突 |
| 大模型接口 | 超时、无效 JSON、未知菜谱、重复回调 | 结构化比赛请求正常；未通过校验的语言请求不产生业务事件；已处理意图不重复生效 |
| SSE 与通知 | 推送断连、恢复读取、重复消息、重排后旧消息延迟到达 | 依持久化游标补发；客户端去重并核对计划版本，不将旧提示当作当前动作 |
| 执行异常 | 热加工失败后未确认释放、恢复但腔体仍有物料、共享输出损坏 | 保留真实占用和库存损失；只按已审核恢复规则续做或重做 |
| 服务重启 | 有运行中工序、待提交计划、待发送通知时重启 | 恢复已提交事件和版本；不把计划时间到达当成真实完成；不重发已失效动作 |

每个用例检查运行状态、事件账本、物料账本、当前计划、通知状态和请求响应。要求是“同一事件只产生一次业务效果、同一发布身份最多提交一次计划”，不承诺网络传输只发生一次。若新计划失败，已经确认的真实故障和物料损失仍然存在。

至少覆盖第 16.9.4 节的恢复案例，并逐项覆盖本表中列出的提交前后边界。报告故障位置、注入方式、恢复时间、是否使用回退、失败码和最终状态哈希。注入结果与功能测试均通过后，才能声明相应故障路径已实现和验证。

## 22 建设阶段与验收出口

本节规定系统逐步形成的能力和验收出口，不替代后续逐文件实施计划。

| 阶段 | 主要产物 | 验收出口 |
| --- | --- | --- |
| P0 数据与规则样本 | 统一 Schema、设备映射、代表菜谱审核集、ExtractionRun 归档 | 关键工艺可表达，来源与修订可追溯 |
| P1 离线发布与图谱 | 数据发布包、图谱投影、知识快照、索引与版本校验 | 100 道菜最终覆盖，图谱可重建，关闭 Neo4j 可在线冷启动 |
| P2 基础调度 | Compiler、Greedy 插入与回退、CP-SAT、校验器、约束目录与规模统计 | 人工与设备无冲突，剪枝保真，失败状态与诊断可解释 |
| P3 共享优化 | 共享前处理、批次、物料映射 | 精确覆盖与热加工案例通过 |
| P4 执行和重排 | 会话、事件、库存、版本事务、异常恢复、模拟器 | 加菜、延误与失败恢复保留实际事实，释放和重试语义正确 |
| P5 接口和展示 | 比赛 Adapter、通知、甘特图 | JSON 契约通过，重排变化可解释 |
| P6 实验与交付 | 受控实验、时长扰动、属性与故障测试、性能报告、部署包 | 形成可复现结果、恢复证据和公网服务验证 |

P1 的最终全量审核可与 P2 的代表性案例开发并行推进。P2 开始不需要等全部人工补全完成，但 P6 正式发布必须覆盖全部固定菜谱。

每个阶段保留可运行的最小系统，复杂共享和精细人工优化通过功能开关逐步启用。原始数据中的强制工艺不能通过关闭优化功能而被删除。

| U13 | 蒸烤一体机与清单分列设备的物理对应 | 默认两台设备，按实例可配置 | 审核实际工艺与设备映射 |

这些事项不阻止内部数据模型、求解器、状态机和显式开发 Adapter。9 月 30 日答疑已解决后轮单菜追加的输入语义，并给出任务身份建议；U01 的传递细节、U02 的动态输出和 U03/U04 仍须明确，不能据此宣称全部正式动态接口已联调。P5 准备见独立基线，实际进度只维护在 task.md。

技术风险与处理：

- 候选增多导致求解更慢：记录规模，确定性截断，保留单独候选和可行解。
- 数据估时影响“最优”含义：固定审核与时长策略版本，按第 21.7 节记录扰动和重排效果。
- 人工目标模型过大：跳过精确优化阶段，保留准确测量与明确优化标志。
- 图谱投影、规范化知识与快照不一致：发布时做语义核对，启动时检查版本和哈希；在线不依赖图数据库连接。
- 求解时状态变化：基于 state_revision 条件发布。
- 输出量化导致错误：先构造可表达的模型，再求解和双层校验。
- 原始菜谱缺少可实现路径：离线修订，运行时不编造替代工艺。

### A.4 关键设计不变量

1. 正式知识版本不可在运行中静默改变。
2. 每个必须满足的加工需求都有可解释的供应或执行来源。
3. 每个实际载体只占用一次实际资源。
4. 原料相同不自动产生依赖，能够共享不自动强制合并。
5. 共同热加工不改变每道菜未经审核的有效加热时长。
6. 没有完成事件或明确模拟规则，不把计划结束当作实际完成。
7. 未经独立校验的候选不能作为成功计划发布。
8. 过期状态上的求解结果不能覆盖更新后的运行事实。
9. 同一物料数量不能在多个需求中重复消费。
10. 官方输出来自同一已发布计划，不能由大模型另行编造数值。
11. 求解状态、优化阶段和最优性声明相匹配。
12. 关闭优化功能不能删除菜谱的强制工艺。
13. 在线知识来自经过校验的固定快照，Neo4j 可用性不决定在线调度是否能够启动。
14. 工序失败和设备恢复均不自动证明资源已释放；重试使用新的执行身份。
15. 时长估计、实际完成和缓冲预约分别记录，固定热工艺不因风险缓冲被改写。
16. UNKNOWN、预算截断和未最小化的冲突集合均保留真实含义。
17. 抽取结果能够追溯到实际输入、返回、处理版本和人工修订。
