## 2. 可以直接实施的开发协议

以下是 **USER_AUTHORIZED_PROJECT_DESIGN**，用于 P5 开发和提交接口说明。查询参数、幂等头和累计响应范围是已获用户授权的项目选择，尚未得到赛方逐字段确认。当前机器可读定义在 `data/preparations/p5-v2/implementation_inputs.json`，运行契约在 `app/api/competition_profiles.py`；`p5-v1/competition_profiles.json` 保留历史草案。

建议请求：

~~~http
POST /api/competition/plan?task_id=meal-001
Content-Type: application/json
Idempotency-Key: meal-001-initial-001
~~~

请求体保持 `[{"id":"真实菜谱ID","name":"原名称"}, ...]`。

| 调用条件 | 开发处理 |
| --- | --- |
| 首次出现的 `task_id`，非空数组 | 创建并持久保存任务到会话的映射；`START_SESSION` 初排；单菜初排也合法 |
| 已有活动 `task_id`，恰好一项 | 将该项转为 `ADD_RECIPE`，完整求解累计未完成菜单，使用重排预算 |
| 已有 `task_id`，多项数组 | 本开发 profile 明确拒绝；不猜测是全量覆盖、批量新增还是独立请求 |
| 未携带 `task_id` | 保留独立初排兼容模式；不能通过数组长度、菜名、调用间隔或单并发猜测属于哪个旧任务 |
| 相同任务和相同幂等键、同内容 | 返回该请求的既有业务结果及绑定的发布身份，不重复加菜；动态 HTTP 请求摘要不得依赖服务器新生成的接收时刻 |
| 相同幂等键、不同内容 | 冲突，不落新事件 |
| 无幂等键，再次追加已在任务中的相同菜谱 ID | 当前开发范围拒绝重复菜品；不推断用户要第二份，也不把载荷相同永久等同于请求重试 |
| 任务结束后复用旧 `task_id` | 拒绝追加，保留历史；新一轮使用新任务身份 |

`task_id` 映射和 HTTP 请求身份需要新的持久表及迁移，不能只放进内存字典。首次建任务与幂等登记需要事务保护，避免并发首次请求创建两个会话。HTTP 重试首先查已有请求身份，再检查当前版本，复用 P4 的事件和发布幂等机制。

建议开发流程：同一 `task_id` 的三菜初排 → 同一 ID 追加一道菜 → 再追加一道菜；每次内部计划都完整覆盖累计菜单。不同 `task_id` 独立维护菜单和执行事实。共享一个求解进程只表示计算资源有限，不表示共享做饭会话。

## 3. 加菜时加工进度从哪里来

连续 HTTP 调用只提供新增需求。答疑没有说明工序执行反馈、模拟加速或自动推进方式。

开发默认采用 **PLAN_ONLY**：底层保持人工反馈语义；没有实际开始/完成反馈时，旧菜仍为未执行需求，可以重新排列。服务器经过了几秒、返回了初排结果，都不构成操作已完成的证据。真实执行演示通过内部事件 API 提交反馈，模拟演示明确使用 `SIMULATED`，两者都复用 P4 的状态机、物料账和冻结规则。

已完成工序冻结实际时间；运行中的物理设备、批次成员、真实消费和内部阶段保持不变；腌制从实际起点计算已等待时间；预计结束只产生提醒。不能为了“看起来重排了”在第二次比赛请求前自动执行旧计划。

比赛任务的初始化可使用 `COMPETITION_PROFILE` 事件来源；具体人工、设备及模拟反馈仍保留各自来源。P5 不增加真实 IoT 控制，也不开放无审核依据的库存替代或失败续做。

## 4. 成功响应和时间投影

五个成功字段保持 `overview`、`cookingTimeline`、`ingredientsSummary`、`detailTimeline`、`recipeDetail`。内部版本、日期、任务/请求身份不加入这五项之外的 JSON 字段。

存在一个必须记录的规范冲突：旧规范要求 `recipeCount` 等于当前请求数组长度、两种菜谱明细只覆盖请求菜谱；加菜请求只有一项，但新的内部调度必须覆盖原菜单加新菜。答疑没有说明重排响应范围。

开发 profile `QA0930_TASK_INSERT_DEVELOPMENT` 选择 **累计菜单输出**，`recipeCount` 为该任务本轮有效累计菜品数，菜单中使用 `recipe_instance_id` 区分身份。该选择有利于查看整桌新排程，但不能宣称与原静态契约已经完全相容。静态 `STATIC_ARRAY_V1` 继续按输入长度校验。不得静默删除旧规则或把累计响应交给仅针对原请求的校验器。

若赛方要求仅返回新增菜，则另选 `REQUEST_ONLY` 投影策略：内部仍规划整桌，返回新增菜的实际边界；整桌调整通过内部 API 展示。采用哪一种需要接口提交时确认，不能按客户端请求长度自动切换响应含义。

内部继续使用原会话时间原点和完整实际历史。开发累计响应使用 **SESSION_ORIGIN**，`detailTimeline` 区间相对初次任务原点，避免把已完成动作投影成负分钟或再次加工。原规范的“每次接收时刻为规划开始”只直接适用于独立初排；重排原点仍需确认。串行基线、`timeSave`、已完成菜是否继续展示也必须随 profile 明确，不现场取零掩盖口径差异。

秒级输出需要同步处理全部时间字段：当前 P0 `competition_contract.py` 的 `MinuteString`、`MinuteInterval`、`parameters.time` 和时间投影核对仍只接受整数分钟。P5-02 应增设版本化小数分钟开发契约，复用已有秒到小数分钟的精确回读校验；保留旧整数契约读取与测试。原规范的整数 `parameters.time` 尚未获赛方修订，不能擅自声称所有 100 道秒级工艺均已满足原接口。不可逐字段四舍五入或延长原工艺以通过类型检查。

先以内部数字时间校验依赖和设备，再投影 `HH:mm`；跨日展示端保留完整日期。同名“麻辣对虾”的两个真实 ID 必须保留，不能按名称去重。设备主要展示字段不能丢失实际多设备接力；不使用官方示例中有疑问的装盘时间作为算法正确答案。

## 5. 前置代码与接入缺口

固定输入保持 `delegated-v3-p4-preparation-v1-all`、100 菜、1562 工序、27 设备配置及 S02/H02；使用 `data/policies/p4-runtime-v1.json`。P4 已实际 DEVELOPMENT_VERIFIED：733 次测试执行通过、0 失败/跳过；100 份历史计划再次独立校验通过。知识仍为已授权的 development 发布，不重新申请本轮已有数据代审授权。

| 接入对象 | 已有实现 | P5 需要补充 |
| --- | --- | --- |
| 知识 | `SnapshotKnowledgeRepository` / 固定发布加载 | 生命周期加载全目录、持有会话固定版本，读菜谱与子图不查 Neo4j |
| 执行事实 | `app.runtime.service.RuntimeService` | HTTP DTO、接收时刻、版本错误与来源校验 |
| 事件与重排 | `PlanningService.apply_event` / `drain` | 服务单例；线程池中执行阻塞编译、求解等待和 SQLite 操作；不同任务的持久待重排作业恢复 |
| 预算 | `Deadline`、`ComputationBudget` | 从 HTTP 入口开始计时，贯穿任务映射、事件、计算、校验、发布和序列化；不得再领取一份完整预算 |
| 发布 | `PlanPublisher` | 只有已提交、与请求绑定的发布计划能返回成功；PENDING/FAILED 不包装为旧计划成功 |
| 通知 | P4 持久通知及撤销 | 模板、派发、SSE 游标恢复、客户端去重，SSE 接收不等于执行确认 |
| 模型 | 已有离线抽取 Provider/HTTP 适配 | 独立意图 Schema 与归档，不把菜谱抽取请求直接拿来做在线意图 |
| HTTP/前端 | 尚无 `app/main.py`、`app/api/`、`web/` | 按八项任务逐步建设，不把准备场景当作实际接口通过 |

现有 `PlanningService.apply_event(event)` 在方法内创建截止时间，`drain` 支持传入截止时间；P5 入口如需统一 HTTP 总预算，应作兼容的最小接口补充或集中编排，禁止在多个层次重置截止时间。P4 的单作业锁、事件短事务和状态/计划双版本 CAS 继续保留。健康、事件接收、历史读取和 SSE 在求解中也必须响应。

P5 初排/重排工程预算仍为 4200/2400ms，Greedy 150/100ms，CP-SAT 全阶段 3000/1500ms，发布预留 400/300ms。比赛优秀阈值为初排 <5s、重排 <3s，合格阈值 <10s/<8s；同时记录 HTTP 客户端和服务内计时。P4 第五轮 90 次预热重排 P50/P95/最大为 1901.391/2127.233/2223.686ms、0 失败；初排有一次 4515.270ms 发布前回滚的长尾，仍需调优，不能把 P4 求解数据当作 P5 浏览器响应已经达标。

## 7. 开发顺序和准备场景

建议顺序：**P5-01 → P5-03 → P5-02 → P5-05/P5-04 → P5-06 → P5-07 → P5-08**。保留原八个任务编号。

P5-01 先建立可冷启动的容器、固定快照、SQLite、工作进程和错误边界；P5-03 建立普通事件入口与只读查询。P5-02 再接任务映射、初排/单菜追加、独立请求兼容、版本化输出校验和协议 profile，保证结构化动态流程先贯通。通知与语言入口接入统一事件链；前端从真实后端读取已发布版本，最后做浏览器联调。

`api_scenarios.json` 保存 **DESIGN_ONLY** 场景，真实 ID/名称来自固定发布。必须转为可执行测试后才能作为功能证据。覆盖以下内容：

- 三菜初排、一次和多次单菜追加、首轮单菜、跨任务隔离、缺任务身份、已有任务多项输入及结束任务复用。
- 相同请求重试、不同内容复用键、首次请求并发、提交后响应丢失、重启后的任务与请求身份。
- 整桌完整覆盖、累计响应与静态响应范围冲突、原点与历史、整数/小数分钟、跨日、同名异 ID、未知整数映射。
- 加菜时无执行反馈、人工完成冻结、正在运行的腌制/热批次、故障未释放、求解中收到事件、重排失败保留事实。
- SSE 断线恢复、旧提醒撤销、语言模糊/超时/禁用模型、浏览器重复点击、Neo4j 停库冷启动、求解期间健康与读写响应。
- 答疑 5 的独立食材分支与同食材强依赖：可以改变独立分支的先后，不解除单人人工互斥。

场景的预期逻辑只确定可验证的不变量，不编造一个固定“最优”甘特图。成功计划仍由真实 Compiler、Greedy、CP-SAT、Validator 和 SQLite 发布链验证。

准备生成器固定 38 个场景、8 组正负请求夹具和 9 项协议未决问题；检查器使用真实知识仓储和现有请求校验器核对输入。P4 的前置通过结果通过报告、实际命令、原有 339 个源码/配置哈希及 100 份历史计划哈希核验，本轮不重新执行整阶段。准备校验结果只说明后续实施输入可用，不表示场景已经运行。
