## 2. 优化目标与参数

当前代码已实现：总耗时、出菜差超标量、最长连续人工忙碌、重排稳定性模型。累计人工用时只有统计。本轮确认将累计人工用时加入设计，**尚未将其标记为已实现**。

| 优先步骤 | 目标与约束 |
| --- | --- |
| A | 找到较短且合法的总完成时间 C_ref |
| 总时间上界 | C_ref + min(120 秒，5% × C_ref 向上对齐到秒)；有有效串行基线时不得超过串行时间 |
| B | 在上界内最小化 max(0, 出菜时间差 − 240 秒) |
| C | 保持 B 的结果，再缩短总完成时间 |
| D1（待实现） | 保持上层结果，最小化所有实际选中人工段的累计秒数 |
| D2 | 保持上层及 D1 结果，缩短最长连续人工忙碌块 |
| D3 | 保持上述结果，尽量减少未开始任务的时间、资源和分组变化 |

累计人工只算主动操作，共享操作只计一次，腌制、自动加热与纯等待不计；不能通过把主动操作改为等待来制造收益。已完成的人工用时是固定常数，运行中的已执行部分不能删去；全程和剩余计划分别报告。共享只是候选，不强制采用。

连续忙碌块之间的有效休息阈值为 60 秒。累计人工 D1 可以直接对选中人工段时长求和；D2 的精确顺序模型仍受 120 段和剩余预算约束。每阶段需报告是否实际优化、是否超时和最优界；没有执行 D1 时不能声称累计人工已最优。

| 参数 | 确认值 |
| --- | --- |
| 人工 / 灶眼 | 固定 human_1、容量 1 / burner_1、burner_2 |
| 时间 | 内部整数秒，默认输出小数分钟；禁止逐字段四舍五入 |
| 初排预算 | 总 4200 ms；Greedy 150 ms；CP-SAT 全阶段合计 3000 ms；发布预留 400 ms |
| 重排预算 | 总 2400 ms；Greedy 100 ms；CP-SAT 全阶段合计 1500 ms；发布预留 300 ms |
| 求解并发 | 一个作业、一个常驻求解进程，最多 4 个搜索线程 |
| 数据库 | SQLite，WAL；busy_timeout 100 ms，最多写重试 2 次 |
| 求解状态冲突 | 剩余预算内最多重算 1 次；拒绝旧状态结果覆盖新事实 |

可运行的现有算法配置为 `planning_policy_current.json`；新增目标及事件策略为 `runtime_design.json`，后者标记 DESIGN_ONLY，不作为已经支持新目标的 SchedulingPolicy 直接加载。

## 3. 重排触发规则

事件先校验身份、来源和预期版本，在短事务内更新事实，再判断是否需要重排；求解在事务外进行。重复事件只返回原处理结果，不能重复扣料、释放资源或触发新求解。无变化的观测不反复触发重排。

| 事件 / 场景 | 处理及是否求解 |
| --- | --- |
| START_SESSION | 建立会话，触发初排 |
| ADD_RECIPE / CANCEL_RECIPE / DELAY_RECIPE | 合法且实际改变未完成需求后重排；运行中取消保留实际占用 |
| OPERATION_STARTED / COMPLETED | 每次都记录有效事实；按计划发生且剩余计划仍合法时仅推进执行，不必全量重排；实际偏差、产物或资源变化影响余下计划时重排 |
| DURATION_UPDATED | 剩余时间真实改变并影响预约时重排；未知剩余时长不取零 |
| OPERATION_FAILED | 记录失败、物料结果和未确认占用，停止受影响派发；重排其他可执行部分，不能将缺必需菜的部分计划当完整成功 |
| DEVICE_UNAVAILABLE / RECOVERED / STATE_UPDATED | 新状态影响已选设备、合法候选或后续预约时重排；恢复不等于占用已释放 |
| DEVICE_RELEASE_CONFIRMED | 校验对应 execution_id，释放旧占用；影响待执行任务时重排 |
| MATERIAL_SHORTAGE / ADJUSTED | 更新真实物料账，影响需求或候选供应时重排 |
| MANUAL_OVERRIDE | 仅允许现有白名单偏好/剩余时间修正，实际改变计划条件时重排 |
| OPERATION_RETRY_REQUESTED | 只有合法恢复规则才建立新执行身份，再重排；无规则则拒绝并保留失败历史 |
| ADVANCE_SIMULATION | 仅模拟模式推进时钟，处理已发生的开始/完成事件；不能提前把未来扰动传给 Planner |
| RESET_SESSION | 结束会话、撤销未来派发并保留历史，不自动把正在进行的物理动作或设备占用清空 |
| 人工模式到达预计结束时刻 | 提醒/标记待确认，不自动完成或释放；不能每秒盲目重排 |

实现时设置明确 `requires_replan` 与原因。求解期间同一会话的新事件先落账，将后续计算合并到最新 revision；旧结果不得发布。事件确认不是自动保证新计划成功，失败必须显式返回状态并阻止失效任务继续派发。

## 4. 人工释放与等待的执行语义

普通工序使用拆分动作表示，不能给一个 20 分钟整体任务仅填“人工 3 分钟”却缺少具体占用边界。主动操作与等待是不同执行节点，必要时使用已有批次内部阶段。

示意场景（合成参数，不改真实菜谱）：拌料 0～3 分钟占 human_1；3～23 分钟腌制不占人；23 分钟后取出/装入重新申请人。第 3 分钟确认拌料完成后，人可立即处理其他菜；鸡腿仍须满足完整 20 分钟腌制。若还需要装入冰箱，该搬运动作也需人工段；冷藏等待保留温区占用。

当前真实例：南瓜鸡腿煲 `65795250c458a177d8438dea` 中，`op_007_01` 混合 120 秒、`op_008_01` 调味混合 120 秒占人；`op_009_01` 腌制 1800 秒只占冷藏；`op_011_01` 装入 30 秒重新占人。发布中 28 个 MARINATE 节点均不占人工。

人工模式的实际释放依赖合法完成反馈，不依赖计划时钟。整道菜不必完成才释放人；同一设备自动运行时，人也可以已释放。实际开始必须记录等待起点；依赖前一步的真实完成时刻计时，而不是继续用已过时的原计划时刻。重排时保留已经发生的腌制时间；未知开始时刻不得凭空补足。

## 5. P4 开发顺序与验收场景

1. P4-01：运行库、迁移、短事务、事件与版本唯一性。
2. P4-02 / 04：事件去重、状态机、人工释放、模拟时钟和确认反馈。
3. P4-03 / 05：物料账、合法余料及已完成/运行中事实冻结。
4. P4-06：补齐累计人工目标及比较器、Greedy 选优和报告字段，再接入加菜/延误/取消重排。
5. P4-07～10：条件发布、冲突恢复、设备异常、合法重试、通知与完整验收。

必须覆盖：腌制中人去切另一菜；人工反馈迟到不提前放人；两个主动开始争用 human_1；腌制中加菜不重新计时；已开始热批次不得塞入新菜；故障后恢复但未清空；事件重复和同 ID 异载荷；求解期间新事件；定性余料拒绝虚构克数；重启不凭时间补完成；旧通知撤销；总人工目标与连续忙碌目标给出不同选择的小规模见证。

机器可读设计场景：`data/preparations/p4-v1/runtime_scenarios.json`。场景是 P4 待实现断言，不是已经通过的动态功能测试。
