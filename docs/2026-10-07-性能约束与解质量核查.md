# 性能、约束、交互与解质量核查（2026-10-07）

## 结论

本次代表菜单的已预热本机响应速度满足用户观察的三秒内返回；计划可行性和主要接口功能有实际证据。解质量尚不足以稳定满足“全部菜品在五分钟内出锅”的优秀指标，且至少四个实测菜单存在明确、合法的改进空间。真实浏览器还观察到提醒 SSE 的 SQLite 写锁异常，不能将浏览器断言通过等同于交互可靠性验收通过。

本次新增核查脚本、报告和任务记录。被测应用及基准源码哈希保持一致；菜谱、工艺、在线默认策略和实际运行数据库沿用原内容。

## 被测范围和指标定义

- 当前默认策略：`data/policies/p4-runtime-v1.json`，OPTIMIZE，初排总预算 4200ms、重排 2400ms，CP 总预算分别 3000/1500ms。
- 当前在线发布：`delegated-v3-p4-preparation-v1-all`，development，100 菜谱、1562 工序。发布知识直接从离线快照读取。
- Windows 11；Python 3.12.14；i7-1165G7；8 逻辑线程；约 32GB 内存。一个 API 实例、一个求解进程、单并发调度、最多四个搜索线程。
- 固定代表场景为 combination-000/031/041/043/052 和 replan-000/001/002/003；共九个场景，八种不同初始菜单，初始均为四或五道菜。三轮共 27 次初排、12 次重排。动态脚本包含加菜、推迟、取消及另一加菜身份场景。
- HTTP 为真实本机回环 TCP。所有成功响应从独立测试 SQLite 重载，再运行完整 ScheduleValidator 和比赛 JSON 事实投影校验。二次验证与报告 IO 在计时范围之外；HTTP 本身的编译、求解、验证、发布和序列化在计时范围之内。
- 五分钟优秀指标按 `max(各菜完成时刻) - min(各菜完成时刻) <= 300秒` 统计，采用内部整数秒；这不是要求整桌菜五分钟内做完。恰好 300 秒按本次用户口径计入。
- 这是代表样本评估，不是 100 单菜及 200 菜单全量重跑，也不是公网、多并发或官方动态联调。

## 为什么在线这么快，为什么质量会波动

1. **主要语言理解提前完成。** 在线结构化请求使用固定快照，初排、重排不依赖 Neo4j 或在线大模型；本次没有真实收费模型调用。固定 ID 定位和参数整理的成本已经在离线流水线承担。
2. **模型规模适中。** 代表请求有 35～84 个逻辑任务，40～93 个保留候选。CP-SAT 的 hint、依赖边界预处理和并行搜索能很快找到合法解。本次 39 个请求均未发生候选截断，快速不能归因于本次删掉必需工序或候选。
3. **先有完整可行方案。** Greedy 构造合法候选，求解器再尝试改进；最终只发布通过独立扫描的方案。39 个结果选中来源为 CP_SAT 38 次、GREEDY 1 次；这不代表全部质量阶段成功。
4. **预算和优化阶段会主动停止。** 默认初排/重排总预算为 4200/2400ms，比赛适配器还预留 400ms 做响应处理。参考构造与所有优化共享 Solver 额度；Planner 再把剩余额度切分给总时长、出菜差、人工和稳定性各阶段。
5. **后续阶段常因时间片过短未运行。** 常驻工作进程须预留建模、JSON 编解码及 IPC 时间。参考构造会先消耗额度；剩余片段若短于测得的最低开销，worker 返回 UNKNOWN，部分片段在建模时就超时。当前代码位于 `app/scheduling/engine.py` 和 `app/scheduling/worker.py`。本次共 210 个阶段结果：95 OPTIMAL、13 FEASIBLE、102 UNKNOWN；其中 39 OPTIMAL 是串行参考，不能当成 39 个发布计划全目标最优。
6. **出菜差是软目标。** 当前目标为 240 秒，通常只在总流程允许额外 5%、最多 120 秒的范围内改善。未找到达标候选也可合法返回。人工总工作量、连续忙碌和稳定性依赖更晚的阶段；本次 39 个结果的这三类优化完成标记全部为 false，因此不能保证“减少总人工时间”。
7. **另有可选快速策略。** `p6-feedback-fast-v2.json` 使用 FEASIBILITY_FIRST，重排 3000ms、Solver 2100ms；在已有合法 Greedy 候选和串行参考时省略可选质量阶段。`p6-window-guard-v1.json` 另加派发保护。这两份不是本次 HTTP 表格的默认被测策略，不能将策略间的速度或出菜率直接混算。

最值得先改进的是优化阶段时间分配与模型/消息的重复构造成本，并为五分钟目标提供明确的搜索优先级和返回质量标记。本次反例显示仅盲目增加整体求解时间不是唯一方向；进程内完整合法的改进见证本身通常很快。具体方案需要新的实现与同预算实验，不能把本次离线对照直接写成上线修复已完成。

## 专项测试及环境失败

同一专项测试集第二轮实际 **213 通过、0 失败、0 跳过**，耗时 124 秒。包含 Validator 故意错误计划、设备例外、强制程序、目标阶段、总人工小例独立枚举对照、估计/审核重放、比赛接口与事实投影、人工反馈、重排冻结、通知原子提交，以及旧 P2 发布的 100 单菜路径扫描。

第一轮 70 通过、143 失败，84 秒；143 项全部是读取旧 `data/releases/development-v3-rebased-v2-all/manifest.json` 的同一个 Windows PermissionError。使用已存在的 `.tools/p2-regression/releases` 回归副本重新运行。副本 snapshot_id 与当前旧发布指针一致，加载时执行完整文件哈希校验；没有改快照权限、知识、断言或将失败设为预期通过。

证据：[原失败 XML](../benchmarks/reports/2026-10-07-user-audit-regression.xml)、[同集重跑 XML](../benchmarks/reports/2026-10-07-user-audit-regression-run2.xml)。pytest 缓存写入权限和依赖弃用警告分别保留，不是功能断言失败。

真实 Edge/Playwright 三个现有场景实际 **3 个断言场景通过**，44.5 秒；但服务日志出现 `sqlite3.OperationalError: database is locked`，随后为 `Caught handled exception, but response already started.`。项目 `tests/web_verification_support.py` 的完整质量门槛明确拒绝带这类异常的运行，因此本次不将该浏览器运行标为完整验收通过。

异常路径是 `app/api/notifications.py` 的 frames 在响应开始后的重复 poll → `NotificationDispatcher.poll` → `UnitOfWork.transaction` 的 BEGIN IMMEDIATE。数据库 busy_timeout 为 100ms；SSE 已开始后无法再转成正常 JSON 错误响应。流开始前的同类锁冲突会返回 503，边界不同。

独立真实 API 上在首帧发送后持锁，三次均出现长期 SSE 提前结束（客户端 StopIteration），API 日志有数据库锁及响应已开始异常。解锁后通过新 TCP 连接查询提醒均为 200，执行事实未改变。StopIteration 在这里表示持续流提前 EOF，不能因 HTTP 首部是 200 就判为正常提醒交付。第一轮在流开始前持锁只得到诚实 503；第二轮复现异常后复用已断连接做恢复检查而提前中止；两轮报告和日志均保留。最终 [三次复现报告](../benchmarks/reports/2026-10-07-user-audit-quality/notification-lock-run3/report.json) 绑定此观察，分类时同时检查三个流的提前结束及服务端异常日志。
